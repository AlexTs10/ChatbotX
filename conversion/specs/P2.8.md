# P2.8 — Realtime gateway in Rust (analyst spec)

Unit: replace `apps/realtime` (uWebSockets.js gateway, Redis Streams reader) and the Redis part of the producers (`packages/business/src/platform/realtime-*.ts`) with the crate `crates/rt`: an axum WebSocket route on the one server and an in-process `tokio::sync::broadcast` fan-out. One Rust binary, one person, SQLite (one writer + 3 readers). No Redis.

## 0. Scope and facts

| Owner | Part | Status |
|---|---|---|

Facts that drive the design:

1. **The socket is server -> client only.** The behaviors register no `message` handler: a client frame other than pong/close is ignored. Guest typing and every other client action go over HTTP. So the gateway only authenticates, replays and pushes.
2. **Redis Streams were the only cross-process link.** The builder and the worker appended to `rt:{shard}` (256 shards); the gateway read with `XREAD BLOCK 1000 COUNT 200`. In one process the producers call the hub directly. The shard keys, the reader loop, its PING probe, reconnect/recovery, the "tainted" shard marker, the 512-entry recent ring and the activation cursor exist only to bridge processes and Redis races. None is needed.
3. **Replay was best effort already.** `realtime-stream-publisher.ts:18`: "A capped shard is replay best-effort; clients must tolerate missed records." Redis kept the stream over an app restart (5 min); an in-memory buffer does not. After a restart every client reconnects with its old `lastSeq`, gets 4002 `replay-cursor-ahead`, runs its resync (refetch) and goes on. P2.7 K44 judged this acceptable. **Only the revoke marker must survive a restart** (P2.7: `DurableKv`).
4. Records are typed in Rust and validated at publish. "Malformed record" cases (rolling-deploy skew, other writers) cannot happen.
5. The gateway and the builder used one shared secret (`REALTIME_BROADCAST_SECRET`, ≥ 32 chars) for HS256 JWTs. In one process the minting endpoint and the verifier are the same binary; the token stays (the browser passes it in the URL; clients do not change).
6. Presence went gateway -> HTTP POST `/api/workspace-presence/report` (JWT + `bodyHash`) -> `workspacePresenceService.heartbeatMany` -> `presenceStore` (Redis ZSET) + `WorkspaceMember.onlineSince` on transitions. In one process: gateway -> `PresenceSink` trait -> the same service on `kv::Presence`. The HTTP hop, its token purpose and `bodyHash` go away.

Counts: 19 event types; 4 stream record kinds; 5 close codes (4000–4004) + 4 HTTP refusals; 2 socket routes + 2 probes; 42 publish call sites in 27 files (1.6); 236 frozen test cases in scope (section 4).

## 2. Behaviour to keep

### 2.1 Auth (`packages/realtime-protocol/src/auth.ts`)

- HS256 JWT, secret `REALTIME_BROADCAST_SECRET` (≥ 32 chars). Header `{"alg":"HS256"}`. Claims: `iat` (s), `exp = iat + 60`, `aud = "<kind>:<id>"`, `purpose`, plus purpose claims. Verify: algorithm HS256 only, signature, `exp` and `nbf/iat` with **5 s** clock tolerance, `aud` exact, `purpose` exact, then the claim schema.
- Purposes: `member-connect` (`userId` non-empty, `chatScope` ∈ all/assigned/none, `teamIds[]` default [], `iat`, `iatMs` integer ≥ 0; `iat = floor(iatMs/1000)`), `guest-connect` (`guestConversationId`, `workspaceId`), `presence-report` (`bodyHash`).
- `issuedAtMs` is read by the mint **before** the membership lookup (`mint-member-connect-token.ts:9-13`), so a permission change that races the mint is caught by the marker compare `revokedAt > iatMs` (strict).
- Revoke: `realtime:revoked:<ws>:<user>` = max revoke ms, TTL 65 s (= token TTL + tolerance). Checked at upgrade, then again after replay load (race), and live through `member-revoke`. A non-numeric marker counts as revoked. Read error -> 503 (fail closed).
- `extractBearerToken`: `"Bearer <t>"` -> `t`, else `null` (used by the token mint routes).

### 2.2 Channels, scopes and routing (`delivery.ts`)

- Member sockets are indexed by `(ws, user)`; `chatScope: all` sockets get the full batch (uWS topic `ws:<ws>:all`, one serialization); `assigned` sockets are grouped by `(user, sorted teamIds)` and get only events with no `route`, or whose `route.assignedUserIds` has the user or `assignedTeamIds` meets the socket's teams (one serialization per group); `none` gets no workspace events. Member-send records reach every socket of the member regardless of scope.
- Guest sockets subscribe to `guest:<ws>:<guestConversationId>` (the workspace is part of the key: the same conversation id in two workspaces is two channels).
- `resyncWorkspace(ws, reason)`: closes 4002 every member and guest socket of the workspace.

### 2.3 Replay (`replay.ts`, `stream-reader.ts`)

On connect with `lastSeq`:
1. `lastSeq` absent -> no replay; the cursor sent on open is the newest id ("0-0" for an empty stream).
2. Not `^\d+-\d+$` -> 4002 `invalid-last-seq`.
3. Oldest retained id after `lastSeq` -> 4002 `replay-window-expired` (also for `0-0` against non-empty history).
4. Stream empty and `lastSeq != 0-0`, or `lastSeq` after the newest id -> 4002 `replay-cursor-ahead` (this is also the restart case).
5. More than **500** of the workspace's own entries after `lastSeq` -> 4002 `replay-window-too-large`.
6. Else send the entries (filtered as live), then the cursor frame, then live records.

Retention: `XADD MAXLEN ~ 10 000` and `XTRIM MINID ~ now − 300 000` per shard; a 512-entry in-memory ring per active shard closes gaps between replay and live reads. Revoke entries are never replayed (the connect-time marker check covers them).

### 2.4 Heartbeat, lifetime, timeouts

- Server: `{"hb":1}` every 25 s; uWS `idleTimeout: 60` with automatic pings (a dead peer is closed after ≤ 60 s without data/pong).
- Client: closes 4000 when no frame arrives for 60 s; reconnect backoff: random in `[0, min(30 000, 500 × 2^attempt))`; attempt resets after 10 s of uptime; a 4003 uses `retryAfter` exactly and survives `reconnectNow` (focus/online events).
- Connection lifetime: `REALTIME_CONNECTION_LIFETIME_MS` (default 1 800 000, min 60 000) ± 15 % jitter -> 4004 `connection-lifetime-exceeded`.
- Shutdown: stop timers, wait `REALTIME_SHUTDOWN_DRAIN_MS` (default 5 000), close every socket 4003 `{"retryAfter":1000–4999}`; producers flush pending batches (`flushAllPendingWorkspaceRealtimeEvents`); force exit after 10 s.

### 2.5 Backpressure and limits

- Slow consumer: uWS `maxBackpressure: 512 000` bytes with `closeOnBackpressureLimit`; a send that returns "dropped" or throws -> 4002 `backpressure-drop` / `send-failed`.
- Admission (env, defaults): `REALTIME_MAX_CONNECTIONS` 10 000 (members + guests), `REALTIME_MAX_CONNECTIONS_PER_WORKSPACE` 500 (members), `REALTIME_MAX_GUEST_CONNECTIONS` 8 000, `REALTIME_MAX_GUEST_CONNECTIONS_PER_WORKSPACE` 1 000, `REALTIME_MAX_CONNECTIONS_PER_GUEST` 5 (per `(ws, guestConversationId)`). Counts include pending upgrades. Over a cap -> upgrade, then close 4003 with `retryAfter`.
- Token mint rate limit (builder, P2.7 K1): guest realtime mint 100 / 10 s per workspace.
- Producer: 25 ms / 64 events / 256 KiB per workspace record; 8 appends in flight.

### 2.6 Presence (`lib/presence-reporter.ts`, `lib/presence-report.ts`, `workspace-presence/service.ts`)

- `connectedUsersByWorkspace`: a user's first socket marks the workspace dirty; reports are coalesced **1 000 ms**; a sweep every **10 000 ms** (`PRESENCE_REPORT_INTERVAL_MS`) reports every connected workspace, stalest first; **16** reports at once; a workspace is never reported twice at once (a `reportNow` during a report re-runs after it); a failed report keeps the workspace stalest. A closing last socket sends **no** report (the lease expires after `PRESENCE_TTL_MS` 20 000).
- Report = up to **5 000** user ids -> `heartbeatMany(workspace:presence:<ws>, ids, 20 000)` -> newly live ids -> `WorkspaceMember.markOnlineBulk` (one DB write). Readers: `listOnlineMembers(ws)` (≤ 200, recent first) for VoIP ring targets.

### 2.7 Metrics

Gateway counters logged every 10 s (`realtime_server_metric`: connections, publishes, sends, drops, …); producer relay metrics (`realtime-relay-metrics.ts`) logged per 10 s window, backpressure once per window. Logs only; no endpoint.

### 2.8 Durability across a restart

| State | Old stack | Rust | Why |
|---|---|---|---|
| revoke marker (65 s) | Redis (kept) | **SQLite** `kv_entry` (P2.7) | a token minted before a revoke must not reconnect after a restart |
| replay stream (5 min) | Redis (kept) | memory | best effort; clients resync on `replay-cursor-ahead` |
| presence leases (20 s) | Redis | memory (`kv::Presence`) | sockets reconnect and report within 11 s |
| connections, counters, pending batches | process memory | process memory | — |
| last seq | Redis stream ids | memory, seeded from the clock | ids stay monotonic while the clock does (5.2 item 4) |

## 3. Rust design

### 3.1 Crate place and dependencies

- `crates/rt` (`chatbotx-rt`) sits **below** `core`: `db <- kv <- {jobs, rt} <- core <- {api, server}`. The business code (core) calls the publish API, so `rt` must not depend on `core`. The P2.7 order (`core <- api/rt/server`) needs this one change (decision D1). `rt` depends on `kv` (revoke marker, `Clock`) only; the retry job and the presence service come in as traits.
- Modules: `protocol` (event types, envelopes, records, `Seq`, close codes, route helpers, presence constants), `token` (HS256 JWT), `hub` (buffers, socket index, fan-out), `publish` (producer API + coalescer + relay metrics), `gateway` (axum routes, admission, connection task, heartbeat), `presence` (reporter).
- New dependencies: axum feature `ws` (adds `tokio-tungstenite`, `sha1`, `base64`; workspace axum is already 0.8); `hmac` 0.13 (with the workspace `sha2`) for HS256; `base64` (already pulled by axum `ws`) for JWT segments; `tracing`. Dev: `tokio-tungstenite` client for the gateway tests. No `jsonwebtoken` (it pulls `ring`/`aws-lc`).

### 3.3 Hub: one buffer and one `broadcast` per workspace (`rt::hub`)

```rust
    GuestEvent { guest_conversation_id: String, frame: Arc<str> },
}
struct ConnHandle { id: u64, iat_ms: u64, control: mpsc::Sender<Control> } // Control = Close{code, reason} | Cursor(Seq)
```

- **One lock** (`std::sync::Mutex<HubState>`, no `.await` inside) guards seq allocation, buffer append and `tx.send`. A connecting socket takes its replay snapshot and `tx.subscribe()` under the same lock, so replay and live never overlap or leave a gap. This removes the activation cursor, the 512-entry live ring, `hasRecentEntriesGap`, `taintedUpToId` and their races.
- Seq: `ms = max(now_ms, last.ms)`, `n = 0` or `last.n + 1` on the same ms — the Redis id rule, global for the process, so ids stay ordered across workspaces and the client's `isRealtimeSeqAfter` dedupe still works.
- Buffer bound: 512 entries per workspace is enough because replay refuses more than 500 own entries (2.3 step 5); a cursor older than the evicted part gets `replay-window-expired` (this covers the old `recent-entries-expired`). Age 5 min and 4 MiB per workspace keep memory bounded. Entries are dropped on append and by one maintenance tick every 60 s that runs **only while some buffer is non-empty**; an empty bus with no sockets is removed.
- Producers append even when no socket is connected (a tab that drops for 30 s must replay).
- Revoke and resync never enter the buffer: they go to the live `ConnHandle`s through `control` (bounded 8; a full control queue means the task is stuck and the socket is dropped).
- Fan-out: each connection task `select!`s on `rx.recv()`, `control.recv()`, the heartbeat tick and its lifetime sleep. On a workspace entry it sends `all_frame` (scope `all`), filters `events` by route and serializes per socket (scope `assigned`; few sockets), or skips (scope `none`); member/guest entries are sent when the target matches. `RecvError::Lagged(_)` -> close 4002 `backpressure-drop` (the slow-consumer rule; 256 records behind ≈ the old 512 KB budget for typical frames). A write error -> 4002 `send-failed` attempt, then drop.
- Memory per connection: one task (≈ 1–2 KiB), the axum/tungstenite socket with `read_buffer_size 4 KiB`, `write_buffer_size 0`, `max_write_buffer_size 512 KiB` (the uWS `maxBackpressure`), `max_message_size 64 KiB` (clients send nothing), a `broadcast::Receiver` (one slot index) and a `ConnHandle` (≈ 64 B) ≈ **8–12 KiB**, plus pending frame bytes while the peer is slow (≤ 512 KiB, then the socket is dropped). Buffers: ≤ 4 MiB per active workspace, ≈ 0 when idle.

### 3.4 Gateway (`rt::gateway`)

```rust
pub struct RtConfig { secret: String, connection_lifetime_ms: u64, max_connections: usize, max_connections_per_workspace: usize,
                      max_guest_connections: usize, max_guest_connections_per_workspace: usize, max_connections_per_guest: usize,
                      shutdown_drain_ms: u64 } // same env names and defaults as gateway-config.ts (no Redis keys)
pub fn router(rt: Realtime) -> axum::Router; // /rt/workspaces/{workspace_id}, /rt/guests/{guest_conversation_id}, /health, /ready
```

Upgrade handler (member; guest is the same without the revoke check):
1. Parse path + query; verify the JWT (sync, ≈ 5 µs). Failure -> 401 (rejection log throttled to 1 / 10 s with a suppressed count, as `logTokenRejection`).
2. Admission against counts **including pending** upgrades; over a cap -> accept the upgrade and close at once 4003 `{"retryAfter": 1000 + rand(4000)}`.
3. `PendingGuard` (RAII) increments pending + the workspace `refs`; dropped on every early return **and** when the client aborts (axum drops the handler future), so a dead upgrade never leaks a slot.
4. Revoke check (`RevokeStore` = `DurableKv` read on a reader connection): `Err` -> 503, marker `> iat_ms` (or not a number) -> 401.
5. Replay snapshot + subscribe under the hub lock (2.3 rules); a close reason -> upgrade, then close 4002 with that reason.
6. Recheck the marker (same rule; keeps the TS order for the abort/recheck tests), then `ws.on_upgrade(...)`.
7. In the socket task: register the `ConnHandle`, send replay frames, the cursor frame, arm the lifetime sleep (jittered ± 15 %), add the user to presence when it is the user's first socket. A send failure on any of these steps closes 4002 and skips the later steps (no presence, no timer).

`/ready` is 200 once the router is serving and `Kv` is started (there is no Redis probe). `Realtime::shutdown()` is idempotent: flush producers, wait the drain, close every socket 4003 with `retryAfter`, stop timers; the server binary owns the signals.

Heartbeat: one global `tokio::time::interval(25 s)` task exists **only while at least one socket is open** (started by the first open, stopped by the last close). Each tick sends `{"hb":1}` and a WebSocket Ping to every socket through a shared `watch`/`broadcast<()>` signal; a socket with no inbound frame (pong/close/any) for 60 s is closed (the uWS `idleTimeout`). No per-connection interval.

Compression: axum 0.8 `WebSocketUpgrade` does not negotiate permessage-deflate. Frames go uncompressed (risk 5.2 item 3).

### 3.5 Producer API (`rt::publish`), used by `core` and `jobs` in the same process

```rust
#[derive(Clone)] pub struct Realtime { /* Arc<Inner>: hub, coalescer, presence, revoke store, retry, clock, cfg */ }
impl Realtime {
    pub fn start(kv: Arc<chatbotx_kv::Kv>, clock: Arc<dyn Clock>, cfg: RtConfig,
                 presence: Arc<dyn PresenceSink>, revoke_retry: Arc<dyn RevokeRetry>) -> Realtime;
    /// Coalesced 25 ms / 64 events / 256 KiB; immediate types flush at once. Resolves when the record is in the buffer.
    pub fn publish_workspace_event(&self, workspace_id: &str, event: Envelope) -> impl Future<Output = Result<(), PublishError>> + Send;
    /// `queueWorkspaceRealtimeEvent`: logs and swallows `PublishError`.
    pub fn queue_workspace_event(&self, workspace_id: &str, event: Envelope) -> impl Future<Output = ()> + Send;
    pub fn queue_message_created(&self, workspace_id: &str, message: Value, conversation: Option<&ConversationRoute>, inbox_id: Option<&str>);
    pub fn publish_member_event(&self, workspace_id: &str, user_id: &str, event: Envelope) -> Result<(), PublishError>; // direct
    pub fn publish_guest_event(&self, workspace_id: &str, guest_conversation_id: &str, event: Envelope) -> Result<(), PublishError>;
    /// Marker (`DurableKv::raise_number`, TTL 65 s; 3 attempts, 250 ms linear) then closes live sockets with iat_ms < revoked_at_ms.
    pub async fn revoke_member(&self, args: RevokeArgs) -> Result<(), RevokeError>;
    /// `tryRevoke…`: logs and calls `RevokeRetry::enqueue` (jobs: `retryRealtimeMemberRevoke`, 8 attempts, exponential 1 000 ms).
    pub async fn try_revoke_member(&self, args: RevokeArgs, error_message: &str) -> bool;
    pub async fn shutdown(&self);
}
pub trait PresenceSink: Send + Sync { fn report<'a>(&'a self, workspace_id: &'a str, user_ids: &'a [String]) -> BoxFuture<'a, Result<(), BoxError>>; }
pub trait RevokeRetry: Send + Sync { fn enqueue<'a>(&'a self, args: &'a RevokeArgs) -> BoxFuture<'a, ()>; }
```

- Coalescer: per workspace a pending batch + one `tokio::time::sleep(25 ms)` task created by the first event and gone after the flush (no timer while idle). The append is synchronous (hub lock), so the TS "8 appends in flight" cap and the append-rejection paths do not exist; validation errors still reject the single event without delaying the others.
- `Realtime` is `Clone` (one `Arc`); the server puts it in the app state; `core` services receive it; `jobs` handlers get it through their context. Code rule: never hold the hub lock across `.await` (enforced by `std::sync::Mutex`).

### 3.6 Presence (`rt::presence`)

Same reporter as 2.6 (coalesce 1 s, sweep 10 s stalest first, 16 at once, no double report, rerun after flight, failed = stalest, stop). The sweep interval runs **only while some member socket is open**. `report` truncates to 5 000 ids and awaits `PresenceSink::report`; `core` implements the sink as `workspacePresenceService.heartbeatMany` = `kv::Presence::heartbeat_many("workspace:presence:<ws>", ids, 20 000)` + `markOnlineBulk` for the newly live ids. The presence-report JWT, `bodyHash` and the builder route `/api/workspace-presence/report` are not needed (decision D3).

### 3.7 Idle RSS and wake-ups

| Part | Idle (no socket, no event) | One open tab |
|---|---|---|
| hub state | empty maps (< 1 KiB) | 1 bus, ≤ 512 entries (≤ 4 MiB, usually < 100 KiB) |
| heartbeat task | not running: 0 wake-ups | 1 wake / 25 s + 1 socket task wake / 25 s |
| presence sweep | not running | 1 / 10 s (+ the 1 s coalesce once per connect) |
| buffer maintenance | not running | ≤ 1 / 60 s while the buffer is non-empty |
| coalescer | no timer | one 25 ms sleep per burst |
| lifetime timers | — | one sleep per socket, fires once per ~30 min |
| **Total** | **≈ 0 B extra, 0 wake-ups/s** | **≈ 0.2 wake-ups/s, ≈ 20–100 KiB** |

Old stack: the realtime container used 93 MiB RSS idle (MEMORY.md P1.1) and polled Redis (`XREAD BLOCK 1000`, i.e. ≥ 1 wake/s per active shard set, plus a 250 ms idle loop).

## 5. Doubts, risks and decisions

### 5.1 Decisions needed

| ID | Decision | Proposal | Who |
|---|---|---|---|
| D1 | Crate order: `rt` below `core` (`db <- kv <- {jobs, rt} <- core <- {api, server}`) instead of `core <- rt` (P2.7 2.1) | yes: the business code publishes, so `core` must call `rt` | orchestrator |
| D2 | The 51 candidate not-applicable cases (4.3) | approve | **user** |
| D3 | Drop the realtime -> builder presence HTTP hop (`/api/workspace-presence/report`, presence-report token, `bodyHash`) and report in process | approve; keep the `presence-report` purpose in `rt::token` only so the 8 generic auth cases port 1:1 | **user** (with D2) |
| D4 | The 21 browser-client cases stay TypeScript as class B (4.4) | approve | **user** |
| D5 | No permessage-deflate (axum `WebSocketUpgrade` does not negotiate it) | accept for one person; revisit only if bandwidth matters | orchestrator |
| D6 | Keep `REALTIME_BROADCAST_SECRET` as a required env var (≥ 32 chars) | keep (parity, no client change); a generated secret stored in SQLite is possible later | orchestrator |

### 5.2 Risks

1. **Restart = resync for everyone.** The buffer is memory only. After a restart each open tab reconnects (backoff 0.5–30 s), gets 4002 `replay-cursor-ahead` and refetches its views. The old stack replayed from Redis across an app restart. P2.7 K44 accepted this; the revoke marker is durable, so no security gap.
2. **Slow-consumer threshold changes form.** uWS closed at 512 000 buffered bytes; Rust closes when a socket lags 256 records behind (broadcast `Lagged`) or the tungstenite write buffer passes 512 KiB. For normal frames both trigger later than before; a mobile client on a bad link may resync a little later. Tune the capacity in Phase 5 if needed.
3. **Bandwidth without compression.** Message lists with attachments can be large; uncompressed frames cost more bytes on mobile. One person: acceptable.
4. **Seq monotonic only with the clock.** Ids come from `max(now_ms, last.ms)`. A wall clock that jumps back across a restart can make new ids smaller than a client's `lastSeq`; the client then drops frames as duplicates until time passes the old id, or gets `replay-cursor-ahead` (which resyncs). Mitigation option: store the last seq in `DurableKv` at shutdown and seed from it.
5. **Hub lock contention.** All publishes and connects of all workspaces take one `std::sync::Mutex` for a few µs (append + `broadcast::send` + snapshot). For one person this is far below any limit. Never serialize JSON or do I/O under it (frames are built before the lock).
6. **Ordering across producers.** Before, ordering held per shard in Redis; now per process (seq under the lock). The coalescer still delays workspace events up to 25 ms while member/guest sends go at once, as before (a member-send can overtake a coalesced workspace event, same as the old stack).
7. **Revoke between check and register.** The marker is checked before and after the replay snapshot, and live revokes close registered sockets. A revoke whose marker write lands after the recheck but before registration is missed by both paths. The old stack had the same window. Option: register the `ConnHandle` inside the snapshot lock, then recheck (closes the window); recommended for the implementer.
8. **Public URL and path.** `publicRealtimeUrl` (tenant settings) must point at the Rust server (same origin; the reverse proxy path `/ws/` -> `/rt/...`). A wrong value breaks every client; the P1.27 parity test catches it.
9. **Guest limits under a flood.** Per-guest 5 and per-workspace 1 000 guest sockets stay; the guest token mint keeps its 100 / 10 s workspace limit (P2.7 K1). Each guest socket costs ≈ 10 KiB, so 1 000 guests ≈ 10 MiB — within the 200 MB budget, but worth a Phase 5 check.
10. **`contactBlocked` / `contactUnblocked`** have no producer in the current code (declared only). Keep the variants for client compatibility.
11. **Presence report on connect only.** A closing last tab sends no report (the lease expires in 20 s), as before; VoIP ring targets can include a user for up to 20 s after the tab closed. Same as the old stack.
12. **Test port of the live gateway cases** needs a WebSocket client dev-dependency (`tokio-tungstenite`, already in the tree through axum `ws`) and real sockets on `127.0.0.1`; keep them on the PC run like the other crates.
