## 2. BullMQ semantics callers rely on, and the Rust design that keeps each

### 2.1 Semantics (S1–S14)

| # | BullMQ behaviour (5.78.0) | Who relies on it | Rust keeps it by |
|---|---|---|---|
| S1 | **At-least-once**, never exactly-once. A job runs again after a stall (lock lost) or a retry. | Every handler is written idempotent (skill `reliability-concurrency` §3; status-guarded UPDATEs). | Same: lease + stalled recovery (2.5). No exactly-once claim is made. |
| S2 | **jobId dedup across every state** until the job hash is deleted. `add` with an existing id (waiting, delayed, prioritized, active, completed-retained, failed-retained) is a no-op that returns the existing job (`addStandardJob`: bare `EXISTS jobIdKey`). The jobId check runs **before** `deduplication`. | ~100 id patterns. Retained completed jobs extend the window (`comment-auto` keeps 24 h by age); `true/true` frees the id at once for re-driveable cron work; ids embed `attempts` so a retry of a retained failed run is not swallowed (`coexist-job-ids.ts:5-60`). | `UNIQUE(queue, job_id)` on `jobs`; `INSERT … ON CONFLICT(queue, job_id) DO NOTHING`; the row lives until retention deletes it (2.8). A job id containing `:` is rejected with `Custom Id cannot contain :` (frozen tests assert ids have no `:`); scheduler ids `repeat:<id>:<ms>` are internal and exempt. |
| S3 | **`deduplication` option** (`de:<id>` key): simple (no ttl): dedup until the job finishes (key removed on completion/failure only if it still points to that job); throttle (`ttl`): key with PX ttl, **not** removed on finish; debounce (`ttl + extend + replace` with `delay`): a new add while the old job is still **delayed** removes the old job and stores the new one (data and delay reset), ttl reset; while the old job is active/finished it is deduplicated; `keepLastIfActive`: a new add while the job is **active** stores the latest add as "next" (only the last one kept) and re-adds it when the active job finishes; the key is PERSISTed while active. | aiAgent automated response (debounce smart delay), flow actions, handoff re-entry, welcome-message flows (with keepLastIfActive), media restore (throttle 1 h), step-input (simple). | `job_dedup` table (2.3) implementing the four modes in the enqueue tx, with the exact Lua order (2.4). |
| S4 | **Delayed jobs**: `delay` ms → delayed ZSET; promoted when due by the worker's marker/blocking pop; precision a few ms when a worker is idle; a promoted job goes to the **tail** of wait (or into prioritized by priority). | VoIP expiry (30–60 s deadlines), smart-delay resumes, reminders, debounces, poll ordering 250 ms. | `state='delayed'` + `run_at_ms`; one timer task sleeps until `MIN(run_at_ms)` and promotes in one write tx; precision ≈ 1 ms + writer queue time. |
| S5 | **Priority**: no priority (0) jobs live in `wait` and are always taken **before** any prioritized job; prioritized are ordered by priority ascending (1 = highest), FIFO inside one priority (priority counter). `changePriority` moves a waiting job. | Broadcast/sequence 5, replay 10, low bulk 10, AI embeddings 5, CAPI 1, template 1/10, materialize 10, optimizeStoredImage 1000. Comments in code depend on "unprioritized first". | `priority INTEGER NOT NULL DEFAULT 0`; claim `ORDER BY priority, ready_seq` (0 sorts first, which is exactly BullMQ order). |
| S6 | **FIFO** within the same priority; no ordering guarantee across concurrent slots. A stalled job is pushed back to the **head** (RPUSH) and runs next. | Flow step ordering relies on waits (S11), not on queue order. | `ready_seq` = monotonic counter set on insert/promote/retry; stalled requeue sets `ready_seq` = min − 1 (head). |

All times are unix ms (`INTEGER`), JSON is `TEXT` + `json_valid` (P2.2). Tables are `STRICT`. These are infrastructure tables (no Drizzle origin), created by a `jobs` migration in the `db` crate migration runner.

### 2.3 Enqueue (`Enqueuer::add`, one short write tx)

Order mirrors `addStandardJob`/`addDelayedJob`/`addPrioritizedJob` Lua:
1. Validate: `job_id` must not contain `:` (error text `Custom Id cannot contain :`), `priority ≤ 2^21`, `delay ≥ 0`.
2. jobId check: `SELECT 1 FROM jobs WHERE queue=? AND job_id=?` → if present return `AddResult { job_id, created: false }` (S2). No other effect (priority is not changed — hence `promoteQueuedJob`).
3. `deduplication` (only when `dedup` is set), exactly the Lua of `includes/deduplicateJob.lua`, `deduplicateJobWithoutReplace.lua`, `storeDeduplicatedNextJob.lua`, `setDeduplicationKey.lua`:
   - an expired `job_dedup` row (`expires_at_ms <= now`) counts as absent (delete it);
   - `replace` and current owner is **delayed** → delete that job row, insert the new one, set the key (`extend` or no ttl → new ttl; else keep the old expiry; `keepLastIfActive` → no ttl);
   - current owner **active** and `keepLastIfActive` → upsert `job_dedup_next` (latest wins), set `expires_at_ms = NULL` (PERSIST), return the active job id;
   - `extend` + ttl and key present → reset ttl to now+ttl (or no ttl with keepLastIfActive), return the existing job id;
   - otherwise `INSERT OR IGNORE` semantics (`SET NX`, with ttl if given); present → return the existing job id.
4. Insert the row: `state = 'delayed'` if `delay > 0` (`run_at_ms = now + delay`), else `'waiting'`; `ready_seq = next()`.
5. After commit: `notify_waiting(queue)` (waiting insert) or `timer.reschedule(run_at_ms)` (delayed insert). Signals are sent only after the commit returns.

`add_bulk` = the same steps for N jobs in **one** tx (BullMQ `addBulk` is one MULTI). Producers inside a caller tx (`optimizeStoredImage` comment: "the enqueue can run inside a caller-owned transaction") get `Enqueuer::add_in(tx, …)` so the job commits with the business write (transactional outbox; strictly better than BullMQ; keep the 5000 ms delay for parity).

### 2.4 Claim (one short write tx per batch)

Each queue has one dispatcher task. When `free = concurrency − running > 0` and the limiter allows `k` starts:

```sql
UPDATE jobs
   SET state = 'active', lease_owner = ?1, lease_until_ms = ?2, processed_at_ms = ?3,
       attempts_started = attempts_started + 1
 WHERE id IN (SELECT id FROM jobs
               WHERE queue = ?4 AND state = 'waiting'
               ORDER BY priority, ready_seq
               LIMIT ?5)                    -- ?5 = min(free, k)
RETURNING id, name, job_id, data, priority, attempts, attempts_made, attempts_started,
          backoff_kind, backoff_ms, keep_complete, keep_fail, dedup_id, scheduler_id, created_at_ms;
```

`BEGIN IMMEDIATE` (writer thread), no I/O inside. `jobs_claim` serves both the filter and the order (index scan, no sort). A job whose `failed_reason = 'job stalled more than allowable limit'` marker is set (stall over limit, S9) is failed in the same tx instead of returned. Handlers run outside the tx. Completion/failure is a second short tx (2.6). Expected cost: one indexed UPDATE per claim batch; with `LIMIT free` a burst of 100 jobs on `trigger` is 1 tx, not 100.

### 2.5 Lease, heartbeat, stalled recovery

- `lease_owner` = a random 64-bit id made at process start; `lease_ms` = the worker's `lockDuration` (30 000 default, 600 000 integration and heavy).
- **Heartbeat**: one task per process; every `min(lease_ms)/2` **only while some job is active** it runs one batched `UPDATE jobs SET lease_until_ms = now + lease_ms(queue) WHERE lease_owner = ?me AND state = 'active'` (per lease class; 2 classes). Idle: no wake-ups. This is BullMQ `lockRenewTime` with one statement for all jobs.
- **Stalled recovery** (S9): at startup (before workers start) and every `stalledInterval` while any active row exists with a foreign or expired lease: `UPDATE jobs SET state='waiting', stalled_count = stalled_count+1, ready_seq = <head>, lease_owner = NULL … WHERE state='active' AND (lease_owner <> ?me OR lease_until_ms < now)`. Rows whose new `stalled_count > max_stalled` (1) and `scheduler_id IS NULL` get the failure marker (failed at next claim, as BullMQ `defa`). A `JobEvent::Stalled` is emitted (heavy metric listener).
- A second process on the same file is prevented by an exclusive lock file next to the database (`flock`), so a live process never sees its own jobs as foreign. The lease still protects correctness if that guard is bypassed.
- Hung handler: as in BullMQ, the heartbeat keeps the lease while the task is alive; there is no per-job timeout in the queue layer (handlers have their own, e.g. heavy provider timeouts).

### 2.6 Finish, retry, backoff (one short write tx)

- Success: `state='completed'`, `finished_at_ms`, `return_value`; dedup finalization (`removeDeduplicationKeyIfNeededOnFinalization`: delete `job_dedup` row only if `expires_at_ms IS NULL` and it points to this job; a ttl key stays); if a `job_dedup_next` row exists → insert that job now (`requeueDeduplicatedJob`) and set its key; retention (2.8); emit `JobEvent::Completed`.
- Failure (`Retryable`): `attempts_made += 1`; if `attempts_made < attempts` → `state='delayed'` with `run_at_ms = now + backoff(attempts_made)` or `'waiting'` (new `ready_seq`) when the delay is 0; else `state='failed'` + dedup finalization + retention. `failed_reason`, `stacktrace` (array, last N). Emit `JobEvent::Failed { final }` in both cases.
- `Unrecoverable` → final failure at once (still `attempts_made += 1`). `Delayed { run_at_ms }` → S7.
- Backoff (exact BullMQ, `classes/backoffs.js`, no jitter in use):

```rust
fn backoff_ms(kind: BackoffKind, delay: u64, attempts_made: u32) -> u64 {
    match kind {
        BackoffKind::Fixed => delay,
        // Math.round(Math.pow(2, attemptsMade - 1) * delay); attempts_made >= 1 here
        BackoffKind::Exponential => ((2f64.powi(attempts_made as i32 - 1)) * delay as f64).round() as u64,
    }
}
```

  Defaults: exp 5000 → retry after 5000; heavy processAIFile exp 30 000 → 30 000, 60 000; VoIP fixed 2000 × 9 retries; native call capture fixed 300 000 × 12 retries.
- `JobCtx::is_final_attempt()` = `attempts_made + 1 >= attempts`; `has_exhausted_attempts()` = `attempts_made >= attempts` (used from `on_failed`, after the increment).
- `on_failed` hook: called after the failure tx commits, never awaited by the dispatcher (BullMQ does not await listeners); its error is logged (`Failed-job handler threw`).

### 2.7 Cron (no new crate)

The 44 patterns are static and use only `*`, `N`, `*/N` per field (1.3), in 5-field and 6-field (seconds-first) form. A ~120-line std-only parser + "next fire after t" over UTC civil time (days-from-civil algorithm) covers them; a property test compares it to a table of expected next-fire values computed once from cron-parser on the TS side. If later work needs ranges, lists or time zones, switch to `croner` (pure Rust, supports optional seconds). Recommendation: std-only now (no chrono, smaller binary).
- `job_schedulers` row per scheduler; `register_schedules(edition)` = upsert (pattern/template changed → recompute `next_run_at_ms` from now, replace the pending job) and `remove_scheduler(id)` for the gated ones (S13), all in one tx at boot.
- The **timer task** (one per process) sleeps until `min(next delayed run_at_ms, next scheduler fire)`. On fire, in one tx: for each due scheduler insert job `repeat:<id>:<slot_ms>` (dedup by `UNIQUE`) with the template, set `next_run_at_ms` = next slot after **now** (one catch-up run after downtime, no backfill); promote due delayed jobs; then notify the affected queues.
- `every`: first slot = upsert time, then prev + every, re-aligned as in `getJobSchedulerEveryNextMillis.lua`.
- `LICENSE_REFRESH_MINUTE = randomInt(60)` per boot: keep (inject the random source in tests).
- Zone: UTC (see 6.3).

### 2.8 Retention and cleanup

- `Remove` (`true`): delete the row in the finish tx (frees the job id at once).
- `KeepCount(n)` / `KeepAge{age_secs, count}` (queue-wide, using the finishing job's own option, else the worker default): in the finish tx, at most once per 50 finishes per (queue, state) or when 1 s passed, run `DELETE FROM jobs WHERE id IN (SELECT id FROM jobs WHERE queue=? AND state=? ORDER BY finished_at_ms DESC LIMIT -1 OFFSET n) LIMIT 500` and the age delete. Amortized trimming can keep a few more rows than BullMQ for a moment; that only lengthens dedup windows (safe direction).
- `Keep` (no option anywhere, e.g. a queue with no worker such as `quota`): rows stay.
- A low-rate sweep (every 3600 s, one wake-up) applies age limits on queues with no recent finishes.
- `job_dedup` rows with `expires_at_ms < now` are deleted lazily on access and by the hourly sweep.

### 2.9 Waiting for a job (QueueEvents replacement)

- One `tokio::sync::broadcast::Sender<JobEvent>` per process (capacity 1024), events sent after commit: `Completed { queue, job_id, return_value }`, `Failed { queue, job_id, reason, final }`, `Stalled`, `Delayed`. No Redis stream, no idle cost.
- `wait_until_finished(queue, job_id, timeout)`: subscribe **first**, then read the row; if already `completed`/`failed` return at once; else wait for the first matching event (a `Failed` rejects, like BullMQ); timeout → `WaitError::Timeout`. A lagged receiver re-reads the row (no lost result).
- `wait_for_completion_with_retries`, `wait_for_integration_job_completion` (10 000 ms, never errors), `wait_for_job_result` (strict) are ported 1:1 on top (frozen `job-wait*.test.ts`). `JobCompletionStateUnknownError` maps to the case where the row read fails or the row is gone.
- `Enqueuer::add` returns `AddResult { job_id, created }`; waiting uses `(queue, job_id)`, so a job removed by `Remove` right after completion is still observed through the event (the subscribe-first order closes the race BullMQ has).

### 2.10 Concurrency and rate limit

- Per queue: `tokio::sync::Semaphore(concurrency)`; the dispatcher claims `min(available_permits, limiter_quota)` rows; each claimed job runs in its own task holding a permit.
- Limiter (callTranscription `10 / 60 000`, profileSnapshot `10 / 1000`): fixed window like BullMQ `rateLimiterKey` (counter + PEXPIRE on first start); when exhausted the dispatcher sleeps until window end (one timer, only while jobs wait).
- Separate pools per queue keep the original isolation (integration waits on chat; different semaphores, no deadlock).
- Total default slots in `standalone`: integration 10, chat 5, aiAgent 5, heavy 1, schedule 5, trigger 100, webhook 50, default 5, template 2, sequenceScheduler 100, notification 10, callTranscription 1, voip 10, low 30, profileSnapshot 1, leaderboard 10, marketingMessage 10 = **355**. Keep the env names and bounds (they are config contract), but most slots wait on the single SQLite writer; see 6.4.

### 2.11 Inspection API (S14)

`JobStore` on a reader connection: `get_job(queue, job_id) -> Option<JobRecord>` (fields `priority`, `attempts_made`, `opts.attempts`, `state`), `get_state` returning BullMQ strings (`waiting` with `priority > 0` → `"prioritized"`; missing → `"unknown"`), `get_job_counts(queue, &[states])`, `prioritized_count`, `delayed_count`; on the writer: `remove(queue, job_id)` (BullMQ refuses to remove an active/locked job: keep that, return `false`), `change_priority(queue, job_id, p)` (waiting only, new `ready_seq` inside the priority as BullMQ `changePriority` re-adds with a new counter).

### 2.12 Wake-up signal (no hot polling)

- Per queue `Arc<tokio::sync::Notify>`: `notify_one` after an insert/promote/retry commit for that queue, and after a slot frees while rows may be waiting. The dispatcher loop: `loop { claim batch; if none { notified.await } }` — it never sleeps on a timer when idle.
- Lost-wakeup safety: the dispatcher creates the `notified()` future **before** the claim query (`Notify` permit semantics), so a notify between "claim found nothing" and "await" is not lost.
- One timer task for all delayed jobs and schedulers (2.7) with `sleep_until(next)`; `reschedule(t)` via a `watch` channel when an earlier `run_at_ms` is inserted.
- Startup: one claim pass per queue (rows left from the previous run).

### 2.13 Graceful shutdown

Port `apps/worker/src/lib/shutdown.ts` 1:1 as `Shutdown` (frozen `worker-shutdown.test.ts`, 16 cases):
- `watch`-based cancel token; SIGINT/SIGTERM via `tokio::signal`; a panic hook / failed task maps to the fatal path (exit code 1, 30 000 ms deadline when unset).
- On request: dispatchers stop claiming; running jobs finish (`worker.close()` waits for active jobs); closers run concurrently with `allSettled` semantics; then finalizers (realtime flush, completion registry close) run; optional deadline `WORKER_SHUTDOWN_TIMEOUT_MS` (Docker modes default 8000) → log `Shutdown timed out with workers still draining` with the pending names and exit 1. Jobs cut off stay `active` with this process's lease and are recovered at the next start (S9), the same outcome as BullMQ.
- `run_worker(name, start)`: bootstrap once, skip start when shutdown began, start error → drain + exit 1; `spawn_worker` after shutdown began → error `Cannot start <queue> worker: shutdown already requested`.

## 3. Scheduler and sequence-scheduler

### 3.1 What they do now

- `packages/scheduler` (`SchedulerClient`, 132 lines): Redis ZSETs per bucket `seq:dispatch:{b}:schedule` and `seq:dispatch:{b}:retry` (score = run/retry ms, member = dispatch id) + Redlock `withLock(bucket, dispatchId, ttl)` on `seq:dispatch:{b}:lock:<id>`. Ops: add/remove schedule/retry, `removeFromAll`, `getDue(key, now, limit)` (`ZRANGEBYSCORE -inf now LIMIT 0 limit`), counts, `batchAddToSchedule` (pipeline, `AggregateError` if any command fails), `getZSetMembers`. Connection: `REDIS_SEQUENCE_URL ?? REDIS_URL`.
- `packages/sequence-scheduler` (business logic over the `SequenceDispatch`/`ContactOnSequence`/`SequenceStep` tables): `calculateBucket(workspaceId, contactId)` (base-31 hash mod 2 147 483 647, then % 256; persisted on the row), `createDispatch` (idempotency key `ws:enrollment:step:ISO`), `enrollContact`, `advanceEnrollment` (computes the next step's `runAt` and calls `scheduler.addToSchedule`), `cancelPendingDispatches` (DB cancel + `removeFromSchedule`, optional after-commit), `calculateNextRunAt(FromStep)`, `sendTimeValidator`, `contactsOnSequences` helpers, `sequenceDispatchUtils`.
- `apps/worker/src/sequence-scheduler`:
  - **producer** (`worker-producer.ts`): one `setTimeout` loop per assigned bucket (default 256), every `SCHEDULER_TICK_INTERVAL_MS` (5000, clamped 100–10 000): `getDue` on schedule and retry (limit 100 each) → claim each id with `withLock(…, 30 s, ZREM)` → `listPendingWorkspaceIds` → `addBulk` to `sequenceScheduler` with jobId `sequence-<dispatchId>`; publish failure re-inserts (schedule at now, retry at now).
  - **consumer** (`worker-consumer.ts`, concurrency 100): blocked-workspace guard → `withLock(bucket, id, 30)` → fetch pending dispatch (missing → remove from schedule) → validate → not ready → re-add with its `runAtMs` → `lockDispatch` (DB claim pending→running, `lockOwner = HOSTNAME`) → enqueue `integration` `sendSequenceFlow` (jobId `seq-<id>-<attempt>`, `3 × exp 5000`, priority 5, `removeOnComplete: true`); enqueue failure → `revertDispatchToPending`. Lock contention → skip silently; other errors → BullMQ retry.
  - **reconcile** (`worker.ts`): at start and every `BOOTSTRAP_INTERVAL_MS` (3 600 000): re-add every pending dispatch due within 24 h to its ZSET (batches of 1000); every `CLEANUP_INTERVAL_MS` (21 600 000): remove ZSET members that are not pending rows; every `SEQUENCE_DISPATCH_RETENTION_INTERVAL_MS` (86 400 000): delete terminal dispatches older than `…_TTL_DAYS` (30) in batches (1000).
- **Sharding**: `SCHEDULER_BUCKET_RANGE` (`buckets.ts`): `"a-b"` range or `"a,b,c"` list, default 0..255 (vitest sets `"0-255"`). It lets several producer replicas split the 256 buckets; the Redlock claim prevents double publish when ranges overlap. The **retry** ZSET is only ever filled by the producer's own re-insert path (no other `addToRetry` caller exists).

### 3.2 Single-process replacement

- Keep the bucket **column** and `calculate_bucket` (tests pin the hash), keep `SCHEDULER_BUCKET_RANGE` parsing (tests), default all buckets; document that it has no use with one process.
- Replace the ZSETs with one table that has the same set semantics (keeps every `SchedulerClient` op and the reconcile/orphan logic 1:1, so the frozen tests port without semantic change):

```sql
CREATE TABLE sequence_schedule (
  kind        TEXT    NOT NULL CHECK (kind IN ('schedule','retry')),
  dispatch_id INTEGER NOT NULL,
  bucket      INTEGER NOT NULL CHECK (bucket BETWEEN 0 AND 255),
  at_ms       INTEGER NOT NULL,
  PRIMARY KEY (kind, dispatch_id)        -- ZADD = upsert score
) STRICT, WITHOUT ROWID;
CREATE INDEX sequence_schedule_due ON sequence_schedule (kind, at_ms);
```

  `trait DispatchSchedule` (SQLite impl + recording fake) with the same method names. `batch_add_to_schedule` is one tx (all-or-nothing; the Redis pipeline was partly applied → note in 6.8). `get_due(kind, now, limit)` = `SELECT dispatch_id FROM sequence_schedule WHERE kind=? AND at_ms<=? ORDER BY at_ms LIMIT ?` (plus `AND bucket IN (…)` only when a range is set).
- **Claim without Redlock**: the producer tick is one write tx: `DELETE FROM sequence_schedule WHERE (kind, dispatch_id) IN (SELECT kind, dispatch_id … due … LIMIT 100) RETURNING dispatch_id, bucket, kind`, then (same tx) join pending `SequenceDispatch` rows for `workspace_id` and insert the `sequenceScheduler` jobs (`sequence-<id>`, `Remove` retention) through `Enqueuer::add_in(tx)`. The ZREM-then-publish loss window ("lost until the hourly reconcile") disappears; the re-insert path stays for parity (it runs only if the tx fails).
- **Consumer lock**: `withLock(bucket, id, 30)` → the P2.7 in-process keyed lock (`LockMap::try_lock`, fails fast with the same `LockAcquisitionError` kind), because the DB claim `pending→running` already guards double sends across restarts.
- **Wake-up**: no 256 timers. The producer task waits on `min(at_ms)` of `sequence_schedule` (one indexed `SELECT MIN`), `Notify` on every `add_to_schedule`, and caps the sleep at `SCHEDULER_TICK_INTERVAL_MS` only as a safety net (keeps the env contract and `resolveTickIntervalMs` tests). Latency drops from ≤ 5 s + tick to ≈ ms (6.8).
- Reconcile, orphan cleanup and retention keep their intervals as `tokio::time::interval` tasks (3 timers, ≤ 1 wake-up/h).
- `lockOwner = HOSTNAME` stays (the DB column contract); value = hostname or `unknown`.
- Placement: `crates/jobs/src/sequence/` for the scheduler, producer, consumer, reconcile; the business functions of `packages/sequence-scheduler` live in the same module now (they are part of this package), and can move to a Phase 3 crate later without test changes. They need the P2.4 sequence tables.

## 4. Event bus

### 4.1 What it is now

`packages/event-bus`: `BaseEventBus` over **Redis Streams** with consumer groups, 4 configured buses (`src/{message,flow,dashboard,error-log}/event-bus.ts`), all on the `hot` connection:

| Bus | Stream / group | maxLen (`XADD MAXLEN ~`) | Selective retry | DLQ |
|---|---|---|---|---|
| message | `events:message` / `message-events-group` | 100 000 | no (ack whole batch even on handler failure) | `events:message:dead` (default name), maxDeliveries 5 |
| flow | `flow:events` / `flow-events-group` | 100 000 | no | default |
| dashboard | `events:analytics-dashboard` / `analytics-dashboard-events-group` (consumer uses `cloneForGroup` with the **same** group name) | 500 000 | yes | `events:analytics-dashboard:dead`, maxLen 100 000, maxDeliveries 5 |
| error-log | `events:error-log` / `error-log-events-group` | 50 000 | yes (writes idempotent on producer-minted row id) | `events:error-log:dead`, maxLen 10 000, maxDeliveries 5 |

- `emit(type, payload)` (index.ts) routes by event type to its bus; zod schema check (invalid → `""`, no write); optional payload transformer; `XADD * type payload timestamp`. ~40 non-test files import `@chatbotx.io/event-bus` (producers and listeners).
- Consumer (`apps/worker/src/events/worker.ts`, in `core` and `standalone`): per bus a loop: every `claimIntervalMs` (30 000) `XAUTOCLAIM` entries idle > `claimIdleMs` (180 000) → delivery count > `maxDeliveries` → dead-letter (with the last remembered error or `max deliveries exceeded`) + ack, else reprocess; `XREADGROUP BLOCK 5000 COUNT readBatchSize(500)`; group the batch by type; run all listeners of that type in parallel on the whole batch with an `AbortSignal` and a `processTimeoutMs` (120 000) watchdog (timeout → leave unacked for reclaim); listener may return `{failedMessageIds}`; ack all (or only successes with selective retry); payloads carry `EVENT_BUS_MESSAGE_ID` = stream id. `stopWorker`: stop loops, drain ≤ 6000 ms, `DELCONSUMER` only when nothing is pending. Entries are not `XDEL`ed (multi-group design), only trimmed by `MAXLEN`.
- Semantics callers rely on: **durable, at-least-once, batched** delivery decoupled from the request (MAC tracking, analytics counters, ads conversion, provider error logs). Producers (builder, worker) do not wait for consumers.

### 4.2 Replacement

Use the SQLite store, not an in-memory `broadcast`: an in-memory channel would lose events on crash/restart and at shutdown, and analytics/MAC counters would drift (they are billing-relevant). One process means no fan-out between processes, and every stream has exactly one group, so the stream reduces to a durable per-stream queue with batch claim:

```sql
CREATE TABLE event_entry (
  id              INTEGER PRIMARY KEY,            -- monotonic; EVENT_BUS_MESSAGE_ID = "<id>-0" (keeps the "ms-seq" shape)
  stream          TEXT    NOT NULL,               -- 'events:message', 'flow:events', …
  type            TEXT    NOT NULL,
  payload         TEXT    NOT NULL CHECK (json_valid(payload)),
  ts_ms           INTEGER NOT NULL,
  delivered_at_ms INTEGER,                         -- NULL = new; set at read/claim (PEL idle time)
  delivery_count  INTEGER NOT NULL DEFAULT 0,
  consumer        TEXT,
  last_error      TEXT                              -- persisted, so a restart keeps it (improves on the in-memory map)
) STRICT;
CREATE INDEX event_entry_new     ON event_entry (stream, id)              WHERE delivered_at_ms IS NULL;
CREATE INDEX event_entry_pending ON event_entry (stream, delivered_at_ms) WHERE delivered_at_ms IS NOT NULL;
CREATE TABLE event_dead_letter (id INTEGER PRIMARY KEY, stream TEXT NOT NULL, type TEXT NOT NULL, payload TEXT NOT NULL,
  original_id TEXT NOT NULL, delivery_count INTEGER NOT NULL, error TEXT NOT NULL, ts_ms INTEGER NOT NULL) STRICT;
```

- `emit`: schema check + transformer as now, then one insert. Hot path: message events are emitted on every message, so `emit` goes through the writer's **group commit** (many small inserts per tx) and never waits for the commit when the caller did not ask for the id (`emit` returns the id future; most callers ignore it) — see 6.4.
- Read = one write tx `UPDATE … SET delivered_at_ms=now, delivery_count=delivery_count+1, consumer=? WHERE id IN (SELECT id … new … ORDER BY id LIMIT read_batch_size) RETURNING …`; ack = `DELETE` (acked entries are not kept: no second group needs them, and `MAXLEN` retention of acked entries has no reader); reclaim = same update over `pending` rows idle > `claim_idle_ms`, at most once per `claim_interval_ms`; dead-letter = move row in one tx; `maxLen` = cap on **unacked** rows (oldest dropped with a warning) to bound disk if the consumer is down, matching the `MAXLEN ~` intent.
- Consumer loop waits on a per-stream `Notify` (emit commit → `notify_one`) instead of `BLOCK 5000`; no timer when idle except the reclaim check, which runs only when pending rows exist.
- `processTimeoutMs`, `AbortSignal` → `CancellationToken`-like `watch` per batch, selective retry, `failedMessageIds`, dead-letter boundary (`count > maxDeliveries`), `stop` → drain ≤ 6000 ms → deregister: all ported (frozen `event-bus.test.ts`, 20 cases; 7 TS-only with proposals).
- Alternative considered (not recommended): `tokio::sync::broadcast` per bus — zero writes, but loses events on crash/shutdown and cannot express reclaim/dead-letter tests.

### 5.2 scheduler + sequence-scheduler (107 cases)

Shared test support for these files (one `tests/support/sequence.rs` module):
- `TestDb`: an in-memory SQLite from the `db` crate test helper, with the real `SequenceDispatch`, `ContactsOnSequence`, `SequenceStep`, `Inbox`, `ContactInbox` tables (P2.4 schema). Ids are fixed strings, as in the TS tests.
- `RecordingSchedule`: a fake `DispatchSchedule` that records each call `(op, bucket, dispatch_id, at_ms)` and can fail the n-th call. It replaces the vitest `SchedulerClient` mock.
- `TxProbe`: a wrapper on the write connection that counts `BEGIN IMMEDIATE` / `COMMIT` and pushes `"tx-done"` into a shared order log. It replaces `transactionMock` and the `order` array.
- `TestClock` for "now". Dates with a local-time meaning (send-time-validator) use a fixed `chrono_tz` zone passed in, not the process TZ.
- Where the TS test only checks the shape of a Drizzle call (columns in `WHERE`), the Rust test asserts the effect on real rows (for example, a row of another workspace or another status stays unchanged).

## 6. Doubts and risks

Numbered so the orchestrator can answer by number. "Ask" = needs a user decision.

1. **SQLite single writer vs. queue write load (top risk).** Each job costs ≥ 3 write tx (add, claim, finish) and every message emits 1–3 event-bus inserts. A broadcast to 10 000 contacts with 3 steps is ≈ 10 000 × 3 × (integration + chat) jobs ≈ 180 000 tx plus business writes. SQLite WAL with `synchronous=NORMAL` does several thousand small tx/s, so it fits, but only if the writer thread does **group commit** (many queued closures in one `BEGIN IMMEDIATE … COMMIT`) and claims in batches (`LIMIT free`). P2.3 must confirm the writer API allows batching; if not, the jobs crate adds its own write batching on top of `Db::write`. Measure in Phase 5.
2. **Long write transactions block every queue.** Template install/sync (`template` queue comment: "each is one long transaction"), purges, and partition maintenance hold the single writer. The jobs layer keeps its own tx short, but a long handler tx delays every claim and every enqueue (BullMQ had no such coupling; Postgres had MVCC writers). Phase 3 handlers must chunk (P2.2 rule). Hot/bulk Redis groups (`queueGroupByName`) no longer isolate anything; consider a writer priority lane (hot tx first) if Phase 5 shows latency.
3. **Cron time zone.** BullMQ passes no `tz`, so daily crons (`0 3 * * *` …) run in the process local zone. The Docker image is UTC by default, but a self-hoster who sets `TZ` gets local-time crons today. The Rust design uses UTC always. Ask: accept UTC-only (recommended, simpler, no tz data) or honor `TZ`?
4. **Retention semantics are queue-wide (possible original bug).** BullMQ trims by the finishing job's `count` across the whole completed set, so a job kept by `age` (`comment-auto-<id>` 24 h, leaderboard awards 24 h) can still be evicted by other jobs' `count: 1000` trims — the comment in `received-message.ts:2149` assumes otherwise. The design copies BullMQ exactly (parity). Option: per-job retention (each row deleted only by its own rule) is safer for dedup and costs the same. Ask, or keep parity and log the difference.
5. **Dedup window depends on volume.** Ids kept by `{count: N}` dedup only while fewer than N newer jobs finished. With amortized trimming the Rust window is slightly longer, never shorter. Tests do not pin trim timing.
6. **`quota` has no consumer in this repo.** With a durable `jobs` table, community installs accumulate `quota` rows forever (BullMQ had the same, in Redis). Proposal: keep the producer (parity), give the queue `Retention::KeepCount(1000)` on enqueue, or skip enqueue when `edition == community`. Ask (product contract with the private quota-worker; also: how will the enterprise worker read jobs now that there is no Redis?).
7. **Bull Board admin UI** (`/developer/queues`, super admin) has no Rust equivalent. Options: drop it (Phase 4 decides), or a small read-only JSON/HTML page over `jobs` (counts per state, failed rows with reason, retry/remove buttons). Ask.
8. **Behaviour changes that are improvements but visible:**
   - sequence sends fire ≈ at `runAt` instead of up to `SCHEDULER_TICK_INTERVAL_MS` (5 s) late; consecutive zero-delay steps no longer add 5 s each;
   - `batch_add_to_schedule` is all-or-nothing (Redis pipeline was partly applied; frozen `smoke.test.ts:10` asserts the `AggregateError` and both `zadd` calls — port asserts the error and that **no** row was written, marked in section 5);
   - the ZREM→publish loss window and the "lost until hourly reconcile" log path go away (code kept for parity);
   - enqueue can join the caller's transaction (outbox); BullMQ could not. Producers that today enqueue after commit keep that order unless Phase 3 opts in.
9. **Delayed-job precision for VoIP deadlines.** 30–60 s Meta answer windows use `delay`. The timer is ms-precise, but a busy writer queue (risk 1) adds latency to promotion and claim. Give the timer's promote+claim tx priority in the writer, or keep VoIP on its own small path. Low risk at expected volumes.
10. **Waiting for jobs inside job slots.** `integration` (10 slots) waits up to 120 s for `chat` (5 slots) and up to the heavy budget (≈ 9 min) for `heavy` (1 slot). Same as today; separate semaphores avoid deadlock, but under bursts integration slots idle-wait. Not a new risk; do not merge pools.
11. **`attemptsStarted` / deferral budget** depends on `attempts_started` counting every activation including after `Delayed`. The claim SQL increments it; stalled recovery must **not** reset it (BullMQ does not). Covered by `lock-contention-deferral` tests.
12. **Stall after shutdown deadline.** Jobs cut off at the 8 s Docker deadline are recovered on the next boot (stalled_count 1). A second cut-off of the same job fails it (`job stalled more than allowable limit`). Same as BullMQ; mention in ops docs. Restart loops with long jobs (heavy 9 min) can fail jobs this way.
13. **Single-process lock file.** The design assumes one binary per data file (P2.1). If two binaries ever share a file (blue/green deploy), leases still prevent double claims, but crons would fire twice (two timer tasks). The `flock` guard makes the second process refuse to start; document it.
14. **Job ids with `:`.** BullMQ rejects them; the Rust store would accept any string. Keep the BullMQ check (frozen tests assert ids contain no `:`; `send-flow-` ids replace `:`), exempting internal `repeat:` ids.
15. **Event-bus durability vs. write cost.** The recommended durable `event_entry` table doubles as a write hot spot (risk 1). If Phase 5 shows the writer saturated, fall back for the `flow` and `message` buses to in-memory batching with periodic flush (bounded loss window), keeping dashboard/error-log durable. Ask only if measured.
16. **Sequence business code placement.** `packages/sequence-scheduler` is mostly domain logic on P2.4 tables (enroll/advance/cancel/validate). This spec puts it in `crates/jobs::sequence` because this unit owns the package; its 105 cases need the P2.4 schema and the `db` crate test helper. If P2.4 is not merged when P2.6 starts, port those tests failing and mark them blocked by P2.4.
17. **Scope of section 5.** Included: the 33 frozen files of the four packages + 17 queue-mechanics files of `apps/worker/__tests__`. Left to Phase 3 (handler logic that only *uses* queue options): e.g. `enqueue-broadcast`, `enqueue-recurring-broadcasts`, `enqueue-attachment-downloads`, `purge-draft-broadcast-recipients`, `default-worker`, `heavy-worker`, `integration-worker-boot`, `low-worker-boot`, `marketing-message-worker-boot`, `*-audit-context`, `schedule-worker-*-dispatch/purge`, `settle-and-log`, `packages/automated-response/__tests__/enqueue-*.test.ts`, `packages/business/__tests__/google-ads-send-queue.test.ts`. Those tests assert `JobOptions` values through `FakeEnqueuer`; the P2.6 API must support them (it does: every option above is modelled). Re-check when Phase 3 ports them.
18. **`deduplication` corner cases** (debounce `replace` when the old job already became active; `keepLastIfActive` + ttl expiry) are subtle. The design copies the Lua order; add Rust tests derived from BullMQ's own test suite for these four modes, since only a few frozen cases (`resolve-step-input-job`, Phase 3 `enqueue-message`) cover them.
19. **No exactly-once.** Handlers must stay idempotent (status-guarded UPDATEs). The SQLite store makes an "exactly-once for DB-only handlers" option possible (run handler writes and the job finish in one tx), but that changes semantics; not proposed.
