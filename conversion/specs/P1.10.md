## 1. Common contract (all 52 operations)

### 1.1 Auth (`workspaceTokenAuthAPIForScope(scope)`, `apps/builder/src/orpc.ts`)

All checks run before input validation (test `00-auth`):

1. No bearer and no `?token=` -> **401** `{defined:true, code:"INVALID_CHATBOT_TOKEN", status:401, message:"Invalid or missing workspace API token"}`. An unknown `cbx_ws_` token -> the same 401.
2. Read-only token on any POST/PUT/PATCH/DELETE -> **403** `{defined:true, code:"FORBIDDEN", message:"Read-only token cannot perform this operation"}`. No route of this unit is on `READ_ONLY_TOKEN_ALLOWED_POST_PATHS`. This check runs before the scope check. Read-only tokens pass auth on every GET.
3. Scope: `scopes === null` = all scopes, else the route scope must be listed, else **403** `{defined:true, code:"FORBIDDEN", message:"Token is not authorized for the '<scope>' scope"}`.

| Namespace | Scope |
|---|---|
| inboxes | `inbox` |
| instagramChannels | `channels` |
| integrations | `integrations` |
| keywords | `automation` |
| leaderboards | `leaderboards` |

### 1.2 Errors

- Input validation (zod, oRPC) -> **422** `{defined:true, code:"invalidRequestData", data:{issues:[{path,message}]}}`.
- `validationException(field, message)` -> **422** `{defined:true, code:"validation", message}`.
- `notFoundException(message)` -> **404** `code:"notFound"`; `defined:true` only when the route declares `notFound` (finding/mutating/deleting error sets). `keywords.create` does not declare it, so its 404s are `defined:false`.
- `ModelNotfoundException` (drizzle `findOrFail`) -> 404 `notFound`, message `Record not found`.
- A channel SDK error (`SdkException`, e.g. Instagram Graph) -> `code:"BAD_REQUEST"`, status = the SDK status, `defined:false`.
- Id path params are `zodBigintAsString` (non-numeric -> 422 `id`) except `integrations.get` (`z.string()`), `leaderboards.getExport` (`fileId`, `z.string()`) and the query params `leaderboards.telegramChats.inboxId` / `getViewLink.contactId` (`z.string()`).
- Times are ISO-8601 strings with milliseconds (`Date` output).

## 5. keywords (6) (`features/automated-response/api/public.ts`, `packages/business/src/automated-response/service.ts`, `packages/automated-response`)

Resource: `{id, keywords, conditions, status, text, flowId, type, createdAt, updatedAt}`.
Every route takes `type` = inbound (default) | outbound and only sees rows of that type.

- `create` POST `/v1/keywords` (201): `keywords?` (1+ strings 1..255) or `conditions?` (1..10 of `{operator, values[]}`, values trimmed 1..255, max 50; valueless operators containsPhone/Email/Image/Video/Link/isThumbsUp need `[]`; `matchesRegex` must compile as RE2, ≤200 chars), never both (422 path `conditions`), one required (422 path `keywords`); `text?` min 1; `flowId?`; `folderId?`. Inbound: keywords are trimmed and stored as one `contains` condition; `keywords` column = deduplicated trigger words (is, similarTo, contains, containsWholeWord, beginsWith, endsWith). Outbound: trimmed exact keywords, `conditions: null`; conditions -> 422 validation `Conditions are only supported for contact (inbound) keywords`. All blank keywords -> 422 validation `At least one keyword is required`. Unknown flow -> **404 `Flow not found`, `defined:false`** (template-lock parent check); text + flow -> 422 validation `A keyword replies with either text or a flow, not both`; unknown folder -> 404 `Folder not found` (`defined:false`). `status` starts true.
- `get` GET `/v1/keywords/{id}` -> 404 `Automated response not found` (unknown, foreign, other type).
- `list` GET `/v1/keywords` -> `{data, pageCount}` newest first, `page` default 1, `perPage` 1..50 default 50, `pageCount = ceil(total/perPage)` (0 when empty).
- `update` PATCH `/v1/keywords/{id}`: at least one of keywords, conditions, text, flowId, folderId (else 422 invalidRequestData with an issue at the root path); a text clears the flow, a flow clears the text, **both sent -> text wins, flow cleared**; keywords replace the conditions (inbound); unknown flow -> 422 validation `Flow not found`; unknown id -> 404.
- `updateStatus` PATCH `/v1/keywords/{id}/status` `{status}` -> the rule; 404 first.
- `delete` DELETE `/v1/keywords/{id}` (204), also for unknown, foreign or other-type ids (nothing deleted). `type` is read from the body only.
- Firing (test 41): an inbound contact message (API channel) is queued, then after `AUTOMATED_RESPONSE_DELAY_SECONDS` (2 s) the worker checks the enabled inbound rules of the workspace oldest first (cached, invalidated on every write); the first matching rule of the first matching message of the batch replies: text -> outgoing message (`sendChatMessage`, spintax + contact variables), flow -> `sendFlow` of a published flow. All conditions AND, values OR; matching lowercases and folds Vietnamese accents; `is` = whole message; `containsWholeWord` = word sequence; `notContains` blocks. Disabled and outbound rules never fire on a contact message. The effect is the API channel's signed `message_created` callback and the realtime `messageCreated` event.

## 8. Not covered black-box (with reason)

- Leaderboard automatic scoring (comments, keywords, story, follow, message, join/discussion, email, minigame, referral rules; `maxPerDay`, `cooldownSeconds`, `followersOnly`, `tagIds`, time window, golden hour): each needs a real channel webhook event (Messenger/Instagram/TikTok/Zalo/Telegram/email/minigame); later webhook units. The leaderboard "keywords" rule scores only on messenger/instagram/tiktok contact inboxes, not on the API channel.
- Auto rewards on finish (`autoOnFinish`): queued with a 10-minute grace delay; too slow for a parity run.
- Outbound keyword rules: fire only on an agent (user) message; a workspace token has no user, so the public API cannot send one.
- Keyword `similarTo`, `containsEmail/Link/Image/Video`, `isThumbsUp`, `matchesRegex` matching at run time (validation is covered); same matcher, low value per test cost.
- The keyword-received contact activity and ads-conversion evaluation side effects (other units' read routes).
- `setCoexist` `coexistInvalidAuth` / `coexistSyncNotStarted` (WhatsApp only); the Facebook-Login coexist pull; coexist teardown on disconnect (needs a live run at the right moment).
- CAPI with a dedicated CAPI token (only set by the builder OAuth/custom connect, no public path) and the WhatsApp token fallback.
- `integrations.get` with a non-numeric id and `leaderboards.telegramChats` / `getViewLink` with a non-numeric id: the string reaches a bigint column (likely 500); not asserted (same policy as P1.3).
- `inboxes.list` row order (no ORDER BY): compared unordered.
- Graph 5xx retries of the Instagram client (3 retries with back-off) in settings/disconnect.

## 9. Original behavior the Rust port must match (surprises)

1. `inboxes.list`/`listChannels` without `perPage` return up to 20 rows but compute `pageCount` with 10 per page; `perPage` > 50 returns 50 rows but `pageCount` uses the asked size.
2. `integrations.list` reports `pageCount: 1` for an empty list (in-memory paging); `integrations.get` returns a `metaCatalog` row that `list` hides.
3. `instagramChannels.updateSettings` (PUT) on an unknown account id answers **400 `systemError` `Failed to update Instagram integration`**, not 404 (lookup inside the catch-all); PATCH answers 404 `Record not found`. Any Meta error is also 400 `systemError` and rolls the save back.
4. `patchSettings` always re-pushes the merged settings to Meta (also for an empty body or a `markReadOnOutbound`-only change).
5. Instagram-Login disconnect unsubscribes `<metadata.pageId>/subscribed_apps` on graph.instagram.com; the Facebook-Login Messenger-sibling check is not workspace-scoped.
6. CAPI routes treat Instagram-Login accounts as 404 `Channel not found`; `setCapiDataset` without `datasetId` always asks Meta even when a dataset is stored.
7. `keywords.create` with an unknown flow is 404 `notFound` (`defined:false`), `keywords.update` with an unknown flow is 422 `validation`; `update` with both text and flowId keeps the text and clears the flow (create refuses both).
8. `keywords.delete` is 204 for unknown, foreign and other-type ids; inbound `keywords` are deduplicated while the condition values keep duplicates.
9. Leaderboard manual adjust works while the leaderboard is active before `startsAt` (no window check); a negative first adjust creates a 0-score participant; scores clamp at 0.
10. `participants.reset` logs a `reset` history event but leaves the breakdown; `resetPoints` clears the breakdown.
11. `triggerRewards` answers 200 with no winners for an empty finished board the first time and 409 `leaderboardRewardsAlreadySent` after.
12. The read-only check runs before the scope check (a read-only token without the scope gets the read-only message).
13. oRPC input coercion: the strings `"on"` / `"off"` pass as `true` / `false` for boolean inputs (`updateAiProvider.autoReply`, `keywords.updateStatus.status`); other strings (`"yes"`, `"no"`) and numbers are 422.
14. `keywords.delete` reads `type` from the JSON body; a `?type=` query parameter is ignored (the default `inbound` applies, so an outbound rule is not deleted). GET routes do read `type` from the query.
15. The leaderboard CSV export applies the formula guard to every cell, so a phone number `+84…` is written as `'+84…` and a name `=X` as `'=X`.
