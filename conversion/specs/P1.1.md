# P1.1 — Parity harness scaffold (spec)

Analyst spec for unit P1.1 (see `conversion/TRACKER.md`). Read-only analysis of
baseline `40e733cee`. Paths are relative to the repo root. "Verify" marks a
fact that P1.1 must confirm on the running stack before it builds on it.

## 0. Summary of decisions in this spec

- Run the original stack with a harness-owned compose file
  `conversion/parity/stack/compose.original.yml`. Do not use
  `docker-compose.dev.yml` as is (it needs the JavaScript executor and has a
  broken builder healthcheck).
- Put an edge proxy (Caddy) in front: `http://app` → builder, `/ws/*` →
  realtime, `/storage/*` → RustFS. The production Next build has no `/ws` or
  `/storage` rewrites.
- Run the tests in a runner container on the compose network, not on the Dell
  host. Presigned S3 URLs, MailHog and the fake upstream use service names.
- Intercept all third-party traffic with one fake upstream container at IP
  `1.1.1.1` on a private Docker subnet: DNS server, DoH server, HTTPS (test CA)
  and HTTP. App containers use `dns: [1.1.1.1]` and `NODE_EXTRA_CA_CERTS`.
- Workspace creation, workspace API tokens, platform credentials and channel
  connects exist **only as Next.js server actions**. Bootstrap goes through a
  pluggable "fixture driver". This is the largest open question (section 9).

Problems in the dev compose file that the harness compose file must fix:

1. Worker depends on `javascript-executor` (`docker-compose.dev.yml:60-61`) and on
   its internal network (:52). Remove both.
2. Builder healthcheck runs `curl` (`docker-compose.dev.yml:39`), but the builder
   `release` stage installs no curl (`apps/builder/docker/Dockerfile:90-108`, base is
   `node:24.22.1-trixie-slim`). Use
   `["CMD","node","-e","fetch('http://127.0.0.1:3000/api/health').then(r=>process.exit(r.ok?0:1),()=>process.exit(1))"]`.
3. Worker and realtime depend only on postgres/redis. Migrations run inside the
   builder entrypoint, so the worker can start on an unmigrated DB. Add
   `builder: {condition: service_healthy}` to worker and realtime.
4. The included `docker-compose.yml` publishes host ports 5432, 6379, 9000, 9001,
   1025, 8025. Use `include: [{path: [../../../docker-compose.yml, ./infra.override.yml]}]`
   with `ports: !reset []` in the override, so the Dell host keeps its ports free.

### 1.2 JavaScript executor: worker starts without it

`JAVASCRIPT_EXECUTOR_URL`/`_TOKEN` are validated lazily, only inside
`javascriptExecutionService.execute()` (`packages/business/src/javascript-execution/keys.ts:4-12`,
`service.ts:24`). The worker env schema has no executor key
(`apps/worker/src/env.ts:12-196`). So the worker boots without the variable; only an
"Execute JavaScript" step fails at run time. Do not set the variable.

### 1.3 Migrations and seed

- Builder entrypoint: `RUN_DB_MIGRATE=true` runs `/app/migrate-runner/scripts/run-migrations.mjs`;
  `RUN_DB_SEED=true` runs `/app/seed-runner/seed.cjs`; then `node apps/builder/server.js`
  (`apps/builder/docker/rootfs/usr/local/bin/docker-entrypoint.sh:7-22`).
  Set both to `true` on the builder only (as `docker-compose.dev.yml:43-45`).
- Seed (`packages/database/src/seed/index.ts:10-70`) is idempotent (skips if any
  user exists, :12-15). It creates user `demo@example.com` / password `Demo@1234`,
  `emailVerified: true`, a credential account, workspace `DEMO`
  (timezone `Asia/Saigon`) and an `owner` membership with all permissions.
- The root tenant `ROOT_TENANT_ID = "1"` comes from the `add_tenant_tables`
  migration, not from the seed (`docs/tenancy.md:13`).
- Tests must not depend on the demo rows except as a known extra user/workspace.

### 1.4 Readiness order and health endpoints

1. postgres, redis, filesystem healthy; filesystem-init exits 0; mailhog and
   fake-upstream started.
2. builder: migrate → seed → listen. Health `GET /api/health` → 200
   `{"status":"healthy","timestamp":"<iso>","service":"builder"}`
   (`apps/builder/src/app/api/health/route.ts:3-9`). Wait up to 5 min (cold
   migrate on TimescaleDB).
3. worker: no HTTP health. Ready when the log has `"Trigger worker started"`
   (`apps/worker/src/trigger/worker.ts:98`) or Redis `CLIENT LIST` shows BullMQ
   connections (verify the name pattern).
4. realtime: `GET /health` → `ok`; `GET /ready` → `ready` once the stream reader
   runs, else 503 (`apps/realtime/src/gateway.ts:310-318`).
5. edge `app`: `GET http://app/api/health` and `GET http://app/ws/ready`.

### 1.5 Edition flag

`NEXT_PUBLIC_EDITION` = `community | enterprise | cloud`, default `community`
(`apps/builder/src/env.ts:8-10`, `apps/worker/src/env.ts:4-6`). Effects (58 call sites
of `isCloud/isEnterprise/isCommunity`):

- `community`: no quota rows (unlimited); enterprise features off; support
  access always needs owner consent (`.env.example:22-25`).
- `cloud`: sign-up writes a bootstrap `UserQuota` trial row and enqueues
  `publishEntitlements` for a **private** quota worker that is not in this repo
  (`apps/builder/src/lib/auth/on-user-created.ts:38-60`); webhook credential lookup
  requires the broker host (`apps/builder/src/app/integrations/[...integration]/webhook.ts:303-310`).
  Enterprise features are always entitled (`docs/licensing.md`, table "edition sets the ceiling").
- `enterprise`: enterprise features need a vendor-signed `LICENSE_KEY` (Ed25519,
  `docs/licensing.md`). We cannot sign one.

Use `community` for P1.1–P1.27. Enterprise-only routes (white-label tenants,
admin workspaces, OIDC) need a second run profile with `cloud`; decision in
section 9.

### 1.6 Edge proxy (required)

In a production build, Next has no `/ws` or `/storage` rewrites
(`apps/builder/next.config.ts:84-86` returns before :101-109). The public realtime
URL is `<builder>/ws/` and the public storage URL is `<builder>/storage/`
(`packages/business/src/platform/derive-urls.ts:1-2,25-33`). `stack/Caddyfile`:

```
:80 {
  handle_path /ws/* { reverse_proxy realtime:1999 }
  handle_path /storage/* {
    rewrite * /chatbotx{path}
    reverse_proxy filesystem:9000
  }
  reverse_proxy builder:3000
}
```

Use port 80. `getPublicUrlFromRequest` drops the port (`packages/utils/src/request.ts:10-15`)
and better-auth rewrites only the hostname of email links
(`packages/auth/src/server.ts:758-759`), so a non-default port breaks links.
The Rust stack later sits behind the same edge.

### 1.8 Build time and size (estimates, verify on first run)

- Builder: `turbo prune` + `pnpm install` + `next build` + migrate/seed runners
  (`apps/builder/docker/Dockerfile:11-87`). `NODE_OPTIONS=--max-old-space-size=4096`
  (:20); the real peak of `next build` for this app is likely 5–8 GB RSS. Cold build
  15–30 min on 8 cores. Image ~1.5–2 GB.
- Worker: tsdown build + sourcemap prune (`apps/worker/docker/Dockerfile:27-31`),
  5–10 min, image ~0.7–1 GB, runtime ~500 MB (:57).
- Realtime: no release stage; the final image is the `deps` stage with the full
  pruned install, run by `tsx` (`apps/realtime/docker/Dockerfile:17-32`,
  entrypoint `exec ./node_modules/.bin/tsx src/main.ts`). Image ~1.5–2.5 GB.
- Pulls: `timescaledb-ha:pg18-all` is several GB.
- Runtime total ≈ 2.5–3 GB RSS (user baseline 2 GB plus edge, fake, runner).
- Build one image at a time (`docker compose build builder && … worker && … realtime`).
  Do not build while the Android emulator (~5 GB) or a `pnpm test` runs on the Dell.
- The build context includes `conversion/` (not in `.dockerignore`); `turbo prune`
  ignores it, so layer cache after `pre` stays valid. No change needed.

## 2. Bootstrap a test tenant from outside

Facts:

- Sign-up is open by default: `AUTH_DISABLE_SIGNUP` default `false`
  (`packages/auth/src/keys.ts:20`); the gate is `guardEmailSignUp`
  (`packages/auth/src/server.ts:560-571`).
- Email verification is required: `requireEmailVerification: true`
  (`server.ts:686-688`). There is no auto-verify flag. The verification mail goes
  through `SMTP_SERVER` (MailHog) (`server.ts:738-783`).
- Session: better-auth cookies `better-auth.session_token` and
  `better-auth.session_data` (cookie cache, 5 min, `server.ts:934-940`). No
  `__Secure-` prefix because the URL is http. `bearer()` plugin also accepts
  `Authorization: Bearer <session token>` (`server.ts:864-869`).
- Trusted origins = broker URL + `NEXT_PUBLIC_BUILDER_URL` + custom domains
  (`server.ts:944-972`). Send `Origin: http://app` on every non-GET auth call.
- better-auth rate limit (production): `/sign-in*`, `/sign-up*` max 3 per 10 s per
  client IP (better-auth 1.7.14 `dist/api/rate-limiter/index.mjs:305-312`).
- Workspace creation and workspace API token creation have **no** `/rpc` or
  `/api/v1` procedure. They are server actions only:
  `createApiAction` (`apps/builder/src/features/integration-api/actions/create-api.action.ts:12-50`,
  creates a workspace + API channel, returns `{workspaceId, token: cbx_api_…}`) and
  `createWorkspaceTokenAction` (`apps/builder/src/features/workspaces/actions/create-workspace-token-action.ts:16-43`,
  returns `{token: cbx_ws_…}`). 514 files in `apps/builder/src` start with `"use server"`.
- Token check: SHA-256 hex of the token, looked up in `WorkspaceApiToken.tokenHash`
  (`apps/builder/src/middlewares/workspace-token-auth.ts:115-120`,
  `packages/business/src/workspace-api-token/credentials.ts:49-55`).

Request sequence (all JSON bodies use `Content-Type: application/json`):

|---|---|---|
| 1 | `POST http://app/api/auth/sign-up/email`, `Origin: http://app`, body `{"email":"u<run>-<n>@parity.test","password":"Parity#12345","name":"Parity <n>"}` | 200, `user.emailVerified=false`, no session cookie |
| 2 | `GET http://mailhog:8025/api/v2/search?kind=to&query=<email>` (poll ≤10 s) | 1 message; decode quoted-printable; extract `http://app/api/auth/verify-email?token=…` |

`/rpc` uses the oRPC 1.15.4 RPC protocol (`apps/builder/src/app/rpc/[[...rest]]/route.ts:8-17`):
path `/rpc/<routerKey>/<procedureKey>`, POST body `{"json":<input>,"meta":[…]}`,
response `{"json":<output>,"meta":[…]}` (`meta` encodes Date/BigInt/undefined).
Batch plugin is on. `/api/*` serves only the public router (`apps/builder/src/app/api/[[...rest]]/route.ts:11-21`).

Alternative user credential for the public API: `POST /api/auth/mobile/token`
`{"grantType":"password","email","password"}` → `{tokenType:"Bearer",accessToken,refreshToken,…}`
(`packages/auth/src/mobile-auth.ts:30,44-65,299`). With `x-workspace-id` this
authenticates as a member (`workspace-token-auth.ts:107-113`). Required for
`GET /api/v1/realtime/connect-token`.

Fixture driver (`src/fixtures/driver.ts`): an interface the tests call for setup
that has no public HTTP path: `createWorkspace`, `createWorkspaceToken`,
`setPlatformCredential(type, config)`, later `connectChannel(...)`. Setup calls
are not parity assertions. Two implementations for P1.1:

- `next-actions` (default for the original stack): call the server action over
  HTTP. `POST http://app/` with headers `Next-Action: <id>`, `Origin: http://app`,
  `Accept: text/x-component`, `Content-Type: text/plain;charset=UTF-8`, cookie;
  body = JSON array of arguments, bound args first
  (`["<workspaceId>",{…}]` for `createWorkspaceTokenAction`,
  `[{"name":"Parity WS"}]` for `createApiAction`). Parse the RSC response line
  that holds `{"data":…}`. Action IDs change per build: `run-original.sh` copies
  `/app/apps/builder/.next/server/server-reference-manifest.json` out of the
  builder container to `.state/actions.json`. Verify that the manifest maps IDs to
  file + export name in Next 16; if not, map by worker module path.
- `sql` (fallback): `docker compose exec postgres psql` inserts rows
  (`Workspace`, `WorkspaceMember`, `WorkspaceApiToken` with `tokenHash` =
  sha256 hex). Schema: `packages/database/src/schema/workspace-api-token.ts`.
  Platform credentials are encrypted with `ENCRYPTION_KEY`
  (`packages/database/src/schema/platform-credential.ts:33-37`), so the SQL driver
  cannot write them without the encryption code.

Rate-limit plan: create users in `globalSetup` only, at most 3 per 10 s, or send a
unique `X-Forwarded-For` per user (verify better-auth honors it). One owner user
per run, one new workspace per test file. Community edition has no workspace
quota.

The SSRF guard is the hard part. It resolves every user URL through DoH at
`https://1.1.1.1/dns-query` and rejects private IPs (`ssrf-guard.ts:8-23`), so a
fake on a 172.x Docker IP is always "unsafe". `decision/transport.ts:85-111` then
dials the **pinned** resolved IP with its own undici `Agent`, so env proxies do not
apply.

No certificate pinning: no `checkServerIdentity`, `rejectUnauthorized`, custom
`ca:` or `node:dns` use in app code. No gRPC dependency (google-ads uses REST).

### 3.1 Proposed interception (default)

- Docker network `parity-upstream`, subnet `1.1.1.0/24`, gateway `1.1.1.254`.
  `fake-upstream` has `ipv4_address: 1.1.1.1` on it and is also on
  `chatbotx-network` (admin API). builder, worker, realtime join both networks.
- `fake-upstream` serves:
  - DNS UDP+TCP :53 — every A query → `1.1.1.1`, AAAA → empty. Docker's embedded
    DNS answers service names first and forwards other names to `dns: [1.1.1.1]`.
  - HTTPS :443 — SNI cert from the test CA, routed by `Host`. Includes the DoH
    endpoint `GET /dns-query?name=&type=A` on host `1.1.1.1` (cert SAN `IP:1.1.1.1`)
    returning `{"Answer":[{"type":1,"data":"1.1.1.1"}]}`. `1.1.1.1` is not in the
    blocked ranges, so the guard passes and the pinned dial reaches the fake.
  - HTTP :80 — same router.
  - Admin HTTP :4010 (only on `chatbotx-network`).
- TLS: `run-original.sh` makes `.state/tls/ca.{crt,key}` (openssl, 30 days) and one
  leaf cert from `fake-upstream/hosts.txt` (SANs incl. `*.facebook.com`,
  `*.myshopify.com`, `*.api.mailchimp.com`, `*.googleapis.com`, `*.tiktokapis.com`,
  `*.parity.test`, `IP:1.1.1.1`). `*.pem`/`*.key` are git-ignored, so certs are
  never committed. Unknown SNI gets a fallback cert and the fake records
  `unknownSni`, so the test sees the miss.
- Trust: `NODE_EXTRA_CA_CERTS=/parity-tls/ca.crt` in builder, worker, realtime.
  Node applies it to `https`, undici `fetch` and the SDKs above. Later, Rust:
  `SSL_CERT_FILE` works only with native-roots TLS; a Rust build that uses
  `webpki-roots` ignores it (record this for the Rust units).
- Hermetic: the fake answers unknown hosts with 599 and records them; a test
  fails on any unexpected upstream call.
- Verify in smoke: `getent hosts graph.facebook.com` inside builder → `1.1.1.1`.
  Fallback if embedded-DNS forwarding fails: `extra_hosts` generated from
  `hosts.txt` (no wildcards, so Shopify/Mailchimp hosts must be listed per test).
- Dell check: its DNS is `192.168.1.254` and Tailscale `100.100.100.100`, not
  1.1.1.1, so the host route for `1.1.1.0/24` does not break it.

Simpler alternative considered: Node 24 `NODE_USE_ENV_PROXY=1` + `HTTPS_PROXY`
to a MITM proxy. Rejected as default: the pinned undici `Agent` in
`decision/transport.ts` bypasses it, and it still needs the CA. No per-host env
override exists, so there is no simpler way.

### 3.2 Fake upstream design

- Node 24 TypeScript (erasable syntax, runs with type stripping), no framework.

## 7. Determinism and normalization

Sources:

- IDs: numeric snowflakes `timestamp<<14 | placeId<<10 | seq` (`packages/utils/src/id.ts:4-20`),
  as strings. Time-ordered; place id random 1–15 if unset (`.env.example:168-173`).
- Timestamps: `createdAt`, `updatedAt`, `timestamp`, `expiresAt`, `lastSeenAt`…
- Tokens/secrets: `cbx_ws_…`, `cbx_api_…`, JWTs (realtime 60 s, mobile access),
  better-auth cookies, webhook secrets, presigned URL query (`X-Amz-Date`,
  `X-Amz-Signature`).
- Realtime `seq` (Redis stream ids).
- Ordering: lists by `createdAt`/id with ties; worker job order; fake records.
- Headers: `date`, `etag`, `content-length`, `set-cookie`, `x-*` tracing,
  rate-limit headers.
- Error text: zod messages and Next.js HTML 404/500 pages.
- Async: worker jobs finish after the HTTP response.

Rules (`src/normalize.ts`, used by both stacks):

1. Compare JSON by value, never by text or key order.
2. Snowflake-like strings (`^\d{15,20}$`) in id-named keys (`id`, `*Id`, `*Ids[]`)
   → `<id:1>`, `<id:2>` … by first appearance in the test. The same id gets the same
   label, so references between objects are still checked.
3. ISO-8601 strings → `<ts>`; also assert each one lies in
   `[testStart − 5 s, now + 5 s]` unless the test sets the value.
4. Token patterns → `<cbx_ws>`, `<cbx_api>`, `<jwt>` (decode JWT and check claims
   `aud`, `purpose`, `exp − iat` where it matters).
5. URLs: keep scheme/host/path; drop signature query params.
6. `seq` → `<seq>`; check monotonic order inside one socket.
7. Headers: assert only `status`, media type of `content-type`, `location`
   (normalized), `cache-control`, `allow`, `retry-after` (range),
   `www-authenticate`.
8. Lists: keep order when the API documents a sort; else sort by a stable key
   before compare (`unordered()` helper).
9. Errors: compare HTTP status and oRPC `code` (`defined`, `code`, `status`, `data`
   keys); compare `message` only for errors the code defines with fixed text.
10. Async: `eventually(fn, {timeoutMs, intervalMs})`, never fixed sleeps.
11. Unique data per run: `runId` (time + random) in emails, names, bot tokens.

Tests use explicit assertions plus `expectNormalized(value).toMatchSnapshot()`.
Snapshots are recorded on the original stack and frozen in P1.28.

## 9. Risks and open questions

Risks:

1. **Docker access on the Dell.** User `alextoska` is not in group `docker`
   (`id` → groups `alextoska, wheel`; socket `root:docker 660`); `docker info`
   fails with "permission denied", and `sudo` needs a password. Alex must run
   `sudo usermod -aG docker alextoska` (then log in again) before P1.1 can run.
2. **Dell memory.** At analysis time: 15 GB total, ~1 GB free, 13 GB swap used;
   Android emulator (qemu, ~5 GB) and the P0.3 vitest run were active. A cold
   `next build` (5–8 GB) plus the stack will swap or OOM. Run builds and the stack
   only when the emulator and other test runs are stopped.
3. **Setup paths are server actions.** Workspace, token, platform-credential and
   channel setup have no `/rpc` or `/api/v1` path (514 `"use server"` files).
   The `next-actions` driver depends on build-specific action IDs and the RSC
   wire format. The Rust stack will need its own driver. The tracker has no
   unit for server-action parity at all.
4. **SSRF guard + 1.1.1.1 hijack.** The interception depends on Docker accepting
   subnet `1.1.1.0/24` and on embedded DNS forwarding to `1.1.1.1` from the
   container namespace. If either fails, user-URL tests (webhooks, external
   requests, AI Router, MCP) cannot reach the fake.
5. **Rate limits.** better-auth 3 sign-in/sign-up per 10 s per IP; public API 120
   requests/10 s per workspace and 600/10 s pre-auth per IP
   (`apps/builder/src/lib/rate-limit/api-rate-limit.ts:5-6`,
   `middlewares/workspace-token-auth.ts:47`). All tests come from one runner IP.
6. **Unpinned images** (`rustfs/rustfs:latest`, `rustfs/rc:latest`,
   `adminer:latest`, `mailhog/mailhog`, `redis/redisinsight:latest`) can change
   behavior between the original run and the Rust run. Pin digests in
   `infra.override.yml`.
7. **Async worker effects** make tests slow or flaky without `eventually`
   helpers and unique data.

Open questions (one decision each):

1. Fixture driver: is the SQL driver allowed (it ties tests to the DB schema), or
   must setup go only through HTTP (server actions now, Rust RPC later)?
2. Will the Rust backend keep the same Postgres schema? This decides if the SQL
   driver works on both stacks.
3. Server actions: does the Rust plan replace the 514 server-action files with
   `/rpc` procedures, and must they get parity tests (new tracker units)?
4. Enterprise-only features: add a second run profile with
   `NEXT_PUBLIC_EDITION=cloud` (no private quota worker), or mark those tests out
   of scope?
5. Is it acceptable that the parity network hijacks `1.1.1.1` inside the stack
   (needed because the DoH address is hard-coded)?
