## 1. Common rules

### 1.1 Auth — workspace-token operations (20)

- Same middleware chain as P1.3 §1.1: token → pre-auth IP limit (600/10 s)
  → workspace lookup → per-workspace limit (120/10 s) → read-only check →
  **scope** → idempotency → input validation → handler.
- No / unknown token: **401** `INVALID_CHATBOT_TOKEN`, message
  `Invalid or missing workspace API token`, `defined: true`. A `cbx_api_`
  channel token on a workspace route is also 401 `INVALID_CHATBOT_TOKEN`.
- Scopes: `connections.*`, `connectSessions.*`, `connectionProviders.list`
  → `['channels','integrations']` (OR; one is enough);
  `commentAutomations.*` → `automation`; `contactScans.*` → `contacts`.
  Missing: **403** `FORBIDDEN`, message
  `Token is not authorized for the 'channels' or 'integrations' scope` /
  `... for the 'automation' scope` / `... for the 'contacts' scope`.
- Second, per-provider scope check inside the connections routers
  (`assertTokenScopeForProvider`): a channel-kind provider needs `channels`,
  an integration-kind provider needs `integrations` (403 `FORBIDDEN`,
  `Token is not authorized for the '<scope>' scope`). Applied to
  `connections.create` (requested provider), every `{id}` route (stored
  provider; 404 is checked first) and every connect-session route.
- List kind (`resolveListKind`, `connections.list` and
  `connectionProviders.list`): a token with exactly one of the two scopes
  gets its kind forced; an explicit `kind` outside the token's kinds → 403.
- Read-only token: GET passes; writes are **403** `FORBIDDEN`,
  `Read-only token cannot perform this operation`. Writes of this unit:
  `connections.{create,update,disconnect,reconnect,refresh,verify}`,
  `connectSessions.{cancel,connectTargets}`,
  `commentAutomations.processMissedComments`, `contactScans.create`.

### 1.2 Auth — API channel operations (`channels.*`, 5)

- `Authorization: Bearer cbx_api_…` only (no `?token=`). SHA-256 of the
  token is looked up in `IntegrationApi.tokenHash`; the row must be
  `enabled`. Missing token, unknown token or a `cbx_ws_` token → **401**
  `UNAUTHORIZED` (`defined: true`). The token of a **disconnected** API
  channel still authenticates: the `api` store binding keeps its
  `IntegrationApi` row on disconnect (`onDisconnect: "keep_row"`) and the
  middleware does not check the inbox or connection status. Workspace scheduled for deletion → 403
  (not tested, no public path).
- Rate limit per inbox: 120 requests / fixed 10 s window
  (`channel-api-rate-limit`); over → **429** `tooManyRequests` with
  `Retry-After` (seconds to the next window).

### 1.3 Errors and idempotency

- Body `{defined, code, status, message, data?}`. Input-schema rejection:
  **422** `invalidRequestData`, `data.issues[].path`.
- A `ZodError` thrown inside a handler (the `api`/`webchat` provider config
  is parsed in the handler) is also **422** `invalidRequestData`, but `data`
  is the bare issue array (not `{issues}`); tests read both forms.
- `ChatbotXException` → its own code/status; undeclared codes come back
  with `defined: false` (e.g. `connectSessionLimitReached` 429).
- `Idempotency-Key` (1–255 chars) on any non-GET route: same key + same
  input → the stored output again, header `Idempotent-Replayed: true`;
  `connections.create`'s replay has `secret: null` (one-time token is
  redacted). Same key + other input → 422 `idempotencyKeyReused`; 256 chars
  → 422 `idempotencyKeyInvalid`; in flight → 409 `idempotencyKeyConflict`
  (not tested: needs two concurrent requests with a held lock).
- Lists: `page` ≥ 1 (default 1), `perPage` 1–50 (default 50), response
  `{data, pageCount}`; `pageCount = max(1, ceil(count/perPage))` for
  `connections.list`, always 1 for `connectionProviders.list`.

## 2. connections / connectionProviders / connectSessions

### 2.1 Resources

- `Connection` DTO (never `auth`): `id, kind ('channel'|'integration'),
  provider, channel (null for integrations), status
  ('connected'|'degraded'|'needs_reauth'|'paused'|'disconnected'),
  statusReason, sourceId, displayName, inboxId, integrationId, strategy
  ('oauth_redirect'|'oauth_popup'|'token'|'api_key'|'self_serve'),
  capabilities {refreshable (adapter has refreshAuth), verifiable (provider
  has verify), multiAccount}, authExpiresAt, lastError, connectedAt,
  disconnectedAt, createdAt, updatedAt` (ISO strings).
- `ConnectSession` DTO: `id, provider, purpose ('connect'|'reconnect'),
  status ('pending'|'authorized'|'awaiting_selection'|'completed'|'failed'|'expired'|'cancelled'),
  step ('authorize'→'select'→'done'), nextAction ({type:'open_url', url} |
  null), targets [{id, name, avatarUrl?, selectable, disabledReason?,
  alreadyConnected?: 'this_workspace'|'other_workspace'}], connectionIds,
  errorCode, expiresAt`. Pending TTL 10 min, authorized/awaiting 30 min.
  Expiry is applied lazily on read (`expired`).
- Envelope of `connections.create` / `reconnect` (201):
  `{connection, session, secret}`; exactly one of connection/session is set;
  `secret = {kind:'api_channel_token', token:'cbx_api_…'}` only for `api`.

### 2.3 `connections.create` by strategy

- Guards, in order: provider scope (403) → `googleAds` 403
  `connectionProviderDedicatedOnly` → no adapter (`metaCatalog`) 400
  `connectionNotConfigured` → `facebookAds` 400 `connectionNotOAuth` →
  tenant channel policy 403 `channelHidden` (no tenant policy in community;
  not tested).
- `self_serve` (`api`, `webchat`): `config` parsed by the provider schema
  in the handler (ZodError → 422). `api`: `name` 1–40, `callbackUrl?` URL;
  a callback URL that resolves to a private address (SSRF guard via DoH)
  → 422 `invalidRequestData`. Writes Inbox (id = sourceId = IntegrationApi.id)
  + IntegrationApi (token hash) + Connection; multi-instance.
- `token` / `api_key`: `config` checked against `configFields`
  (`<field> is required`, `<field> must be a string`, unknown key →
  422 `validation` `Unsupported config field(s) for <provider>: <keys>`),
  then live-checked upstream: DeepSeek `GET https://api.deepseek.com/models`
  (Bearer key; 401/403 → 400 `connectionCredentialsRejected`; other failure
  → 502 `connectionProviderUnavailable`), Telegram `GET /bot<token>/getMe`.
  An active row for the same `(workspace, provider, sourceId)` → 409
  `connectionAlreadyConnected` (the upstream check runs first).
- Disconnect of an **integration-kind** connection (AI keys and other
  workspace integrations): the binding deletes the parent `Integration`
  row; the `Connection.integrationId` FK cascade deletes the `Connection`
  row too. The DELETE answers 200 with the `disconnected` DTO, but a later
  GET is 404 and the list no longer has it; a new connect creates a new
  connection id. A **channel-kind** connection keeps its row (`disconnected`).
- `oauth_*` (`messenger`): owner's platform credential (user-owned row, or
  the platform row) → else 400 `connectionNotConfigured`. Creates a
  `pending` session; `nextAction.url` =
  `https://www.facebook.com/<version>/dialog/oauth?client_id&redirect_uri=http://app/integrations/messenger/callback&scope=<12 scopes>&response_type=code&state=<sessionId>.<nonce>&auth_type=rerequest`.
  20 active sessions per workspace max → 429 `connectSessionLimitReached`
  (undeclared, `defined:false`). `redirectUrl` is kept only when its origin
  is allowed (app host); else the completion page `/connect/<id>`.
- OAuth callback (`GET /integrations/<slug>/callback`, no cookie): unknown
  state or wrong provider slug → 404; `error=access_denied` → session
  `failed/provider_denied`, other `error` → `failed/provider_error`; with
  `code`: Graph `GET /v23.0/oauth/access_token` (code → short token, then
  `fb_exchange_token` → long token), `GET /v23.0/me/accounts` (pages with all
  admin tasks + access_token are selectable) → `awaiting_selection`
  (messenger is multi-account, so it never auto-connects); exchange 4xx →
  `failed/exchange_failed`; no pages → `failed/no_candidates` and
  `?connect_error=no_candidates`. Redirect (307) to the return URL.
- connectTargets (messenger): writes Inbox + IntegrationMessenger +
  Connection, then `POST /v23.0/me/subscribed_apps` (Bearer page token;
  first with the marketing-message fields, then once more with the base
  fields; the Graph client retries a 5xx). When every attempt fails the
  connection is still created, with status `degraded` / `verify_failed`.
- Telegram: the bot token is checked with `GET /bot<token>/getMe`; no
  webhook is set on connect; disconnect calls `POST /bot<token>/deleteWebhook`
  (a failure only fills `lastError`, which the DELETE response itself does
  not show yet — a later GET does). A bot id is unique across workspaces
  (the same bot in a second workspace → 409 `connectionAlreadyConnected`).

## 6. Fixtures (`p1-05`)

Setup with no public HTTP path: Messenger / Instagram channel (Inbox +
integration row + Connection, plain-JSON channel auth), bare Inbox,
Contact+ContactInbox+Conversation, CommentAutomation, CommentModerationLog,
user-owned Messenger PlatformCredential (AES-GCM with AAD
`user:<userId>:messenger:false`), and moving a session's `expiresAt` into the
past. The credential row must be written before the tenant's first
credential lookup (the app caches it per owner).

## 8. Not tested black-box (with reason)

- `connections.refresh` success path: needs an OAuth connection whose
  adapter has `refreshAuth` and a refreshable token; Messenger page tokens
  do not expire. Only the refusal paths are tested.
- `channelHidden`, `channelLimitReached`, `hiddenForTenant`: need a tenant
  policy / plan limits (cloud edition only).
- `notImplemented` catalog entries are only in the snapshot (no behavior).
- The channel-provider catalog (`available` / `credentialMissing` for
  Messenger and the other channels) cannot be read: the route fails with 422
  for channel kinds (§2.2). The OAuth `credentialMissing` rule is asserted
  through `googleSheets` in the integration catalog only.
- `idempotencyKeyConflict` (409): needs a request held in flight.
- Workspace scheduled for deletion (403) on the channel API: no public path
  to schedule a deletion with a token.
- `IntegrationApi.enabled = false`: set only by a builder server action.
- `processMissedComments` `workspaceInactive` / `alreadyRunning`: need
  workspace active-hours settings or a held Redis lock; not reachable
  deterministically.
- Instagram / Threads / TikTok missed-comment scans and contact-scan for
  Instagram: same shape as Messenger with other hosts; Messenger covers the
  route logic.
- `channels.markRead` / `deliveryStatus` worker effects: the API channel has
  no outbound message to mark (needs an outgoing message from a bot flow).
- The exact stored phone of an API-channel contact: for the same input
  `+15550001111` the original stored `+848864158` in one run and
  `+15550001111` in another (non-deterministic; to decide in the Phase 3
  contacts unit). Tests only check an E.164-like string.
- The stored inbound message itself: `GET /v1/contacts/{id}/messages` answers
  404 for the API-channel contact in the original (contacts unit, P1.6);
  the message is checked through the conversation timestamps only.
- Realtime events of connect/disconnect and of the inbound message: not
  asserted (covered by the realtime unit).
- Session `authorized` state (callback crashed between exchange and
  listing) and a reconnect callback (identity check): need a provider
  fault between two Graph calls.
- The 422 for a non-numeric `{id}` on connections/connect-sessions
  (`zod` string, then a bigint DB error) is not asserted.
