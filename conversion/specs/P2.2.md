## 1. Type mapping (applies to every column)

Conventions for all generated DDL:

- Keep the Postgres table and column names exactly (quoted CamelCase, e.g. `"ContactInbox"."sourceUserId"`). Raw SQL then ports with few edits.
- Use `STRICT` tables (type check on write). Exception: the 2 vector tables (declared type `F32_BLOB(1536)` is not allowed in STRICT; §1.9).
- Use rowid tables (no `WITHOUT ROWID`). The 25 `ctid` uses (chunked deletes) port to `rowid`.
- Single-column bigint `id` → `"id" INTEGER PRIMARY KEY` (rowid alias, 8 bytes, fastest lookups).
- Every write sets `createdAt` / `updatedAt` from Rust. `$onUpdate` in Drizzle and the 2 Postgres `updatedAt` triggers become Rust code. Keep a DB default only as a safety net.
- Drizzle `.default(...)` with no SQL default (17 columns, all arrays/json: `AIAgent.messages/tools/webSearchAuthorizedDomains/models`, `AIMCPServer.selectedTools`, `AutomatedResponse.keywords`, `Folder.paths`, `IntegrationInstagram.conversationStarters/persistentMenus`, `IntegrationMessenger.conversationStarters/persistentMenus/personas`, `IntegrationWebchat.authorizedDomains/conversationStarters/persistentMenus`, `Trigger.actions`, `UserPersistentMenu.menus`) — give them `DEFAULT '[]'` in SQLite and also write the value in Rust (skill note "`.default()` is not a database default").

### 1.2 Ids

- Format: numeric snowflake, `timestamp(ms since 2004-02-01) << 14 | placeId(4 bits) << 10 | sequence(10 bits)` (`packages/utils/src/id.ts`). Fits in a signed i64 (63 − 14 bits of ms ≈ 17,000 years).
- Generated in app code only (`sharedColumns.id.$defaultFn(createId)`); there is no DB default. The Rust `core` crate must have the same generator (same epoch and layout) so that old ids decode (`resolveId`) and new ids sort after them.
- One process → set `SNOWFLAKE_PLACE_ID` to a fixed value (0–15); the random fallback is for multi-replica Node only.
- Never insert NULL into an `INTEGER PRIMARY KEY` (SQLite would assign a rowid). Repositories always pass the snowflake.
- JSON: always a string. Inputs: accept only `^\d{1,19}$` that fits i64 (`isBigintId`), same as now.

### 1.3 Timestamps — recommendation: INTEGER unix milliseconds

| Criterion | INTEGER unix ms | ISO-8601 TEXT (ms + `Z`) |
|---|---|---|
| API JSON shape | Rust formats `%Y-%m-%dT%H:%M:%S%.3fZ` — identical to `toISOString()` | stored text can be returned as is |
| Precision | ms. Postgres keeps µs, but node-pg/JS already truncates to ms, so the API never showed µs | same |
| Size (764 columns; Message, events, recipients are the big tables) | 1–8 bytes | 24 bytes; index pages 3× larger → more RAM for the same cache hit rate |
| Range/bucket math (`time_bucket` 42 uses, `date_trunc` 6, `interval`/`make_interval` 42) | integer arithmetic: `ts / 3600000 * 3600000` | needs `strftime`/`julianday` per row |
| Format drift | none (one representation) | a writer that emits `+00:00` or no ms breaks ordering and equality |
| Human reading in `sqlite3` | `datetime(ts/1000,'unixepoch','subsec')` | direct |

Recommendation: **INTEGER unix ms UTC** for all timestamp columns. Notes:
- Compare and order in SQL on the integer; convert only at the API edge.
- Pass "now" from Rust as a parameter (one clock, testable) instead of `now()` in SQL; the 205 `now()`/`CURRENT_TIMESTAMP` uses become a bound `?now`.
- Keyset cursors that embed Postgres timestamp text (`pipeline/item-cursor.ts`, `template/selectable-cursor.ts`, µs precision) are opaque tokens; the Rust API makes its own cursor format (integer ms + id). Accept the old text format on input only if a test sends one.
- µs → ms: two `now()`-stamped columns compared in SQL (e.g. generated `isRead = seenAt >= deliveredAt`) can tie at ms where Postgres did not. Accept.

### 1.4 Money

- `money()` columns (`numeric(19,4)`, mode number): INTEGER ×10,000 is exact (`SUM` never drifts — the reason the original uses numeric) and fast. Max value 922,337,203,685,477.5807 major units; numeric(19,4) allows up to 10^15 − 0.0001, so only the top 8 % of the range is lost. Add `CHECK (abs("x") <= 9000000000000000000)` and reject larger input in the API.
- Convert with the same half-away-from-zero rule as `roundToMoneyScale()` (`partials/shared.ts`) on the decimal text of the input, not on the float.
- Unbounded `numeric` (conversion values, 3 columns): TEXT + `rust_decimal`. They are returned as strings and summed into strings.
- `Product.price/taxes/discount`, `ProductVariant.price` are `double precision` in Postgres (legacy). Keep REAL — do not "fix" them, or JSON numbers change.

### 1.5 JSON (jsonb)

- Store compact JSON text written by `serde_json`. `CHECK (json_valid(x))` on every json column (224 incl. arrays).
- SQLite ≥ 3.38 has `->` and `->>` with Postgres-like key syntax (`"referral"->>'adId'`). The 4 partial / expression indexes on json paths (`AIFile.processingRun->>'queuedAt'`, `ContactInbox.referral->>'ctwaClid'/'adId'`, `Cart` `jsonb_array_length(items)`) port with `json_array_length`. The query must use the same expression text to use the index.
- Do not use SQLite binary JSONB storage (3.45 `jsonb()`): text is simpler to debug and is what the API returns.

### 1.6 Arrays

- All arrays → JSON array TEXT. Containment queries:
  - `"paths" @> ARRAY[?]::bigint[]` (`Folder`), `"keywords" @> ARRAY[?]::text[]` (`AutomatedResponse`) → `EXISTS (SELECT 1 FROM json_each("paths") WHERE value = ?)`.
  - `"tags" ?| array[...]` (`Product.tags`, jsonb) → `EXISTS (SELECT 1 FROM json_each("tags") WHERE value IN (SELECT value FROM json_each(?)))`.
  - `cardinality(x) > 0` (CHECK on `WhatsappSignupSession.candidatePhoneNumberIds`) → `json_array_length(x) > 0`.
- `= ANY(?::bigint[])` lists → `IN (SELECT value FROM json_each(?))` with one JSON parameter (no limit on list length, one prepared statement).

### 1.7 Enums

- 154 enums, 174 columns; full list with value counts and users is in the appendix (§A).
- `TEXT CHECK (x IN (...))`. Adding a value later = table rebuild in SQLite (12-step ALTER). The migration runner must support that (§4.3). Postgres `ADD VALUE` is forward-only here too.
- **Sort order**: Postgres orders an enum column by declaration order. Two list endpoints sort on enum columns: `decision/repository.ts:232` (`DecisionProfileStatus`: enabled, disabled) and `business/questionnaire/submission-service.ts:61` (`questionnaireSubmissionStatus`: inProgress, completed, cancelled, failed, timeout). Alphabetical order differs → use `ORDER BY CASE "status" WHEN 'enabled' THEN 0 … END`. The generic `orderBy` helper (`utils.ts`, any column) must do the same for every enum column.
- Some text columns are enums only by CHECK in Postgres (`ConnectSession.status/purpose/errorCode`, `Connection.kind/status/statusReason/providerEventKind`, `ContactReferralEvent.type/provider/clickIdType`, `MetaCapiEvent.channel/actionSource/contentType`, `GoogleAdsConversionEvent.uploadMethod`). Copy these CHECKs unchanged.

### 1.8 Case-insensitive uniqueness and text compare

- No `citext`. 4 unique indexes on `lower()`: `DiscountCode (workspaceId, source, lower(code))`, `Vendor (workspaceId, source, lower(name))`, `PlaceCategory (workspaceId, lower(name))`, `CouponTopic (workspaceId, lower(name)) WHERE deletedAt IS NULL`.
- Postgres `lower()` folds Unicode; SQLite `lower()` and `COLLATE NOCASE` fold ASCII only. Names in this product are often Vietnamese / non-Latin.
- Plan: add a Rust-maintained key column (`"codeKey"`, `"nameKey"` = Unicode `to_lowercase()`), put the unique index on it. Do not return it in the API. `COLLATE NOCASE` is not used anywhere (it would accept "Ä" and "ä" as different, unlike the original).
- `User.email` unique is case-sensitive in Postgres (better-auth lowercases before write). Keep BINARY collation.
- ILIKE (71 uses) / LIKE (9): see §3.5 for ESCAPE and Unicode.

### 1.9 Vectors

| Table.column | Dimension | Metric | Query | Index in prod |
|---|---|---|---|---|
| `AIEmbedding.embedding` | 1536 | cosine (`<=>`, similarity `1 - d`) | `repositories/ai-file-embedding/repository.ts:94` — filter `workspaceId`, `aiFileId IN (…)`, `status='success'`, ORDER BY distance LIMIT k | none (exact scan) |
| `AIConversationEmbedding.embedding` | 1536 | cosine | `repositories/ai-conversation-embedding/repository.ts:85` — filter by workspace/conversation/source | HNSW declared, never created (drift) → exact scan |

Plan: column `"embedding" F32_BLOB(1536)` (same bytes as libSQL `vector32()`), exact cosine over the pre-filtered rows with SQL function `vector_distance_cos(a, b)`:
with libSQL it is built in; with rusqlite (recommended crate, §4.2) register it as a deterministic app function (≈40 lines of Rust).
No ANN index: every query is pre-filtered to one workspace and a few files/conversations, so an exact scan is small, and a
global ANN index (`libsql_vector_idx` + `vector_top_k`) cannot pre-filter (it returns global top-k, then the filter drops rows → lower recall than today).

### 1.10 Full-text / trigram

No `tsvector`. 5 `gin_trgm_ops` indexes serve `ILIKE '%x%'`:

| Table | Columns | Plan |
|---|---|---|
| `Contact` | firstName, lastName, email, phoneNumber | FTS5 external-content table `"Contact_fts" USING fts5(firstName, lastName, email, phoneNumber, content='Contact', content_rowid='id', tokenize='trigram')` + AFTER INSERT/UPDATE/DELETE triggers |
| `ContactKeywordMessage` | normalizedText | `"ContactKeywordMessage_fts" … tokenize='trigram'` + triggers |

FTS5 trigram answers `LIKE`/`GLOB` with ≥ 3 characters; shorter needles fall back to a scan (Postgres trgm did the same for < 3).
Case folding of the trigram tokenizer (`case_sensitive 0`) follows Unicode simple folding; check with Vietnamese test data (risk 3).
Size: a trigram index is about 3× the text; measure in Phase 5 (risk 4).

## 2. Tables per domain

Counts: **P2.3 = 65 tables, P2.4 = 67 tables (65 to create; `MessageShard`, `ShardTimeRange` are not created, §3.2), P2.5 = 126 tables.** Total 258.
P2.5 is about twice the size of the others; the orchestrator can split it (e.g. P2.5a ecommerce + ads + analytics, P2.5b the rest) without changing this spec.

**Execute JavaScript (dropped):** no table, column, or enum value belongs only to that step. The step config lives inside
`FlowVersion.nodes` (jsonb[]). Only a comment in `partials/contact.ts:183` names it. Nothing to drop from the schema. Old flows that
contain the node type keep their JSON; the Rust flow engine must skip or reject the node (P4 decision, not schema).

Legend: FK action C = CASCADE, N = SET NULL, R = RESTRICT (ON UPDATE CASCADE is the default for 545 FKs; ids never change, so ON UPDATE can be dropped in SQLite).
"U(...)" = unique index or constraint, with its WHERE for partial ones. "+n idx" = other indexes; "+n partial" = non-unique partial indexes.
"Special care" lists jsonb / array / enum / money / generated / CHECK / expression-index counts and the notes from §3.

Forward foreign keys (child in an earlier part than its parent). SQLite rejects DML on a child whose parent table does not exist yet, so add these columns in the later part with `ALTER TABLE … ADD COLUMN … REFERENCES … ON DELETE SET NULL` (allowed because the default is NULL):

## 3. Postgres-only features and the SQLite plan

### 3.1 TimescaleDB

| Object | Postgres | SQLite plan |
|---|---|---|
| `Message`, `Attachment` hypertables | 7-day chunks on `createdAt`, compression after 30 d (segment by workspace), no retention. PK `(id, createdAt)`, unique `(contactInboxId, sourceId, createdAt)` (partition key forced into keys). `timescale.ts` lifts the decompression cap for bulk deletes. | Plain tables. `PRIMARY KEY(id)`; unique `(contactInboxId, sourceId)` — stricter than today (today two rows with the same source id but different `createdAt` are allowed). Check `primary-key-collision.ts` and dedup tests; if a test needs the loose form, keep `createdAt` in the unique key. Index `(conversationId, createdAt DESC, id DESC)` for paging. No compression (risk 4). `liftDecompressionLimit` → no-op. |
| 5 analytics hypertables (`Analytics{Contact,BotMessage,Conversation,Message,AgentResponse}Event`) | 30-day chunks, compression 30 d, retention 10 y. PK `(occurredAt, eventId)` | Plain tables; keep `PRIMARY KEY("occurredAt", "eventId")` (`eventId` is the event-bus id; insert is `ON CONFLICT DO NOTHING`, so the key is the dedup rule). Keep the existing `(workspaceId, …, occurredAt)` indexes. Retention job: daily `DELETE … WHERE occurredAt < now − 10 y` in chunks of 5,000 rows. |
| 4 continuous aggregates `analytics_*_events_hourly` | `time_bucket('1 hour')` + `GROUP BY` all filter columns + `count(*)`; refresh every 5 min for the last 7 d; `materialized_only = FALSE` (real-time: queries see un-materialized rows too); retention 3 y | Rollup tables `"analytics_contact_events_hourly"` etc. with the same columns + `count`. Maintain them **in the same write transaction** as the event insert, and only when the event row was really inserted (`changes() = 1` after the `ON CONFLICT DO NOTHING` insert): `INSERT … ON CONFLICT(bucket, workspaceId, …) DO UPDATE SET count = count + 1`; this gives the same real-time result. Nullable group columns (`channel`, `senderType`, `country`, `source`, `adminId`) are stored NOT NULL with sentinel `''` / `0` in the rollup (SQLite UNIQUE treats NULLs as distinct, so upsert would never match); Rust maps sentinel ↔ NULL. Event deletes (workspace purge, retention) also delete/decrement rollup rows. Retention job: rollups `< now − 3 y`. |
| Compression | 7 policies | None. WAL + `auto_vacuum=INCREMENTAL` + periodic `PRAGMA incremental_vacuum` after retention jobs. |

Queries: `time_bucket` 42 uses (all in `packages/analytics/src/repositories/postgres/*-stats.repository.ts`), intervals `1 minute` (2), `1 hour` (7), `1 day` (22), `1 month` (6), variable (5).
Port: `time_bucket('N unit', ts)` → `(ts / N_ms) * N_ms` for minute/hour/day (Timescale buckets align to the Unix epoch for these, same as integer division);
`'1 month'` → `CAST(unixepoch(strftime('%Y-%m-01', ts/1000, 'unixepoch')) AS INTEGER) * 1000`.
Workspace time zone (`ts AT TIME ZONE tz AT TIME ZONE 'UTC'`, 67 uses in analytics) → app SQL function `tz_wall_ms(ts, tz)` = `ts + utc_offset_ms(tz, ts)` (chrono-tz), then bucket. The result is "local wall time labelled as UTC", the same value Postgres returns.

### 3.2 Sharding (`src/sharding/`)

What it does: `MessageShardRegistry` keeps `MessageShard` rows (host, port, db, user, credential ref, `isActive`, `isMain`, `shardKey`) and `ShardTimeRange` rows (time windows → shard, no overlaps by a gist EXCLUDE). `MessageShardConnectionManager` (pg pools, read replicas, cache 30 s, max 10 pools) routes `Message`/`Attachment` reads and writes: the write shard is chosen by time range; reads fan out over every shard whose range overlaps the query; `workspaceShardIndex` (djb2 hash) chooses among shards. `ShardedMessageRepository` (2,762 lines) wraps every message query with fan-out, merge, sort and retry. ### 3.6 Locks and claims (input for P2.6/P2.7)

- One writer at a time. Every write transaction starts with `BEGIN IMMEDIATE` (writer lock at the start, so no deadlock on upgrade; `busy_timeout` waits). Read-only work uses reader connections (WAL snapshot).
- Do **not** hold the write lock across network I/O (Meta/Telegram/HTTP calls). Postgres code that keeps a `FOR UPDATE` transaction open during I/O must be split: claim (short tx) → do I/O → finish (short tx). This is the main design change of the port.
- Claim pattern for every `FOR UPDATE SKIP LOCKED` scan (smart-delay, sequence-dispatch, coexist-sync-run ×3, workspace-purge ×3, coupon, cart, ai-handover-bulk-run, broadcast-purge, chunked-purge, message-cleanup, response-sla, working-hours, sequence):
  ```sql
  BEGIN IMMEDIATE;
  UPDATE "T" SET "claimedAt" = :now, "claimToken" = :token
  WHERE rowid IN (SELECT rowid FROM "T" WHERE <due predicate> AND ("claimedAt" IS NULL OR "claimedAt" < :now - :lease)
                  ORDER BY <order> LIMIT :n)
  RETURNING *;
  COMMIT;
  ```
  The single writer makes the claim atomic; the lease replaces "skip rows another tx holds". Tables without a claim column keep the old "lock, process, release in one short tx" form, if the tx has no I/O.
- Advisory locks (22 sites, keys like `cf-names:<ws>`, `tpl-install:<ws>:<id>`, `mobile refresh familyId`): covered by `BEGIN IMMEDIATE` when the critical section is one DB transaction. Shared variant (`template-version`) → readers need no lock in WAL.

## 4. Migration plan for the Rust `db` crate

### 4.1 Files and runner

- One consolidated initial schema per part — not the 308 replayed migrations:
  `crates/db/migrations/0001_core.sql` (P2.3), `0002_messaging.sql` (P2.4, incl. forward-FK `ALTER TABLE … ADD COLUMN` for the 6 flow references), `0003_rest.sql` (P2.5, incl. `ContactOnSmartDelay.appointmentId`, rollups, FTS). Later changes: `0004_<name>.sql`, …
- Embedded with `include_str!` in a `const MIGRATIONS: &[(i64, &str, &str)]` (version, name, sql). No files on disk at run time.
- Table:
  ```sql
  CREATE TABLE IF NOT EXISTS "schema_migrations" (
    "version"    INTEGER PRIMARY KEY,
    "name"       TEXT NOT NULL,
    "checksum"   TEXT NOT NULL,          -- sha256 of the embedded SQL
    "appliedAt"  INTEGER NOT NULL        -- unix ms
  ) STRICT;
  ```
- Runner at start-up (writer connection, before the HTTP server binds):
  1. On a new empty file: `PRAGMA auto_vacuum = INCREMENTAL;` (must be set before the first table), `PRAGMA journal_mode = WAL;`.
  2. Read applied versions; if an applied version's checksum differs from the embedded SQL → refuse to start (migration was edited).
  3. For each pending version: `PRAGMA foreign_keys = OFF` (cannot change inside a tx) → `BEGIN IMMEDIATE` → `execute_batch(sql)` → `PRAGMA foreign_key_check` must return no rows → insert `schema_migrations` row → `COMMIT` → `PRAGMA foreign_keys = ON`.
  4. Set `PRAGMA user_version = <max version>` (cheap check for tools).
  5. Forward-only, same as the original (no down migrations).
- Table rebuilds (enum CHECK change, column type change) use the SQLite 12-step procedure inside one migration; the runner already turns FKs off.
- A schema test (P2.3–P2.5, class C) compares the created schema with a checked-in manifest generated from the snapshot: every table, column name, NOT NULL, default, FK, unique and partial index must exist (`pragma_table_info`, `pragma_index_list`, `pragma_foreign_key_list`).

### 4.2 Crate choice

State as last known to the analyst (mid-2026). P2.3 must re-check the current releases before it adds the dependency.

| Criterion | `libsql` (local only, `default-features = false, features = ["core"]`) | `turso` (Rust rewrite of SQLite) | `rusqlite` (`features = ["bundled", "functions"]`) |
|---|---|---|---|
| Engine | fork of SQLite ~3.45 (C) + libSQL extensions | new engine in Rust, file-format compatible | upstream SQLite 3.50.x (C), bundled |
| Vector search | native `F32_BLOB`, `vector_distance_cos`, DiskANN index `libsql_vector_idx` + `vector_top_k` | native vector functions; index support newer | none built in; app function (≈40 lines) for exact cosine; same `F32_BLOB` bytes |
| App-defined SQL functions (needed: `tz_wall_ms`, `lower_u`, `ilike`, `regexp_replace`, `vector_distance_cos`) | not exposed in the stable Rust API (verify) | own extension API, different | full: `create_scalar_function` with DETERMINISTIC / INNOCUOUS flags |
| SQL coverage needed here (556 FKs, partial + expression indexes, generated columns, triggers, upsert with WHERE, RETURNING, window functions, FTS5, STRICT) | full (SQLite 3.45 base) | partial in 2025–26 (gaps were in triggers, FK enforcement, some ALTER forms, FTS5); high risk for 258 tables | full |
| Async API | yes (tokio); local calls run inline on the async thread | yes, native async, MVCC "BEGIN CONCURRENT" | no; use 1 writer thread + reader pool via `spawn_blocking` (or `tokio-rusqlite`) |
| Binary size (estimate, measure with `cargo bloat`) | +2–3 MB (libsql-ffi + crate deps) | larger, pure Rust engine (unmeasured) | +1.0–1.5 MB (amalgamation with FTS5, JSON) |
| Memory | same page-cache model as SQLite; controlled by the same pragmas | own cache; fewer knobs | SQLite pragmas + `soft_heap_limit` |
| Maturity late 2026 | maintained, but Turso put new work into the Rust engine in 2025; upstream SQLite merges are slow | beta / early GA; fast-moving API | 10+ years, very wide use, tracks upstream SQLite |

**Recommendation: `rusqlite` with `bundled`.** Reasons: full SQL coverage for this schema, app-defined functions (needed for 5 parity-critical functions), the most mature option, the smallest binary, and the same memory controls. The only feature lost is the libSQL DiskANN index, which this app does not use (§1.9). The file stays a normal SQLite file; columns use the `F32_BLOB(1536)` type name and libSQL's byte layout, so a later move to `libsql` is a contained change. This differs from the tracker wording "libSQL embedded file" (P2.3) → the orchestrator records the choice in DECISIONS.md and tells the user.

Concurrency model: 1 writer connection (owned by a dedicated thread, jobs sent over a channel, every tx `BEGIN IMMEDIATE`) + 4 reader connections (pool). P2.6 jobs and HTTP handlers share the same writer.

### 4.3 Pragmas (RSS budget ≤ 200 MB for the whole binary)

| Pragma | Value | Why |
|---|---|---|
