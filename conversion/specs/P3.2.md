## 2. Rules and query patterns

- A repository function is a sync `fn(&Connection, ..) -> repo::Result<T>`. Reads run on a reader
  (`repo::read(db, |c| ..)`), writes on the writer (`repo::write(db, |tx| ..)`); a TS
  `db.transaction` is one `repo::write` around the whole operation. `repo::write` keeps the
  domain error (`Error::Message` / `NotFound` / `Coded`) and rolls back on any `Err`.
- Async functions (`purge_*`, `chunked_purge`, `delete_workspace_batch`) take `&Db` and run one
  short write job per chunk; they never hold a write transaction across a sleep.
- "now": time-dependent queries take `now: i64` (unix ms) instead of SQL `now()`.
- Ids are `i64` snowflakes (`repo::new_id()`, same layout as `packages/utils/src/id.ts`).
- **Workspace filter:** every query keeps the `workspaceId` scope of the TS (direct column, a join
  on `Inbox.workspaceId`, `Contact.workspaceId`, or an integration's `workspaceId`).
- **Pagination:** `utils::get_pagination_with_defaults` (limit 20 default, max 50; JS truthiness of
  `page`/`perPage` kept). Keyset cursors use `(col, id) > (?, ?)` row values (SQLite ≥ 3.15).
  `limit + 1` over-fetch where the TS does (`has_more`).
- **Ordering:** `ASC NULLS LAST` is written `col IS NULL, col ASC` (same order). Enum columns are
  never sorted alphabetically.
- **Soft delete:** `"deletedAt" IS NULL` in every live-row query (`Broadcast`).
- **Upsert targets:** the TS conflict target is kept 1:1, including partial-index targets
  (`ON CONFLICT (cols) WHERE channel = '<x>' DO NOTHING` for `AdsConversionEvent`), `DO UPDATE ...
  WHERE` guards (`ContactActivity`, `ContactState`, `AIEmbedding`, `AutomationThrottle`) and
  `ON CONFLICT DO NOTHING` without target (`AIHandoverBulkRun`: live + revision indexes).
  Never `INSERT OR REPLACE` (DECISIONS P2.5: skips delete triggers).
- **JSON columns:** `repo::Json` (compact `serde_json` text). jsonb operators map to SQLite JSON:
  `->>` (same syntax), `jsonb_set`/`||` → `json_set` (keeps explicit `null`, unlike `json_patch`),
  `-` → `json_remove`, `array_cat` / jsonb aggregation done in Rust inside the same write.
  `= ANY(array)` → `IN (SELECT value FROM json_each(?))` with one JSON text parameter.
- **Case-insensitive search:** `ilike(col, pattern)` app function (Unicode fold, `\` escape) with
  `utils::like_contains` / `escape_like_pattern`.
- **Time zones:** `queries::date_bucket::zoned_date_key` / `zoned_bucket_key` (zone is a bind value
  through `tz_resolve(?)`).
- **Money / numeric:** unbounded `numeric` sums (`AdsConversionEvent.value`) are summed exactly in
  Rust (`ads_conversion_event::decimal_sum`, scale = max input scale, like Postgres).
- **Row locks / advisory locks** (`FOR UPDATE`, `SKIP LOCKED`, `pg_advisory_xact_lock`) are not
  needed: the one SQLite writer serializes all write jobs. The functions stay (e.g.
  `contact_custom_field::lock_pairs`) so callers port 1:1.

## 3. Test port rules used

- Postgres integration tests → a fresh migrated SQLite temp file per test (instead of a rolled-back
  transaction); same inputs and assertions (`ported`). Two-connection races → two concurrent
  `repo::write` jobs (`adapted`: the writer serializes them; the asserted outcome is the same).
- Mocked-Drizzle unit tests → the observable effect of the asserted call shape on real rows
  (`adapted`): "joins X scoped to the workspace" = rows of another workspace are not returned;
  "where contains eq(col, v)" = rows with another value are not touched; "does not query" = empty
  result for empty input; "`limit(n+1)`" = `has_more` with exactly `n` rows; SQL text / bound param
  checks = the result the SQL produces (e.g. a bound time zone moves the day key).
- Loop mechanics of `purgeBroadcastRecipients` (mocked `Date.now`, mocked timeouts) drive
  `broadcast_purge::run_purge_loop` with an injected clock and chunk step.
- Names: `snake_case(describe > it)`; `test.each` rows expand with the row label.

## 4. Not-applicable (38 rows, reasons in the TSV)

- `timescale.test.ts` (TimescaleDB GUC), `connection-manager.test.ts`, `sharding-shared.test.ts`
  (shard pools / replicas / pg connection errors): the mechanics do not exist in one SQLite file;
  a sharded message lookup is a plain query on the main connection (P2.2 §3.2).
- Single cases that only a mocked client can produce (`RETURNING` without a row on an upsert, a
  settings row without its inbox under FK cascade, a release between two statements of one write),
  partition pruning, and one case that tests `workspaceRepository` (second half, P3.3).
