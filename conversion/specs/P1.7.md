## 1. Common rules (all 53 operations)

### 1.1 Auth and scope (`00-auth.test.ts`)

- Workspace token (`Authorization: Bearer cbx_ws_…`), same middleware order as
  P1.3 §1.1 / P1.6 §1.1.
- No / unknown token: **401** `INVALID_CHATBOT_TOKEN`
  `Invalid or missing workspace API token`, `defined: true`.
- Scope: `conversations.*` → `inbox` (12); `coupons.*` and `discountCodes.*`
  → `ecommerce` (24); `customFields.*` → `contacts` (5);
  `decisionConnections.*` and `decisionProfiles.*` → `automation` (12).
  Missing scope (also with the other three scopes): **403** `FORBIDDEN`
  `Token is not authorized for the '<scope>' scope`, `defined: true`.
- Read-only token: the 16 GETs pass; the 37 POST/PUT/PATCH/DELETE are **403**
  `FORBIDDEN` `Read-only token cannot perform this operation`. None of this
  unit's POSTs is on `READ_ONLY_TOKEN_ALLOWED_POST_PATHS`
  (`discountCodes.validate` and `decisionConnections.test` are refused too).

### 1.2 Errors

- Body `{defined, code, status, message, data?}`. Schema rejection: **422**
  `invalidRequestData` with `data.issues[].path`.
- `notFoundException` → 404 `notFound` with its own message; a
  `ChatbotXException` without a status → 400 with its own code and message;
  `validationException` → 422 `validation`. `defined` is true only when the
  code is in the route's error map.
- An `ORPCError` thrown with a code but without a status is **500** with that
  code and `defined: false` (`coupons.issueCoupon`, `coupons.markCouponUsed`).

### 1.3 Fixture extension (setup only)

`createInbox` (plain inbox, no integration), `createWhatsappChannel` /
`createMessengerChannel` (Inbox + `IntegrationWhatsapp` / `IntegrationMessenger`
with a plain-JSON `Oauth2AuthValue` in `auth`: the app reads that jsonb with a
raw `SELECT *` and does not decrypt it; `clientId` = `P107_META_APP_ID`),
`createContact` (Contact + ContactInbox rows with activity, routing and
referral columns + one Conversation with activity, assignment, SLA columns),
`createInboxTeam`, `addMember` (agent). Every other row comes from public
routes (`webchats.create`, `contacts.create`, `contacts.sendMessage`,
`flows.create`, `aiAgents.create`, `customFields.create`, …). No assertion
reads the database.

- Path id `{id}`: `zodBigintAsString` (digits; else 422 `invalidRequestData`, path `id`).
- Every operation first loads the conversation of the token's workspace
  (`assertConversationAccessForCaller`): unknown or foreign id → **404**

  beyond the shared `Idempotency-Key` middleware.
- Item shape (`listConversationsItemResource`, list view `full` and `get`):
  every `Conversation` column except `awaitingHumanReplyClosedAt`

### 2.3 Thread control by channel

- **WhatsApp** `POST https://graph.facebook.com/v23.0/<phoneNumberId>/thread_control`,
  `Authorization: Bearer <token>`, body `{messaging_product:"whatsapp", to:<sourceId>, action, metadata?, control_pass?}`
  (`recipient` instead of `to` for BSUID rows; `control_pass:{target_role}` only for
  `pass` with a role other than `escalation`; the note is trimmed and never sent with
  `release`). No retry. After success: `take` → `owned`, role `escalation`, event
  `taken`; `pass` → `standby`, role = target (default `escalation`), `passed`;
  `release` → `idle`, role null, `released`. `threadControlUpdatedAt` = request start,
  truncated to whole seconds. Meta error `code 2494191` on `take` → 200
  `notEscalation`, nothing stored. `sync`: WhatsApp has no owner query → `applied`
  with the stored snapshot, no call.
- **Messenger** `take` → `POST /v23.0/me/take_thread_control` `{recipient:{id:psid}, metadata?}`
  (answer must be `{success:true}`) → `owned`, role null, owner app id = the OAuth
  `clientId` (our app), `taken`. `pass` (no role or `ai_agent`) →
  `POST /v23.0/me/pass_thread_control` `{recipient, target_app_id: "622851382610562", metadata?}`
  → `standby`, `ai_agent`, owner app id = the Business-AI app, `passed`. `release` and a
  `pass` to another role are refused **before** any call → 400 `threadControlFailed`.
  `sync` → `GET /v23.0/me/thread_owner?recipient=<psid>`: our app → `owned`
  (`inboundReceived`, owner app id null); the Business-AI app → `standby`, `ai_agent`,
  owner app id kept, `threadOwnerExpiresAt` = Meta `expiration` (epoch s);
  no owner → `released`; an unknown app → partner standby.
- **Channels without a thread-control handler** (tested: webchat):
  take/release/pass → 400 `threadControlUnsupported`; `sync` → `applied` with the
  stored snapshot (the missing owner query is "cannot sync", not an error).
- Every applied state change: routing columns written on the ContactInbox (read back by
  `conversations.get`), a divider message (`messageType: activity`, `senderType:
  system`, `contentType: text`, `createdAt` = the transition time, text e.g. `This app
  took over this conversation`, visible in `contacts.listMessages`),
  `ContactInbox.lastMessageAt` bumped, `Inbox.threadControlSeenAt` touched, realtime
  `messageCreated` (the divider) and `contactInboxThreadControlUpdated`
  `{conversationId, ...snapshot}`.

### 2.4 Not tested (reasons)

- `unread` with two or more incoming messages (`agentLastReadAt` = the
  second-newest incoming message): no public route creates an incoming
  message, and messages live in separate shard databases the fixture does not
  write. Only the "fewer than two" path (null) is asserted.
- Mobile-JWT callers (member chat scope, email/phone masking, `assignedBy`):
  out of this unit, as in P1.6.
- Automation trigger events and `analytics:dashboard` events of every action
  (emitted in-process, read by other units), the assignment push
  (`notifyConversationAssigned`: no device token, Expo is never called), the
  response-SLA window recompute on assign / bot pause, the quick-reply
  follow-up cancel on `disableBot`, `Inbox.threadControlSeenAt`: no public read.
- Realtime `route` (gateway routing for assigned-scope agents): the owner
  socket receives every event; only `eventType` + `data` are asserted.
- WhatsApp BSUID recipients (`recipient` instead of `to`) and a refused
  Messenger `take`: not seeded.
- The same-second tie between two own thread-control actions (2.5): timing
  dependent; tests seed the earlier state one hour back instead.

### 2.5 Original behavior the Rust port must match

- `conversations.list` accepts `status` (validated as a JSON array of
  statuses) but **does not filter** by it; only `tags` filters.
- `tags`, `status`, `contactFilter` must be JSON-encoded strings; unparsable
  JSON and bracket notation are silently ignored (no filter, 200).
- `conversations.list` `perPage` has no upper limit (default 20); `sort` is
  accepted and ignored.
- `assignedId` values other than `u_…`, `t_…`, `unassigned` do not filter.
- `assign` to a non-member user → 400 `invalidAssignee`; to an unknown or
  foreign team → 404 `notFound`.
- `unread` with fewer than two incoming messages sets `agentLastReadAt` to
  null (also for a conversation without activity).
- `threadControl` `sync` on a channel without an owner query (WhatsApp,
  webchat) returns 200 `applied` with the stored snapshot; take/release/pass on
  webchat are 400 `threadControlUnsupported`.
- Our own routing times are truncated to whole seconds. Two own actions on the
  same thread within one second tie; the later one is still sent to Meta, but
  when its event has a lower precedence (`THREAD_CONTROL_EVENT_PRECEDENCE`:
  `passed` < `released` < `taken`) it is stale: not stored, no divider, and
  the response is `applied` with the earlier snapshot. Observed: take then
  pass in the same second → the pass is not stored; take then archive in the
  same second → the worker sends `release` to Meta but the thread stays
  `owned`.
- Messenger `release` and a `pass` to a role other than `ai_agent` are refused
  before any Graph call (400 `threadControlFailed`).

### 3.7 Original behavior the Rust port must match

- `issueCoupon` → **500** `couponIssueUnavailable` and `markCouponUsed` → **500** `couponNotIssued`, both `defined: false` with `data.reason` kept: the handlers throw `new ORPCError(code, {message, data})` without `status`, so oRPC uses 500 and the documented 409 / 404 never happen.

- `bulkCreate` and `import` on an **unknown or foreign** topic → 400 `couponTopicInactive` (not 404).
- `issueCoupon` on an unknown topic (valid contact) → 500 `couponIssueUnavailable` `topicUnavailable` (not 404).
- `updateTopic` silently ignores `name`/`description` once the topic ever had a coupon; a past `expiresAt` is allowed on update but not on create.
- `deleteTopic` takes archived topics only (active → 404 `Archived coupon topic not found`), returns 200 with the row.
- Export column "Used" holds the issue status, not the usage status; an empty export is `failed`.
- `listCoupons` legacy aliases: both forms at once → 422 on the canonical key.
- `discountCodes.delete` returns 200 with the deleted row; `create` is 200 (not 201).
