### 0.2 Facts that drive the design

1. **Redis kept its data across an app restart.** `docker-compose.yml:86-92` runs `redis:8-alpine` with the `cache-data:/data` volume (default RDB snapshots). An app deploy/restart never cleared Redis. In the new stack an in-memory map is cleared on **every** restart. So "survive restart" below means: the old stack kept it over an app restart. Rule from the orchestrator: if the loss changes observable behaviour, the use goes to SQLite.
2. **Redlock locks are auto-extended while `fn` runs.** `distributedLock.runExclusive` → `createRedlock({adapters:[1], key, ttl, retryAttempts: ceil(retryTimeout/200), retryDelay: 200, clockDriftFactor: 0.01}).using(fn)`; `using` → `executeWithAutoExtension` extends at 80 % of `ttl` (`redlock-universal/dist/index.js:443-520, 1061`). So the TTL only matters when a process dies. One attempt + `retryAttempts` retries 200 ms apart; then `LockAcquisitionError(key, attempts)` with message `Failed to acquire lock "<key>" after <n> attempts[: cause]`, `code = "LOCK_ACQUISITION_FAILED"` (`dist/index.js:18-28, 1120-1158`). Not re-entrant.
3. **No Redis pub/sub is used.** No `PUBLISH`/`SUBSCRIBE`/`PSUBSCRIBE`/keyspace events. Fan-out uses Streams (P2.6 event bus, P2.8 realtime). Cache invalidation is a direct `DEL` on the shared Redis; it does not need a message to other processes.
4. **The bloom filter is dead code.** `bloomFilter` / `bloomFilterFactory` (`packages/redis/src/bloom-filter.ts`, `index.ts:12`) have zero callers. `calcBloomFilterTtl` (`packages/analytics`) is only a TTL helper name. Not ported (2.11).
5. Unused API surface of `distributedStore` (no caller outside `packages/redis`): `putBoolean`, `getBoolean`, `putBooleanBatch`, `deleteKeyIfFieldValueMatches`, `zadd`, `zrem`, `zrangebyscore`; `sadd`/`smembers`/`rpush`/`lrange` are used only inside `cache-utils.ts` / `queue-utils.ts`. `cacheConnections.create/destroy`, `createRedisConnection`, `keys()` env (`REDIS_URL`, `REDIS_CACHE_URL`, `REDIS_SEQUENCE_URL`) have no Rust meaning. Not ported.
6. Lua scripts in use (all single-key, atomic in Redis): `INCR_IF_EXISTS`, `INCR_WITH_WINDOW`, `RESERVE_TIME_WINDOW`, `TAKE` (`distributed-store.ts`), `COMPARE_AND_SWAP_JSON`, `COMPARE_AND_DELETE_JSON` (`cas-store.ts`), `admitWithinLimit`, `decrementFloor` (`live-counter-scripts.ts`), `PRESENCE_HEARTBEAT_MANY` (`presence-store.ts`), `SET_SCORE`, `SET_MANY_IF_BUILT`, `SET_IF_BUILT` (`leaderboard-store.ts`), plus app scripts: Moosend `RATE_LIMIT_LUA`, heavy provider `RATE_LIMIT_LUA`, heavy-step outcome (3 scripts), `RAISE_LIVE_MAC_LUA` (`user-quota/service.ts:65`), `MARK_REALTIME_MEMBER_REVOKED_LUA`. In Rust each becomes one function that runs under one lock (volatile store) or inside one write transaction (durable store). Same atomicity.

### 1.2 Distributed locks (67 call sites)

Common semantics for every row (from 0.2 item 2):

- Data type / command: Redlock string key `SET key <random> NX PX ttl`, auto-extended, `DEL`-if-match on release.
- Atomicity: mutual exclusion per key. Cross-process visibility: yes in the old stack (builder + worker replicas). Survive restart: no — a dead process's lock expires after `ttl`; a new process starts with no locks.
- New stack: one process (P2.6: `flock` on the DB file). All HTTP handlers, jobs and crons run in it. An in-process keyed lock gives the same exclusion. **Replacement for all 67: `kv::LockMap::run_exclusive(key, ttl_s, retry_s, fn)`** (2.2). TTL is kept only as metadata (no expiry while held, the same as auto-extension). Retry window = `ceil(retry_s × 1000 / 200) × 200` ms; `retry_s` defaults to `ttl_s`; `0` = one try (fail fast).
- No row is needed only for multi-process safety: every row also guards concurrent tasks inside one process (job concurrency > 1, HTTP requests, crons that overlap their own interval). Keep all 67.
- Restart loss: none observable (old locks also died with their process).

"retry" column: `= ttl` means `retryTimeoutInSeconds` was not passed, so the caller waits up to `ttl` seconds.

### 1.3 Read caches: `withCache` (84 call sites) and invalidation (125 call sites)

Common semantics for every `withCache` row (`packages/redis/src/cache-utils.ts`):

- Data type / command: string `GET`/`SETEX` of `superjson.serialize(result)` under `sj:<key>`; per tag a set `tags:<tag>` (`SADD` the prefixed key, `EXPIRE tags:<tag> max(resolvedTtl, ttl)`).
- Default TTL 86 400 s. `ttlFor(result)` overrides the entry TTL per result. `null`/`undefined` results are not cached. Read or write errors fall back to the source function (never thrown).
- Atomicity: none (read-through, last write wins). Cross-process visibility: yes (builder and worker shared one Redis; an invalidation in the builder was seen by the worker). Survive restart: not needed — every source is the DB or a provider API; loss = one extra source call.
- **Replacement for all 84: `kv::Cache::get_or_load(key, opts, load)`** on `MemKv` (2.4), same key text, same TTL, same tags, same `ttlFor`, same "no `None`". Typed values (serde JSON bytes; no SuperJSON envelope, no `sj:` prefix).
- Exceptions: **C80** (`sharded-message-repository.ts:163`, shard time ranges) and its invalidation `sharded-message-repository.ts:152` — not needed (DECISIONS P2.2: sharding not used; one `Message` table). **C33/C59** take the TTL from the caller (`props.ttlInSeconds`); **C61** from `input.ttlSeconds`.

## 2. Rust design

### 2.1 Where: a new small crate `crates/kv` (`chatbotx-kv`)

- Reason for a new crate (not `crates/core`): `crates/jobs` needs the keyed lock now (P2.6 sequence consumer, `deferOnLockContention`), and `crates/core` (business logic) will depend on `jobs` to enqueue work. So the lock cannot live in `core` (dependency cycle). The durable store needs `chatbotx-db`. `kv` sits between them: `db ← kv ← jobs ← core ← api/rt/server`.
- Size estimate: ≈ 1 300 LOC (lock map 150, mem store 400, cache 200, presence 80, leaderboards 300, durable store 350, sweeper 80). Dependencies: `chatbotx-db`, `tokio` (`sync`, `time`, `macros`, `rt`), `serde`, `serde_json`, `tracing`. No new external crate.
- Alternative if the orchestrator prefers no new crate: the same modules as `chatbotx_db::kv`. Same API.
- Move `Clock` / `SystemClock` from `crates/jobs/src/clock.rs` to `kv::clock` and add a manual `TestClock`; `jobs::clock` re-exports them (no change for the P2.6 tests).
- One handle, built once at start and put in the app state:


### 2.2 `LockMap` (replaces `distributedLock`, the P2.6 interim map, and the 30 s NX locks of K20/K21)

```rust
pub struct LockOpts { pub ttl_secs: u64, pub retry_secs: Option<u64> } // retry None = ttl
pub struct LockMap { inner: std::sync::Mutex<HashMap<String, Arc<tokio::sync::Mutex<()>>>> }
pub struct LockGuard { /* key, entry Arc, OwnedMutexGuard, &LockMap */ }

impl LockMap {
    pub async fn acquire(&self, key: &str, opts: LockOpts) -> Result<LockGuard, LockAcquisitionError>;
    pub fn try_acquire(&self, key: &str) -> Result<LockGuard, LockAcquisitionError>; // retry 0
    pub async fn run_exclusive<T, E, Fut>(&self, key: &str, opts: LockOpts, f: impl FnOnce() -> Fut)
        -> Result<T, RunExclusiveError<E>> where Fut: Future<Output = Result<T, E>>;
    pub fn is_held(&self, key: &str) -> bool;   // K41 `distributedStore.exists(LOCK_KEY)`
    pub fn len(&self) -> usize;                  // tests: idle map is empty
}
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct LockAcquisitionError { pub key: String, pub attempts: u32 }
// Display: `Failed to acquire lock "<key>" after <attempts> attempts` (redlock-universal text)
pub fn is_lock_acquisition_error(err: &(dyn Error + 'static), key: Option<&str>) -> bool; // walks source()
```

- Acquire: under the std mutex, get or insert the per-key `Arc<tokio::sync::Mutex<()>>` and clone it; release the std mutex; then `try_lock_owned()` when the retry window is 0, else `tokio::time::timeout(window, lock_owned())`. Window = `ceil(retry_secs × 1000 / 200) × 200` ms; `attempts = ceil(retry_secs × 1000 / 200) + 1` (same numbers as `retryAttempts` / `retryDelay: 200`).
- Hold: while `fn` runs, with no expiry (Redlock auto-extension). `ttl_secs` is kept only for logs.
- Release (on `Drop` and on a failed acquire): drop the owned guard, then under the std mutex remove the map entry when `Arc::strong_count == 1` (only the map holds it; no holder, no waiter). Result: **an idle map is empty**; no sweeper; no idle memory.
- Order: tokio's mutex is FIFO (Redlock polling was unordered). Not observable.
- Not re-entrant (same as Redlock). Rule for Phase 3: never take the same key twice in one task; never call `acquire` inside a `db.write(|tx| …)` closure (that runs on the single writer thread).
- P2.6 integration (part of this unit's implementation): (a) `jobs::deferral::is_lock_acquisition_error` also accepts `chatbotx_kv::LockAcquisitionError` (additive; P2.6 types stay); (b) `SqliteSchedule::try_lock` (`crates/jobs/src/sequence/sqlite_schedule.rs:310-340`, an interim map whose lock **expires after `ttl` while still held**) uses `LockMap::try_acquire` and maps the error to `ScheduleError::LockAcquisition { key }`. This matches Redlock (no expiry while held).
- Memory: ≈ 200 B per held key; bound = concurrent holders (job concurrency sum + HTTP requests, ≤ a few hundred). Idle: 0 B, 0 wake-ups.

### 2.3 `MemKv` (volatile store with Redis-like methods)

- State: one `std::sync::Mutex<State>`; `State { entries: HashMap<String, Entry>, expiry: BTreeMap<(i64 /*expires_at_ms*/, u64 /*seq*/), String>, bytes: usize }`; `Entry { value: Value, expires_at_ms: Option<i64>, seq: u64 }`; `Value = Str(Box<str>) | Int(i64) | Hash(HashMap<String, String>)`. No `.await` while the mutex is held, so every method is atomic (the Lua guarantee).
- Methods (names follow `distributedStore` / `casStore`): `put(key, &impl Serialize, ttl_s: Option<u64>)` (ttl `None`/0 = no expiry, the `if (ttlInSeconds)` rule), `get::<T>` (malformed → `None`), `take::<T>`, `exists`, `get_all::<T>(&[key])`, `delete(&[key])`, `put_many`, `set_if_absent(key, &v, ttl_ms)` (SET PX NX), `get_raw`, `get_json`, `del`, `compare_and_swap`, `compare_and_delete` (2.10), `set_number(key, n, ttl_s)` (always writes), `set_number_if_not_exists(key, n, ttl_s) -> bool`, `get_number -> Option<f64>`, `increment_counter(key, delta, ttl_s: Option<u64>) -> Option<i64>` (delta 0 → `None`; missing key → `None`, no create; `EXPIRE` on **every** call when ttl > 0 — `INCR_IF_EXISTS_LUA`), `incr_with_window(key, ttl_s) -> i64` (TTL only when the result is 1), `incr_with_window_ms(key, window_ms) -> (i64, i64 /*pttl*/)` (K5), `claim_min_interval(key, interval_ms) -> u64 /*wait ms, 0 = claimed*/` (K6), `reserve_time_window(key, span_ms) -> i64` (`start = max(now, until)`, `until = start + max(0, ceil(span))`, TTL `until − now + 60 000` ms), `expire(key, ttl_s) -> bool`.
- Expiry: every read treats `expires_at_ms <= now` as absent and removes it (lazy). Correctness does not depend on the sweeper.
- Bounds (config): `max_entries` 50 000, `max_bytes` 4 MiB (estimate = key + value + 96 B). Over a bound on insert: (1) drop expired entries from the front of `expiry`; (2) evict the entries that expire soonest; (3) then entries without TTL by insertion order. A `warn` (at most once per minute) when (2)/(3) evict live entries.
- Sweeper (one task for `MemKv`, `Cache`, `Presence`, `Leaderboards`): sleep until `max(earliest expiry, last sweep + 60 s)`; when no entry has a TTL, wait only on a `Notify` (no timer). An insert notifies only when its expiry is earlier than the planned wake-up.

### 2.4 `Cache` (replaces `withCache`, `invalidateCacheKeys`, `invalidateCacheByTags`, `BaseService.invalidateCacheTags`)

```rust
pub struct CacheOpts<T> {
    pub ttl_secs: u64,                                   // default 86_400
    pub ttl_for: Option<fn(&T) -> Option<u64>>,          // per-result TTL; None = ttl_secs
    pub tags: Vec<String>,
    pub dynamic_tags: Option<fn(&T) -> Vec<String>>,
}
impl Cache {
    pub async fn get_or_load<T, E, Fut>(&self, key: &str, opts: CacheOpts<T>, load: impl FnOnce() -> Fut)
        -> Result<Option<T>, E>
        where T: Serialize + DeserializeOwned, Fut: Future<Output = Result<Option<T>, E>>;
    pub fn invalidate_keys(&self, keys: &[&str]);
    pub fn invalidate_tags(&self, tags: &[&str]);
}
```

- Value = `serde_json` bytes of `T`. A hit deserializes into the same Rust type, so `chrono` dates come back as dates (the SuperJSON reason disappears). A hit that does not deserialize = miss (TS: malformed envelope → source).
- `load` returns `None` → not stored (TS `null`/`undefined`). `load` errors propagate (TS: `fn()` errors propagate).
- Tags: `tags: HashMap<String, HashSet<String>>` (tag → keys) and `key_tags: HashMap<String, Vec<String>>`. When an entry expires, is evicted or invalidated, its memberships go too. So a tag set needs no TTL of its own; `invalidate_tags` removes exactly the live entries with that tag. This keeps the intent of `tagTtl = max(resolvedTtl, ttl)` (a short negative entry never removes a longer sibling from tag invalidation).
- No `sj:` prefix and no legacy key: one process, one namespace, empty at start.
- No single-flight (TS has none). Same number of source calls under a cold burst.
- Bounds: `max_entries` 20 000, `max_bytes` 8 MiB, same eviction order as 2.3. Realistic idle content for one workspace: < 1 MiB.

### 2.6 `Presence` (K42)

- `HashMap<String /*key*/, HashMap<String /*member*/, i64 /*expires_at_ms*/>>` under one mutex.
- `heartbeat_many(key, members, ttl_ms) -> Vec<String>`: empty `members` → `[]`, no work. Prune members with `expires ≤ now`; for each member: if not present (after the prune) add to `newly_live`; set `now + ttl_ms`. Return order = input order.
- `live_members(key, limit) -> Vec<String>`: prune `≤ now`; order by expiry descending, ties by member descending (Redis `ZREVRANGEBYSCORE` tie order); first `limit`.
- Key TTL (`PEXPIRE ttl`) is implied: every member expires ≤ last heartbeat + ttl; the sweeper removes empty keys.
- Memory ≈ 100 B per live member; bound = workspace members (`PRESENCE_SCAN_LIMIT` 200 per read).

### 2.7 `Leaderboards` (K43)

- Per leaderboard id: `Board { rank: Option<Ranking>, rebuild: Option<Ranking>, stats: Option<HashMap<String, i64>>, top: Option<(String, i64 /*expires*/)>, rank_expires_at: i64, stats_expires_at: i64 }`; `Ranking { by_member: HashMap<Box<str>, i64>, order: BTreeSet<(Reverse<i64>, Reverse<Box<str>>)> }`. `rank: None` = "not built" (replaces the `-inf` sentinel `_`).
- Rank value stays `score × 100 000 000 + (99 999 999 − tieSeconds)` (exported `encode_rank_value`, `decode_rank_value = floor(v / 1e8)`, `tie_seconds_since`). Stored as `i64` (exact; TS doubles are exact below 2^53, so results are equal).
- Methods 1:1 with `leaderboardStoreFactory`: `set_score` (`SET_SCORE_LUA`: write the rebuild set if it exists; `false` when not built; `totalPoints += newScore − oldScore`; `participants += 1` and `new:<dayKey> += 1` when `isNew`; refresh 30-day TTL of rank and stats), `set_members` (only when built; `None` removes), `set_member`, `remove_member`, `top(limit, offset)` (`None` when not built and `offset == 0`, else `[]` when empty; descending; ties by member descending), `ranks_of` (`built` + 1-based rank; O(n) walk, ≈ 20 µs for 10 000 members), `stats_many(ids, dayKey)`, `replace_ranking(pages, stats, dayKey)` (build a new `Ranking`, swap in one step, replace stats, drop `top`, rebuild = `None`), `read_top_cache`/`write_top_cache(ttl)`, `drop`, `memory_usage(id) -> Option<usize>` (estimate), `used_memory() -> usize` (sum of the volatile stores' estimates; replaces `INFO memory` for `maintenance.ts:64-68`).
- Test helper `begin_rebuild(id)` (the frozen test writes the rebuild key directly with `ZADD … -inf _`).
- Memory ≈ 100 B per participant with 19-digit ids (both indexes); 10 000 participants ≈ 1 MB.

### 2.8 Live quota counters on `DurableKv` (K25–K28)

- Key `${label}-live:${id}` = one `kv_entry` row, `value` = JSON object `field → string` (strings, so corrupt values like `"1.5"`/`"bad"` behave as in Redis).
- Each method = one write transaction on the writer thread (atomic like the Lua scripts; the writer serializes concurrent callers):
  - `hget`, `hmget` (reader connection), `hsetnx`, `hset(&[(field, value)])`, `hincrby` (non-integer field → error, as Redis), `del`.
  - `admit_within_limit(key, field, limit: Option<f64>) -> Result<Admit { status: Admitted | Refused | Missing, value: i64 }, KvError>`: field missing → `Missing, 0`, no write; field not an integer → `Err("ERR live counter field is not an integer")`; limit not an integer → `Err("ERR live counter argument is not an integer")`; `n = max(0, current)`; `limit ≥ 0 && n + 1 > limit` → `Refused, n`, no write; else write `n + 1` → `Admitted, n + 1`. `None` limit = −1 = unlimited.
  - `decrement_floor(key, field, count: f64) -> Result<Option<i64>, KvError>`: field present and not an integer → field error; `count` not an integer → argument error (this order); field missing → `None`, no write; else write `max(0, current − count)`.
  - `raise_live_mac(key, period_field, period, field, value)` (`RAISE_LIVE_MAC_LUA`).
  - `scan_prefix(prefix)` for K28 (primary-key range scan).
- Integer rule (`toint` in Lua): parse after trim as Lua `tonumber` does (decimal, exponent, `0x` hex); integer when finite and `n == floor(n)`; write back as an integer string.
- Cost: one short write per admission/increment (≈ 30–80 µs). Volume = messages; acceptable for one person.

### 2.9 `DurableKv` (SQLite) — the durable list of 1.6

Migration `crates/db/migrations/0005_kv.sql` (next free number after `0004_rest.sql`):

```sql
CREATE TABLE "kv_entry" (
  "key"           TEXT    NOT NULL PRIMARY KEY,
  "kind"          INTEGER NOT NULL,   -- 0 string/JSON, 1 hash (JSON object), 2 list (JSON array)
  "value"         TEXT    NOT NULL,
  "expiresAtMs"   INTEGER             -- NULL = no expiry
) STRICT, WITHOUT ROWID;
CREATE INDEX "kv_entry_expiresAtMs_idx" ON "kv_entry" ("expiresAtMs") WHERE "expiresAtMs" IS NOT NULL;
```

- Reads on a reader connection: `… WHERE "key" = ? AND ("expiresAtMs" IS NULL OR "expiresAtMs" > ?)`.
- Writes: one `db.write(|tx| …)` per method (`BEGIN IMMEDIATE`, one or two statements, no I/O inside). An expired row counts as absent inside the closure. `now` is read from the `Clock` before the call (the TS scripts also took `Date.now()` as an argument).
- Methods: the `MemKv` set that the durable rows use — `put`, `get`, `take`, `exists`, `delete`, `set_if_absent`, `set_number`, `set_number_if_not_exists`, `increment_counter`, `expire`, `reserve_time_window` (K7), `get_all` (K8 `MGET`), `raise_number(key, n, ttl_s) -> i64` (K44 revoke: write only when `n > existing`; return existing or 0), list `push(key, v, ttl_s)` / `range` / `clear` (K16; `EXPIRE` on every push, as `simpleQueue.enqueue`), hash `get_all_fields` / `merge(fields: &[(k, Option<Value>)], ttl_s)` (K15; `None` = untouched, `Some(Null)` written as `"null"`) plus 2.8, CAS (2.10), and `update_json(key, |Option<Value>, now| -> Update)` for the heavy-step scripts (K17; `Update::Keep | Write(Value) /*KEEPTTL*/ | WriteTtl(Value, ms) | Delete`, with a return value).
- Every write method also has a `*_in(&mut WriteTx, …)` form so Phase 3 can put a business row and its marker in one transaction (optional improvement; default keeps the TS order).
- Sweeper (separate task): delete expired rows in batches of 500 (`DELETE … WHERE "key" IN (SELECT "key" FROM "kv_entry" WHERE "expiresAtMs" <= ? LIMIT 500)`, one short transaction per batch); wake at `max(MIN("expiresAtMs"), last + 300 s)`; no timer when no row has an expiry.
- RAM: only the shared SQLite page cache (P2.3 budget). Rows are small, except K15 (AI context, may hold base64 images) — better on disk than in RAM.

### 2.10 CAS semantics (`casStore`; K11, K13, K14)

`trait CasStore { set_if_absent, get_raw, get_json, del, compare_and_swap, compare_and_delete }`, implemented by `MemKv` and `DurableKv` (tests inject either).

- `set_if_absent(key, &v, ttl_ms) -> bool`: SET PX NX; an expired key is absent; a second write can neither overwrite nor extend.
- `compare_and_swap(key, expected: Option<&Map>, next: &Value, ttl_ms) -> bool`: `None` → the key must be absent (create-only); `Some(e)` → the key must exist and every `(field, value)` of `e` must equal the current field by the Lua `cjson` rule: numbers compare by value (`1 == 1.0`), strings by bytes, booleans, `null == null`; a missing field never equals anything (also not `null`); an object or array in `expected` never matches (Lua tables compare by identity). On success write `next` with a new TTL `ttl_ms`.
- `compare_and_delete(key, expected) -> bool`: same match; delete on success.
- `get_json` → `None` when absent or not valid JSON.

### 2.11 Pub/sub, bloom filter, seen-sets

- No generic pub/sub module. No Redis pub/sub existed (0.2 item 3). Cache invalidation is a direct call. Realtime fan-out is P2.8 (`tokio::sync::broadcast`, one sender per process); job events are P2.6 (`broadcast`, capacity 1024).
- Bloom filter: not ported (no caller). If Phase 3 needs a "seen" set, use a table with a `UNIQUE` index and `INSERT … ON CONFLICT DO NOTHING` (exact; no false positives; survives restart).

## 4. Doubts and risks

1. **Restart now clears volatile state; Redis did not** (0.2 item 1). The rule "observable loss → SQLite" puts 15 groups (19 rows) in `DurableKv` (1.6). The orchestrator should confirm the borderline ones: K35/K36 (OAuth state and install intent, 5–15 min windows), K40 (scan cursors: only repeated work), K14 (VoIP offer/answer ≤ 55 s, kept durable only so one CAS store owns `voip:*`). Volatile choices that change something small on restart: K12 dispatch windows (one batch may start early; same as today's fail-open), K4 trigger loop guard (≤ 20 extra runs once), rate limit counters (reset).
2. **Locks that also protected against a second process.** All 67 locks become in-process. This is safe only while exactly one process uses the DB file (P2.6 `flock` guard). Running a second binary on the same file (for example a CLI command that runs jobs) must take the same `flock` or must not run handlers. P2.6's interim `SqliteSchedule::try_lock` lets a held lock expire after `ttl`; P2.7 replaces it with `LockMap` (no expiry while held), which matches Redlock auto-extension but means a hung handler holds its key until it returns — the same as Redlock with a live process.
3. **Single writer thread vs. locks.** A handler that holds a `LockMap` key while it waits for `db.write` is fine; a `LockMap::acquire` **inside** a `db.write` closure would block the writer for up to the retry window and stall every write. Code review rule for Phase 3 (2.2). Durable kv ops add short writes on hot paths: live counters (per message), comment pacing (per live comment, thousands per minute during a broadcast), `comment-live-post` puts. Estimate ≤ 100 writes/s at peak for one person; each < 100 µs. Watch in Phase 5.
4. **Live quota counters (K25–K28) on SQLite.** The original treats them as rebuildable from the DB, but on the community edition `syncUserQuota` is not scheduled (cloud-only), so the user-level `mac` and `monthlyBotMessages` live fields are the only copy. Durable is the safe choice. Alternative for the user: volatile + reseed (Redis-eviction semantics) with the usage display dropping after each restart. A simpler Phase 3 option: compute usage from the SQLite source tables and drop the live layer; that changes business code and is out of this unit.
5. **AI context (K15) can be large** (history with base64 images). Durable is required (summary not rebuildable). Each `merge` rewrites the JSON object; with ≤ `MAX_CONVERSATION_HISTORY` messages this is small for text, but image parts can make rows of several MB. Consider storing image parts by reference in Phase 3 (no change in P2.7).
6. **Rate limits under a flood.** The volatile store has `max_entries` 50 000. An unauthenticated flood on per-IP pre-auth buckets (`workspace-token-preauth-rate-limit`, 600 / 10 s) can fill the map; eviction removes the soonest-expiring counters first, which can reset an attacker's counter early. Redis had no such bound (memory only). Option: a separate, larger bound for rate-limit keys (they are ~100 B each; 200 000 = 20 MB worst case). Decide in implementation; default as specified.
7. **Cache staleness the UI depends on.** TTLs are kept exactly (C-rows). Invalidation becomes immediate in one process, which is fresher than before. `events/base-cache` (K22) loses its RAM tier (5 s / 60 s): reads now see `updateCache` at once instead of after up to 60 s. No test pins the old delay (`evaluator-filtered-cache.test.ts` tests filtering only).
8. **`simpleQueue` TTL quirk (K16).** `enqueue-message.ts:120` passes `timing.ttlSeconds * 5000` to `expire(key, seconds)` (comment says "keep the key longer than process job"). That is 5 000 × the debounce in seconds (likely meant ms). Kept exactly for parity; flag for the Phase 3 owner.
9. **Lua `cjson` comparison edge cases** (2.10). Expected values that are objects/arrays never match; `null` does not match a missing field; numbers compare numerically. The Rust CAS must copy this, or VoIP fence checks (K13) could accept a swap that Redis refused.
10. **Leaderboard ranks are O(n).** `ranks_of` walks the ordered set (Redis `ZREVRANK` is O(log n)). For 10 000 participants ≈ 20 µs per id; for very large live leaderboards consider an order-statistic tree later. Tie order (member descending) must match Redis for equal rank values (equal only when score and tie second are equal).
11. **Moosend fail-closed / TURN fail-open / trigger circuit** are behaviours on store failure. With an infallible in-memory store these branches are dead code in Rust; the Phase 3 ports keep them only if the T71/T72/T78 decision keeps the failing-fake tests.
12. **Durable sweeper vs. reads.** Correctness never depends on the sweeper (reads filter `expiresAtMs > now`); the sweeper only frees space. A clock jump backwards can keep rows longer; a jump forwards expires them early (Redis has the same dependency on server time).
13. **Default plan entitlements (K27)** are written outside this repository (private billing worker, cloud). On community the read always returns `None`; if the cloud edition is ever ported, that writer needs a `DurableKv` key or a table.
14. **Count method.** 475 call sites were found by `rg` plus multi-line and injected-store searches (method list in 0.3). A call through a new alias that none of these patterns match would be missed; the porter of each Phase 3 unit should `rg -n "@chatbotx.io/redis|getRedisConnection"` in its files and check this list.
