# P3.5 — auth + axum API skeleton (porter spec)

Unit: `packages/auth`, the builder auth routes and middleware, workspace API tokens, scopes, and an axum router with oRPC-compatible error JSON in `crates/api`. Goal: the P1 auth-matrix parity tests (`conversion/parity/tests/*/00-auth.test.ts`, `p1-02-ads-ai/ads-auth.test.ts`) pass against the Rust server.

## 1. Slices

The unit is too large for one batch (better-auth server 990 lines + 21 test files, workspace-token middleware with mobile and MCP OAuth principals, ~30 route-scope test files, a Rust parity stack). Orchestrator-delegated, recommended option: cut it in slices, each with a stage 1 / stage 2 commit pair.

- **P3.5a — token rules and error JSON (this batch).** `token-scope`, the scope registry, `authorize-workspace-access` (read-only allowlist, owner quota gate), `ChatbotXException` (API-layer subset), oRPC error body and `commonApiErrors`. 4 frozen test files, 31 tests.
- **P3.5b — workspace-token middleware + route table.** `workspace-token-auth.ts` (bearer / `?token=`, SHA-256 token hash, `workspace_api_token` repo lookup, deletion-scheduled gate, read-only gate, owner gate, rate limits), the public route table (method, path, scope per operation, generated once from the oRPC router), the `*-public-scope` and `workspace-token-*` builder tests, axum wiring in `crates/server`. Unported operations answer after auth (see §4).
- **P3.5c — Rust parity stack.** `conversion/parity/stacks/rust/` (compose, `fixtures.ts` writing the SQLite rows with `node:sqlite`, `run-rust.sh` modelled on `run-original.sh`); auth-matrix parity run.
- **P3.5d — sessions (`packages/auth`).** better-auth email/password, sessions, magic link, generic OAuth, provisioning, signup gate, tenant context; the 21 `packages/auth/__tests__` files and the builder auth route tests.
- **P3.5e — mobile and MCP OAuth principals.** `mobile-auth`, `mcp-resource`, mobile JWT middleware, OAuth consent.

Test map: `conversion/specs/P3.5-test-map.tsv` (P3.5a: 31 rows over 4 frozen files, 30 ported, 1 adapted; P3.5b: 176 rows over 25 files, 62 ported, 69 adapted, 45 not-applicable).

1. `ChatbotXException` lives in `crates/api` for now; the business port can move it to `crates/core`.
2. `null` and `undefined` token scopes are both `None` (marked `adapted`).

## 4. Open points for later slices

- Unported operations (P3.5b): after auth passes, the route answers `404 { defined: false, code: "NOT_FOUND", message: "Operation not ported yet" }` (status < 500 and not 401/403, so the auth matrix "passes auth" cases hold; the business parity tests stay red until P3.6+).

## 5. Stage 2 state (P3.5a)

- All P3.5a items are real; no `todo!()` in `crates/api`.
- `OrpcError::new(code, status, message)`: a common code gets its declared message/status and `defined: true`; another known oRPC code gets oRPC's default status and message; an unknown code gets 500 and the code as message (`defined: false`). `IntoResponse` writes the JSON body with `content-type: application/json`.
- Result on the PC: `cargo test -p chatbotx-api --no-fail-fast` → 38 passed, 0 failed (31 P3.5a + health + unit tests). clippy `--all-targets --no-deps -D warnings` and fmt clean.
- Not done yet: P3.5b–P3.5e (see §1). The router in `crates/server` is unchanged (health + realtime); no auth-matrix parity run yet (needs P3.5b and P3.5c).

## 6. P3.5b — workspace-token middleware + route table

| TypeScript | Rust (`chatbotx_api::…`) |
|---|---|
| `middlewares/workspace-token-auth.ts` `workspaceTokenAuthMidddleware` | `auth::authenticate_workspace_token(deps, TokenAuthRequest, &mut res_headers)` |
| `orpc.ts` `requireTokenScope`, `workspaceTokenAuthAPIForScope` | `auth::{require_token_scope, authorize_workspace_token_for_scope}` |
| `extractBearer`, `hashToken`, `getGuestClientIp`, `isWorkspaceScheduledForDeletion`, `isMobileAccessTokenCandidate` | `auth::{extract_bearer, hash_token, guest_client_ip, is_workspace_scheduled_for_deletion, is_mobile_access_token_candidate}` |
| business services the middleware calls | trait `auth::WorkspaceTokenDeps` (+ `WorkspaceQuota`); production impl `auth::LiveAuthDeps` (SQLite + `kv.mem` rate counters) |
| `routers/public.ts` (`publicRouter`) + `app/api/[[...rest]]/route.ts` | `routes::{PUBLIC_ROUTES, match_route, handle_public_request, public_api_router}` |

- Route table: `crates/api/src/routes/table.rs`, generated by `conversion/tools/route-table-gen/gen.py` from `public-ops.json` (the 811 operations of the original `/api/spec.json`, read from the original parity stack on 2026-11-13: operationId, method, path, `x-mcp.scope`) and a scan of `apps/builder/src` for the source module of each operation. 801 workspace-token routes (12 with two scopes), 5 channel-token routes (`/v1/channels/api/*`), 5 mobile-user routes (`me.*`).
- Matching: same segment count; a literal segment wins over `{param}` at the same position; params are percent-decoded; a trailing `/` is ignored. No match (path or method) = `404 text/plain "Not found"`, like the original handler.
- After auth, every operation answers `404 {defined:false, code:"NOT_FOUND", status:404, message:"Operation not ported yet"}` (§4). A rate limit adds `Retry-After`.
- `crates/server` now opens the database and the kv stores always (not only for realtime) and merges `public_api_router(LiveAuthDeps)`; `isCloud()` = `NEXT_PUBLIC_EDITION=cloud`.

Differences (P3.5b):

1. `LiveAuthDeps`: the owner quota gate never blocks (the quota services are the business port, P3.6+); no token lookup cache (the original caches `findWorkspaceByTokenHash` in Redis; SQLite reads are cheap).
2. Mobile access tokens and MCP OAuth tokens are not verified yet (P3.5e): `mobile_api_audience()` is `None`, `verify_mcp_access_token` answers "not valid" (401 `INVALID_CHATBOT_TOKEN`).
3. Channel-token (`/v1/channels/api/*`) and mobile-user (`/v1/me*`) routes run no auth yet and answer "not ported" (P3.5e / channel domain).
4. Tests: the `*-public-scope` scope-wiring tests read the route table (scopes of a module's routes) instead of the mocked builder calls; "passes the real route" = passes auth; 45 handler tests are `not-applicable` here and belong to the domain ports.

Stage 2 result (PC): `cargo test -p chatbotx-api -p chatbotx-server --no-fail-fast` → api 172 passed (131 P3.5b + 38 P3.5a/health + 3 new unit tests), server tests pass; clippy `--all-targets --no-deps -D warnings` and fmt clean.

## 7. P3.5c — Rust parity stack

- `run-rust.sh` (same options as `run-original.sh` minus `--update-snapshots`): `cargo build --release -p chatbotx-server` on the PC, fake-upstream image when missing, then `docker compose -p parity-rust` with `harness.compose.yml` + `stacks/rust/compose.yml`: mailhog, fake upstream, `server` (the binary mounted read-only into the pinned `node:24.22.1-trixie-slim` image; realtime on), Caddy edge `app` (`/ws/*` stripped to the same server).
