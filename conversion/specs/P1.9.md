## 1. Common contract (all 53 operations)

### 1.1 Auth (`workspaceTokenAuthAPIForScope(scope)`, `apps/builder/src/orpc.ts:208-222`)

All checks run before input validation:

1. No bearer and no `?token=` -> **401** `{defined:true, code:"INVALID_CHATBOT_TOKEN", status:401, message:"Invalid or missing workspace API token"}`.
   An unknown `cbx_ws_` token -> the same 401. The deprecated `?token=<cbx_ws_…>`
   query parameter still authenticates.
2. Read-only token on any POST/PUT/PATCH/DELETE -> **403**
   `{defined:true, code:"FORBIDDEN", message:"Read-only token cannot perform this operation"}`.
   This includes the read-shaped POSTs `flows.validate` and
   `inboundWebhooks.previewMapping` (not on `READ_ONLY_TOKEN_ALLOWED_POST_PATHS`).
   Read-only tokens pass auth on every GET.
3. Scope: `scopes === null` = all scopes, else the route scope must be listed,
   else **403** `{defined:true, code:"FORBIDDEN", message:"Token is not authorized for the '<scope>' scope"}`.

| Namespace | Scope |
|---|---|
| flows, igComments, igStories | `automation` |
| folders | `contacts` |
| googleAds | `ads` |
| inboundWebhookChannels, inboundWebhooks | `integrations` |
| inboxTeams | `inbox` (route lives under `apps/builder/src/enterprise/`, but it is **not** edition-gated: it works on the community edition) |

Covering test: `00-auth.test.ts` (all 53 operations: no token, unknown token
(9 samples), wrong scope with the exact message, a token with every other
scope of the unit, a token with only the route scope passes, read-only on
writes / reads, `?token=`).

### 1.2 Errors

- Input schema failure (path, query or body) -> **422**
  `{defined:true, code:"invalidRequestData", status:422, message:"Input validation failed", data:{issues:[{path,message,code,…}]}}`.
  Tests compare `code`, `status` and the issue `path`s (dotted; `[]` = `""`).
- `notFoundException` -> `notFound`/404, `validationException` -> `validation`/422,
  other `ChatbotXException` -> its own code/status. `defined` is `true` only
  when the route declares the code (see per-operation notes, e.g. `flows.create`
  folder 404 and `flows.export` 409 are `defined:false`).
- `FlowAuthoringException` (flow compile / graph validation) -> **422**
  `{defined:false, code:"invalidRequestData", status:422, message:"<path>: <message>; …", data:[{path, code, message, hint?, candidates?, capability?}]}`
  (`apps/builder/src/orpc.ts:98-104`): `data` is a bare array, not `{issues}`.

### 1.3 Paging (`publicListRequest`, `lib/public-api/list.ts`)

`page` ≥ 1 (default 1), `perPage` 1..max (default 50); bad values -> 422.
`pageCount = ceil(total / perPage)` — **0** for an empty list.

### Receiving endpoint `POST /api/hooks/<token>` (Next route, not oRPC)

Body of every answer is JSON, `Cache-Control: no-store`. Error body `{accepted:false, code, message}` (codes UPPER_SNAKE). Check order:

1. token not `^iwh_[A-Za-z0-9_-]{32,64}$` → 404 `NOT_FOUND` "Webhook not found" (no rate-limit count).
2. per client address (first `X-Forwarded-For` hop, else `x-real-ip`, else one shared `unknown` bucket) fixed 10 s window: 300 (unknown address: 1500) → 429 `RATE_LIMITED` "Too many requests", `Retry-After` = seconds to the next window.
3. body > 256 KiB (declared or streamed) → 413 `PAYLOAD_TOO_LARGE` "The request body is too large" (before the token lookup, so also for an unknown token).
4. token unknown → 404 `NOT_FOUND`.
5. workspace owner blocked (cloud only) → 403 `WORKSPACE_BLOCKED`; workspace scheduled for deletion / purged → 410 `WORKSPACE_UNAVAILABLE`.
6. `!active || inboxResolution IS NULL` → 403 `WEBHOOK_INACTIVE` "This webhook is not active".
7. per webhook 600 / 10 s → 429 `RATE_LIMITED`.
8. body not a JSON object/array, or not jsonb-storable (NUL, lone surrogate, depth > 64) → 400 `INVALID_JSON` "The body must be a JSON object or array" (empty body, `42`, `"text"`, `null` included). Content-Type is ignored.
9. `Idempotency-Key` (trimmed; blank = none) > 255 → 400 `INVALID_IDEMPOTENCY_KEY` "Idempotency-Key is too long".
10. store the request (+ `requestCount + 1`, `updatedAt` unchanged) → 202 `{accepted:true, requestId}`; same key on the same webhook → 200 `{accepted:true, duplicate:true}` (no new row, counter unchanged; the key is per webhook, any body).
11. any thrown error → 500 `SYSTEM_ERROR` "Please retry".

Other methods (GET, PUT, PATCH, DELETE, OPTIONS) → 405, empty body, `Allow: POST`, `Cache-Control: no-store`.

Tokens are looked up through a 10 s Redis cache (`inbound-webhooks:intake:<sha256>`), invalidated by tag on every change, so a regenerate/delete/deactivate takes effect at once in practice and within 10 s at worst.

### Worker processing (default queue `processInboundWebhookRequest`)

Claim (received → processing, `attempts + 1`) → webhook inactive → `skipped/webhookInactive` → resolve inbox (`inbox` mode: the inbox must be `connected`; `payload` mode: read the identifier, look it up by the channel's strategy) → skip reasons `missingInboxIdentifier` (path gave nothing) / `inboxNotFound` / `inboxAmbiguous` / `inboxDisconnected` (inboxId stays null) → find the contact by the **first** usable identity in the fixed order channelUserId, phone, email, fullName (never the next one) on that inbox only → `missingIdentifier` / `contactAmbiguous` (two contacts with that full name) / `contactNotFound` (no creation identity for the channel; inboxId is set) → create (Contact + ContactInbox `source: inboundWebhook` + Conversation; name = full name split, mapped first/last name laid over it) under a per-inbox lock → write mapped fields (rejected ones become `fieldErrors`, the rest are written) → run actions in order, checkpointing each → `processed`, or `completedWithErrors` when any field error or a non-succeeded action. Full-name match collapses ASCII whitespace runs and trims, but is **case-sensitive**.

Actions observed: `addTag`/`removeTag` (contact tags), `setCustomField` O01 / `clearCustomField` (contact custom fields; the action runs after the mapped fields, so it wins), `startAnotherFlow` (published + active flow → the flow's send step reaches the API channel callback as a signed `message_created` envelope; a draft-only flow → `skipped/flowInactive`), `transferConversationToHuman` (conversation `botEnabled` → false).

### Untested (with reason)

- 403 `WORKSPACE_BLOCKED`: needs the cloud edition (owner quota); parity runs community only.
- 410 `WORKSPACE_UNAVAILABLE`: needs `Workspace.scheduledDeletionAt`; the workspace row is cached by the app (`workspaces:*`, no TTL a test can wait for), and scheduling deletion has no public HTTP path, so a direct DB write would not be seen.
- Per-webhook 600 / 10 s limit: needs > 600 accepted deliveries (each a row + a job) in one window; too heavy for the shared runner.
- 500 `SYSTEM_ERROR` and the outbox re-dispatch cron (`received` older than 2 min, lease 15 min, abandon after 24 h), request retention purge (30 days), `failed` status (business error on the final attempt): need fault injection or long waits.
- `skipped/webhookInactive` at worker time (deactivated between accept and processing) and `inboxDisconnected` / `inboxAmbiguous` / `unsupportedInboxIdentifier` at delivery time: race or need a disconnected/duplicated inbox that the public API cannot make deterministic.
- `notifyAdmins: true` of `transferConversationToHuman`: only logs in the original.
- Pre-auth bucket for callers without any address header (1500): the edge always sends `X-Forwarded-For`.

### Original behavior the Rust port must match

- `inboundWebhooks.update` requires the `sampleJson` key (send `null`); omitting it is 422 `invalidRequestData` at `sampleJson`, against the route description ("Omit or null to clear it").
- A bad action of a known `type` reports the issue inside that branch (`actions.0.tagIds`); an unknown `type` reports `actions.0`.

- Read-only tokens get 403 on the read-only `previewMapping` POST; `get` omits the `endpointUrl` key (not `null`).
- `update` returns 404 before it checks the config; config issues report only the first problem, in the order inbox → identifiers → field mappings.
- `previewMapping` with an unknown `inboxId` answers 200 (no channel), not 404.
- An identifier sent as a JSON number beyond 2^53 is treated as absent (`raw: null`).
- A non-string mapped value is written as its JSON text (e.g. `{"sku":"A-1"}`).
- The 413 check runs before the token lookup; the token-shape 404 runs before the rate limit.
- Deliveries do not change the webhook's `updatedAt`; a duplicate does not raise `requestCount`.
- Full-name contact lookup is case-sensitive (whitespace collapsed).

### Surprises the Rust port must match

- igComments: an unknown/foreign flow reply is **404 `notFound`** on create
  but **422 `validation`** on update (same message "Flow not found").
  igStories does **not** check that a flow reply exists at all.
- igStories keeps a text reply as sent; igComments mirrors a public text
  reply into `values` and `value`.
- listStories shows a video story's `media_url` (.mp4) as `full_picture`;
  listMedia shows a video's `thumbnail_url`.
- An Instagram Login Live automation create re-subscribes **every**
  Instagram Login account of the workspace, and ignores the result.
- A Graph error for one account is swallowed: the account stays in `pages`
  with no posts/stories, status 200.
- inboxTeams `list` returns the full `User` rows of the members (including

  team; `removeMembers` takes a JSON body on DELETE.
- googleAds `listEvents` `pageCount` is at least 1; `getStats` normalises

## 8. Original behavior the Rust port must match (surprises)

Part A:
1. `flows.publish` / `flows.updateDraft` with a spec keep the draft's old
   `startNodeId`; the published version's `startNodeId` can name a node that
   is no longer in the graph.
2. `flows.create` without `publish` leaves `draftVersionId` null; with
   `publish:true` it sets `draftVersionId` and `enableInInbox:false`.
3. `flows.list?active=false` returns only inactive flows.
4. `flows.delete` of an unknown or foreign id -> 204.
5. `flows.versions` of an unknown id -> 200 `{data:[]}`; the list is cached and
   not invalidated by delete (Rust may drop the cache; parity tests do not
   assert the stale read).
6. `flows.create` folder 404 and `flows.export` 409 are `defined:false`;
   authoring errors are `defined:false` with `data` as a bare array.
7. Authoring error path of a channel rule names the compiled node path under
   the spec step, e.g. `steps[0].data.details.steps[0]`.
8. `folders.list` without `parentId` lists sub-folders too; `folders.create`
   answers 200, not 201.
9. Empty lists have `pageCount: 0`.

Parts B and C: see "Original behavior the Rust port must match" in §4 and
"Surprises the Rust port must match" in §5.
