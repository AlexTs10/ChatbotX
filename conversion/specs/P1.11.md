## 1. Common contract

### 1.1 Workspace-token auth (47 operations: all but `me.*`)

`workspaceTokenAuthAPIForScope(scope)`; all checks run before input validation (test `00-auth`):

1. No bearer and no `?token=`, or an unknown `cbx_ws_` token -> **401** `{defined:true, code:"INVALID_CHATBOT_TOKEN", status:401, message:"Invalid or missing workspace API token"}`.
2. Read-only token on any POST/PUT/PATCH/DELETE -> **403** `{defined:true, code:"FORBIDDEN", message:"Read-only token cannot perform this operation"}` (checked before the scope). Read-only tokens pass auth on every GET.
3. Scope: `scopes === null` = all, else the route scope must be listed, else **403** `{defined:true, code:"FORBIDDEN", message:"Token is not authorized for the '<scope>' scope"}`.
4. A mobile access JWT with `x-workspace-id` authenticates as that member, only on the routes of `lib/mobile-auth/member-route-allowlist.ts` (in this unit: messages list/get/create/update/delete/changeAttributes, mediaLibrary createUploadUrl/createFile); any other route -> 403 `FORBIDDEN` "This operation is not available to mobile sessions"; no header -> **400** `WORKSPACE_SELECTION_REQUIRED` "A numeric x-workspace-id header is required for this request"; a workspace the user is not in -> 403 "Account has no access to this workspace"; `mustChangePassword` -> 403 "Password change required". A member's `messages.create` is attributed to the user (`senderType:"user"`, `senderId`) (test `20-me`).

| Namespace | Scope |
|---|---|
| magicLinks | `automation` |
| mediaLibrary | `media` |
| messages | `inbox` |
| messengerChannels | `channels` |
| messengerPersonas | `channels` |
| messengerTemplates | `broadcasts` |

### 1.2 `me` auth (5 operations)

`mobileUserAPI` / `mobileUserPasswordChangeAPI`: only a mobile access JWT from
`POST /api/auth/mobile/token` (`{grantType:"password", email, password, deviceId?}`
-> `{tokenType:"Bearer", accessToken, expiresIn, expiresAt, refreshToken, refreshTokenExpiresAt, deviceId, mustChangePassword}`).
No token, a workspace token or a JWT no issuer signed -> **401** `INVALID_CHATBOT_TOKEN`
"Invalid or missing access token". No scope, no read-only check, no
`x-workspace-id` (except the optional one of `registerDeviceToken`). A user with
`mustChangePassword` reaches only `me.get` and `me.changePassword`; the others
-> 403 `FORBIDDEN` "Password change required". The password grant is rate limited
(3 per 10 s per client address, 5 per account), so tests use a new client address per call.

### 1.3 Errors

- Input validation -> **422** `{defined:true, code:"invalidRequestData", data:{issues:[{path,message}]}}`. Union inputs (`messages.create`) report union issues (path not asserted).
- `validationException(field, message)` -> **422** `code:"validation"`.
- `notFoundException(message)` -> **404** `code:"notFound"`; `defined:true` only where the route declares `notFound` (finding/mutating/deleting error sets). `messages.create` declares the creating set without it, so its 404s ("Conversation not found", "Inbox not found", "Flow not found") are `defined:false`.
- A bare `ChatbotXException(message)` -> **400** `code:"systemError"` with that message.
- `ModelNotfoundException` (`findOrFail`) -> 404 `notFound` "Record not found".
- A Meta SDK error -> 400 `BAD_REQUEST`, `defined:false`.
- Lists with `publicListRequest`: `page` ≥ 1 (default 1), `perPage` 1..**50** (default 50); outside -> 422 (no clamp). `messages.list`: `perPage` 1..50, default **20**.

## 9. Not covered black-box (with reason)

- `messages.create` with `files` (multipart `File` upload): the public route takes `z.instanceof(File)`, which only an oRPC multipart body carries; the harness sends JSON. `mediaFile`/`mediaFileId`/`mediaFileIds` cover the attachment path.
- `messages.create` `products` success path and `isPrivateReply`: need a connected Meta catalog / WhatsApp product messages and a comment-anchored private reply; only the refusal on a channel without product messages is asserted.
- `messages.update` with a replacement attachment (`newAttachmentPath`): reads image dimensions from storage; not asserted.
- `messages.sendWhatsappTemplate` with a non-approved template: the request is 202 and the worker drops it; asserting "no call" needs a fixed wait.
- `messages.getFlowResponse` with labels from Meta (`labelSource:"whatsappFlow"`): needs a Flow sent by ChatbotX (flow token) and the Flow JSON on Meta.
- `me.registerDeviceToken`: there is no read route; the stored token is only visible through push notifications (Expo host, not in the fake upstream).
- `mediaLibrary.createUploadUrl`'s pending `File` row: no read route.
- `messengerChannels.setCoexist` → `coexistInvalidAuth` 409 / `coexistSyncNotStarted` 502: WhatsApp-only paths (setCoexist on Messenger never triggers Meta at enable time).
- `messengerTemplates.create` with a `text_and_image` header (downloads `headerImageUrl` through the SSRF guard and uploads it to Meta), and `MINI_APP` buttons.
- The `x-business-use-case-usage` throttle of the coexist pull.
- `mediaLibrary.createFile` / `moveFiles` with a `folderId` of another workspace: the code checks only the FK (no workspace scope on the folder); not asserted, as it would lock in a cross-workspace reference. To decide in the Phase 3 media unit.
- Timing: a Messenger/WhatsApp page created by these fixtures is seen by the daily token-refresh crons; like P1.10, a full run must not cross 02:00 / 14:00 UTC (or P1.28 scripts those calls).

## 10. Original behavior the Rust port must match (surprises)

Locked in by the tests (observed on the original stack):

1. magicLinks: the resource never returns the destination URL — `url` is the shareable `/r/<ws>/<name>` link; `keyword` still searches the hidden destination. A name with `/` is accepted and gets a share URL, but `GET /r/<ws>/<a/b>` is 404 (the route has one `[name]` segment). `PATCH` with `{}` -> 500 `INTERNAL_SERVER_ERROR` (drizzle update with no columns). Empty list `pageCount: 0`.
2. mediaLibrary: `renameFolder`, `deleteFolder`, `recordAccess` and `moveFiles` on an unknown or foreign id answer 204 and change nothing. `listFolders` empty -> `pageCount: 1` (in-memory paging), `listFiles` empty -> `pageCount: 0`. `filter=recent` orders by `lastAccessedAt DESC` with never-accessed files **first** (Postgres NULLS FIRST). `setFavourite` returns the row as read before the write (old `updatedAt`). `createFile` only checks the path prefix (no stored object needed). Folder order is `name ASC` (tests use one letter case; the collation of mixed case is not asserted).
3. messages: `create` 404s are `defined:false`. `productMessageUnresolvable` / `imagesNotSupportedOnChannel` carry a detailed message (`"Product message cannot be sent: channelUnsupported (reason=channelUnsupported)"`, `"The messenger channel can send at most 1 image(s) here (reason=tooManyImages, channel=messenger, max=1)"`), not the declared generic text. `create` with `flowId` -> 201 with body `null`. `delete` is a soft delete of any message type; deleted messages stay in `list` and `get` with `deletedAt`. Unknown message on `update`/`delete` -> **400** `systemError` "Comment not found" and on `changeAttributes` 400 "Message not found" (not 404). `changeAttributes` on a chat message -> 200 but nothing changes (`attributes` stays null). `get` needs the exact `createdAt` (another value -> 404). The Messenger chat send has no `tag`/`persona_id` keys when unset (`messaging_type:"RESPONSE"`).
4. getFlowResponse field order follows the stored jsonb key order (Postgres orders object keys by length, then bytes); the test uses keys already in that order, so a SQLite TEXT store that keeps insertion order gives the same answer. A Rust port that reads another key order must sort the same way.
5. messengerChannels.updateSettings (PUT) on an unknown or foreign page -> **400** `systemError` "Failed to update Facebook page" (the page lookup runs inside the save's catch-all), while getSettings and patchSettings answer 404 "Record not found". An unknown flow -> 404 "Flow does not exists." (sic), before any Graph call. Persona create is `POST /me/personas?access_token=<token>` (no API version, token in the query); `GET /me/personas` runs on every save, even with no personas.
6. messengerChannels.disconnect: the route description says a transient Meta error fails the request, but every unsubscribe error is only logged and the channel is removed (204).
7. `flows.publish` in a workspace with Messenger pages makes the worker POST `/<pageId>/welcome_message_flows` for every page a few seconds later (seen as background calls in these tests; owned by the flows unit P1.9).
8. Messenger CAPI uses Graph `v24.0`; the Messenger send, comment, profile and template calls use the auth's `v23.0`.
