## 1. Layout

- New crate `crates/business` (`chatbotx-business`; deps core, db, jobs, kv, rt;
  `[lints] workspace = true`). One module per `packages/business/src/<domain>`.
  - `errors::BusinessError` = `ChatbotXException` (message, code, status, field,
    data) or a repository error. `notFoundException` = `not_found`,
    `validationException` = `validation` (422).
  - `tx::{write, read}`: `db.transaction` / plain read where a `BusinessError`
    raised inside the closure comes back unchanged (rollback on error).
- `crates/api/src/handlers`: the public `/v1` handlers, one module per builder
  router. `handlers::dispatch(state, route_id, Call)`; `None` = not ported (the
  route keeps the "Operation not ported yet" 404).
  - `handlers::input::Input`: the oRPC compact input (path params + query for
    GET/DELETE, + JSON body otherwise) and the zod checks used by the request
    schemas; every issue goes into one `422 invalidRequestData`
    (`data.issues[{code, path, message}]`). Issue messages follow zod 4 wording
    loosely; the parity tests check the issue paths only.
  - Output helpers: ids as strings, dates as ISO 8601 with ms, JS numbers
    (`10`, not `10.0`).
  - Errors: `business_error(err, ErrorMap)`: same code / status / message;
    `defined: true` when the route's error map (or `commonApiErrors`) has the code
    with that status (oRPC `validateORPCError`). Repository errors are
    `500 INTERNAL_SERVER_ERROR` (cause logged).
- `routes::handle_public_request_with(deps, Option<&ApiState>, method, uri,
  headers, body)`; `public_api_router_with(deps, Arc<ApiState>)` (server uses
  it). The old `handle_public_request` / `public_api_router` (no handlers) stay
  for the P3.5 auth tests.
- Test fixtures: `crates/business/tests/common/mod.rs` (migrated temp database,
  two workspaces), `crates/api/tests/handlers_common/mod.rs` (same + a direct
  `dispatch` call).

## 2. Slice order (orchestrator-delegated, recommended option)

Inside p1-13 the places slice goes first: it is the smallest domain and has no
dependency on unported domains, so the crate, the handler wiring and the input
validation are built and proven on it. Then pipelines (split: core / items),
then polls. Logged in DECISIONS.
