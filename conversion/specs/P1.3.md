## 1. Common rules (all 49 operations)

### 1.1 Auth

- Workspace token (`Authorization: Bearer cbx_ws_…`; also mobile JWT + `x-workspace-id`,
  MCP OAuth JWT, deprecated `?token=`). Middleware order: token → pre-auth IP
  rate limit (600/10 s) → workspace lookup → per-workspace rate limit
  (120/10 s, 429 `tooManyRequests`) → deletion-scheduled check (403) →
  read-only check → owner quota gate → **scope** check → idempotency → input
  validation → handler. Auth errors therefore come before input errors.
- No token / unknown token: **401** `INVALID_CHATBOT_TOKEN`, message
  `Invalid or missing workspace API token`, `defined: true`.
- Scope (`requireTokenScope`): `aiHandover.*` → `integrations`;
  `aiMcpServers.*` → `automation`; `analytics.*` → `analytics`. Token
  `scopes = null` = all scopes. A token without the scope: **403** `FORBIDDEN`,
  message `Token is not authorized for the '<scope>' scope`.
- Read-only token (`permission = read_only`): GET passes; every other method
  is **403** `FORBIDDEN`, message `Read-only token cannot perform this operation`.
  Writes of this unit: `aiHandover.{saveSettings,patchSettings,setApplyToAll,retryApplyToAll}`,
  `aiMcpServers.{create,update,delete}`, `analytics.resetFlowStats`.

### 1.2 Errors

- Body: `{ defined, code, status, message, data? }` (oRPC). Tests compare
  `status`, `code`, `defined`, and `message` only where the code has fixed text.
- Input-schema rejection: **422** `invalidRequestData`, `data.issues[]` with
  `path` (tests compare the dotted path of the issue).
- `ChatbotXException` → its own code/status (`notFound` 404, `validation`
  422, `aiHandoverBulk*` 422). `validation` keeps `data` only for structured codes.
- GET input comes from the query string (and path params). A single query
  value for an array field is wrapped (`?channels=messenger`); repeated keys
  build an array.

### 1.3 Time ranges (analytics)

- `from`, `to`: any `Date`-parsable string (no format check); `from` is
  clamped to `2020-01-01T00:00:00Z`. `timezone`: default `UTC`, any string;
  SQL resolves it through `pg_timezone_names` (unknown → UTC). An unparsable
  `from`/`to` or a timezone that `date-fns-tz` rejects ends in a 500 in the
  original (not tested, see §6).
- Filters `channels[]` (enum `omnichannel|webchat|messenger|whatsapp|zalo|smtp|telegram|instagram|threads|tiktok|api`,
  max 11) and `inboxIds[]` (digits, ≤ 18 chars, max 200). Both empty = all.
  Events without `channel`/`inboxId` are only counted unfiltered.
- Day buckets: `time_bucket('1 day', ts AT TIME ZONE tz AT TIME ZONE 'UTC')`,
  i.e. the local day, written as that day at `00:00:00.000Z`. Month buckets
  likewise (`1 month`). Zero-filled series iterate the local days/months from
  the local day of `from` to the local day of `to` and emit `parseISO(key)`
  in the builder's TZ (UTC) → `YYYY-MM-DDT00:00:00.000Z`.
- `> 60` full days between `from` and `to` (`differenceInDays`) → monthly
  buckets for the contact series, `botMessagesByResult` (granularity day),
  `messagesBySender`, and the comment automation reply series.
- Cagg path: an UNFILTERED read whose `from >= now − 6 days` reads the hourly
  continuous aggregates (`analytics_*_events_hourly`, real-time, but late
  inserts into a materialized bucket stay invisible until the next refresh).
  `botMessages*` with `granularity=hour` and no filter always read the cagg.
  All seeded tests use 2025 data, so they take the raw-table path.
- Response caches (Redis): `blockedContactsCount`, `newContactsCount`,
  `contactsCount`, `activeContactsCount` 120 s keyed by workspace + range +
  tz + filters; `contactsByDimension` (`metric=total`) 120 s;
  `broadcastStats`, `sequenceStepStats`, `flowStats` 120 s (flowStats tagged
  `flow-stats:<flowId>`, cleared by `resetFlowStats`); `macActiveContactCount`
  until end of day. The port may keep or drop the caches, but a cached read
  must never answer another workspace.

availableTools, selectedTools, createdAt, updatedAt }`. `auth` is
`{type:"none"} | {type:"token"} | {type:"header", headers:[{header}]}` —
**the token and header values are never returned** (output schema strips them).
No operation calls the MCP server (no outbound HTTP; `assertSafeMcpEndpoint`

## 3. aiHandover (scope `integrations`)

A "Page" is an `Inbox` of channel `messenger` (the only key of
`AI_HANDOVER_CHANNEL_POLICIES`: takeover window 7 d, hand-to-AI activity window
30 d, message max 2000). Every operation first resolves the inbox in the
workspace; unknown, foreign, or non-messenger inbox → **404** `notFound`
"Inbox not found". `inboxId` must be digits (422).

Settings resource: `{ enabled, scheduleEnabled, timeRanges:[{from,to}], gotoFlowId,
returnMessage, pauseBotWaitingForStaff }`; a Page that never saved returns
all-off defaults. `timeRanges`: ≤ 24 items, integers 0–24, `from ≠ to`,
`from > to` wraps midnight, end exclusive; active check uses the workspace
timezone hour. Run resource (`aiHandoverBulkRunResource`): `{ id, action
(enable|disable), status (pending|running|cancelling|completed|failed|cancelled),
message, requestedAt, startedAt, finishedAt, processedCount, skippedCount,
failedCount, totalCount, currentError, requestedByName (null for token callers),
pausedUntil }`.

| Operation | Input | Output | Errors | Side effects | Tests |
|---|---|---|---|---|---|
| `getSettings` GET `…/settings` | `inboxId` | settings + `applyToAll: {status (run status, or idle / reconciling), applyToAllCustomers, isAutomationActive, run}` | 404 | — | `ai-handover.test.ts` › getSettings |
| `saveSettings` PUT `…/settings` | full settings; `returnMessage` string ≤ 2000 or null; refine: schedule needs ≥ 1 range | settings (returnMessage trimmed, `""`→null) | 422 input; 404 inbox; 404 "Flow not found" (goto flow unknown, foreign or inactive) | `AiHandoverSettings` upsert (Redis lock `ai-handover-settings:<inbox>` 30 s); settings cache cleared; saving `enabled:false` cancels a live enable run | › saveSettings |
| `patchSettings` PATCH `…/settings` | any subset (same field rules, no schedule refine) | merged settings (merge onto saved or defaults) | 422 input; 422 `validation` "Add at least one time range"; 404 | same as save | › patchSettings |

| `listHistory` GET `…/history` | `page`, `perPage` (1–50) | `{data, pageCount}` newest first | 422; 404 | — | › listHistory |

Eligibility (enable): `ContactInbox.lastIncomingMessageAt ≥ now − 30 d`,
`sourceId` not null, DM conversation (`sourceId IS NULL`), thread not held in
standby. Disable: standby held by `ai_agent`, inside 7 d. Worker outcome in the
parity stack: no `IntegrationMessenger` row exists, so `createBulkThreadControl`
fails → the run ends `failed`, `currentError: integrationUnavailable`, all
eligible threads counted `skipped`, `totalCount` = eligible count. No outbound
HTTP happens. Tests poll `getSettings` with `eventually`.

Not covered: real hand-over through Meta (`pass_thread_control` to the Page
inbox app, batching, quota pauses `pausedUntil`, `pageRefused`,
`channelUnavailable`, take-back messages with the HUMAN_AGENT tag). These need
a Messenger integration with encrypted page token and scripted Graph answers
(P1.2's Messenger channel fixture + a thread-control unit). `runNotStartable`
needs a run that is still live when the next change arrives (timing-dependent).
`messageTooLong` is unreachable through the public schema (same 2000 limit).

## 6. Not tested black-box (with reason)

- Cagg read path (ranges starting in the last 6 days, unfiltered; bot
  messages `granularity=hour` unfiltered): the continuous-aggregate refresh lag
  makes counts timing-dependent. The Rust port must give the raw-table numbers
  for the same data; Class B/C tests cover the routing.
- Monthly `botMessagesByResult` with several (responseType, aiProvider) groups
  in one (month, result): the original keeps the first group's
  responseType/aiProvider in no defined order; only counts are asserted.
- Unparsable `from`/`to`, timezone names unknown to `date-fns-tz`, non-digit
  `broadcastId`/`sequenceId`/`stepId`/`flowId`/`linkId`, digit ids longer than
  bigint: the original answers 500 (no input check). Not a contract to keep;
  listed for the port to decide (recommend 422).
- Rate limits (429 `tooManyRequests`), deletion-scheduled workspace (403),
  trial/MAC owner gate (cloud editions only), mobile JWT and MCP OAuth
  principals: shared middleware, covered by the auth/middleware unit, not per
  operation here.
- Idempotency-Key behavior on the write operations: shared middleware unit.
- aiHandover real Meta hand-over / take-back, pauses, `runNotStartable`
  (see §3).
- `commentAutomationContacts` with `eventType=comment:missed` rows
  (`CommentAutomationMiss` hydration) — only the empty case is tested.
- The analytics response caches themselves (hit/expiry); tests only avoid
  them (unique workspaces, a new `to` per poll in the end-to-end test).
