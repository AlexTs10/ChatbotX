### 1.1 How the schemas were ported

The zod definitions are data: `conversion/tools/zod-rust-gen/gen.mts` walks the `_zod.def` tree of every export of the package (loaded with tsx; a Node load hook keeps the superRefine callback and the raw default on the def) and wrote Rust skeletons once: `schema!(pub fn name = z::object(vec![…]).super_refine(f))`, `default_fn!(…)` for zero-argument `*DefaultFn` factories (fresh `create_id()` where two calls differ), constants, and plain data tables (`&'static Value`, parsed from JSON). Descriptions and `.meta()` are kept verbatim (the authoring JSON Schema needs them). Closures (refine, superRefine, transform, preprocess, custom) became named stubs with the TypeScript source in a comment and are ported by hand, like every function export. Shared sub-schemas that are exports are referenced, not inlined; recursion goes through `z::lazy`.

### 1.2 API shape

- Schemas: `fn x_schema() -> Schema` (built once, cheap `Arc` clone; `Schema::same` is `toBe`).
- Flow data is JSON: steps, nodes, edges, template components and params are `serde_json::Value` in and out (what the API and the database store). Small result types are structs: `ButtonPayload`, `FlowActionTarget`, `FieldReference`, `DeepLinkApp`/`AppLinkTargets`, `SendTextLengthLimits`, `SendViewCatalogLengthLimits`, `ChannelFlowPolicy`, `FlowAuthoringError`/`FlowAuthoringException`, `NormalizedAuthoredGraph`, `PaymentRequestIssue`, `LayoutPosition`.
- `*DefaultFn(props?)` → `fn x_default_fn(props: &Value) -> Value` when the TS factory takes props (pass `&json!({})` for none); `pipelineStepDefaultFn(action, carry)` → `(action: &str, carry: &Value)`.
- `StepValidator` = `Schema(Schema)` | `PerChannel { base, overrides }`; `.base()` is `validator.omnichannel`, `.channel(c)` is `validator[c]`.
- Time: `Date.now()` → injected `chatbotx_kv::Clock`; `Date` → `chrono::DateTime<Utc>`.
- Refinement helpers called inside a user superRefine take `&mut z::RefineCtx` (`ctx.addIssue`).

## 2. zod semantics kept (`z`)

- Object: strip unknown keys; `.strict()` → `unrecognized_keys` (continue); `.loose()`; catchall. Absent optional keys stay absent; `.default()` fills absent keys; a required key that accepts `undefined` reports `expected nonoptional`.
- Checks run after the base parse in declaration order; length checks run on any value with a length (zod's `when`); other checks skip once an aborting issue exists (`invalid_type` aborts; `too_small`/`too_big`/format/custom continue). Refinements on an object therefore run when only a field's `min`/`max` failed, as in zod 4.
- String `min`/`max`/`length` count code points (zod 4.6.7); `.trim()`, `.toLowerCase()` and `.url()` (trims, strips TAB/LF/CR) rewrite the value; `.regex` translates JS `\d`/`\w` to ASCII classes; the message shows `/source/flags`.
- Union: first success wins; else the single non-aborted option's issues; else `invalid_union` ("Invalid input"). Discriminated union: picks by the discriminator values (literal/enum/optional), else `Invalid discriminator value. Expected 'a' | 'b'` at `[disc]`.
- Pipe stops on any issue except `unrecognized_keys`; transforms see only defined values; `z.coerce.number()` follows `Number()`.
- Messages: the zod 4.6.7 `en` locale (`Invalid input: expected string, received number`, `Too big: expected string to have <=20 characters`, …); a check message beats the schema-level `error`.
- `z.date()` never matches JSON input (the event-bus `Date` fields get typed payloads in the jobs port).

## 3. Differences and doubtful points

1. Execute JavaScript is gone from `stepTypes`, the action union and the channel policy table: a stored flow with that step no longer parses (no data import, DECISIONS 2026-11-11). Orchestrator-delegated, recommended option (DECISIONS 2026-11-12, P3.4).
2. JSON objects are `BTreeMap`-ordered (no `preserve_order`, DECISIONS P3.1); values are equal, byte order of re-serialized objects can differ (the template structure key sorts keys anyway).
3. `toBe` identity of returned plain objects becomes value equality (marked `adapted`).
4. An explicit `undefined` property in a TS fixture is an absent key (marked `adapted`).
