Changes from Postgres that this spec makes (each is also a doubt in section 4):

1. **`Message` / `Attachment` PK `(id, createdAt)` → `"id" INTEGER PRIMARY KEY`.** DECISIONS P2.2 (hypertable key not needed). A duplicate `id` gives
   `SQLITE_CONSTRAINT_PRIMARYKEY`; the P2.3 error mapping names it `Message_pkey`, the name that `primary-key-collision.ts` checks.
2. **`ContactOnSequence` / `SequenceDispatch` PK `(id, workspaceId)` → `"id" INTEGER PRIMARY KEY`** (P2.2 §3.3). SQLite requires the parent columns
   of a FK to be a PK or a UNIQUE index, so `ContactOnSequence` gets the SQLite-only `CONSTRAINT "ContactOnSequence_id_workspaceId_key" UNIQUE ("id", "workspaceId")`
   for `SequenceDispatch_enrollment_workspace_fkey` (checked: without it, any DML on the child fails with "foreign key mismatch").
3. **`Message_source_dedup_idx` keeps `createdAt`: `UNIQUE ("contactInboxId", "sourceId", "createdAt")`**, as P2.2 §3.1 allowed ("if a test needs the loose form, keep
   `createdAt` in the unique key"). Reason: the frozen `sharded-message-repository.test.ts:90` "conflict target is (contactInboxId, sourceId, createdAt)" pins
   the 3-column `ON CONFLICT` target; SQLite rejects an `ON CONFLICT` target that matches no UNIQUE index, so the 2-column key would make that port impossible.
   Same dedup semantics as Postgres (also the same gap: a re-delivered message with another `createdAt` is a second row). P2.2 open point 3 is answered
   by this choice unless the orchestrator decides otherwise.
4. **`ContactOnSmartDelay.appointmentId` is not created here** (P2.2 §2): it points to the part-3 table `Appointment`. SQLite cannot add a FK to an existing column,
   so P2.5 adds the column with `ALTER TABLE … ADD COLUMN` (section 1.5). Until P2.5, `ContactOnSmartDelay` has 13 columns.
5. **No change to the Postgres index set**, the same rule as 0001 (P2.3 1.2 item 4; the frozen `workspace-purge-coverage` list pins the un-indexed FKs).
   Redundant Postgres indexes are kept for parity: `SequenceDispatch_id_idx` (same key as the rowid), `TriggerStat_triggerId_date_idx` (same key as
   `TriggerStat_triggerId_date_key`). Section 2.3 proposes one extra index; it is **not** in the DDL below until the orchestrator decides (doubt 3).

## 2. Partitioning, hypertables and sharding of messages → one SQLite table

### 2.1 Mapping

| Postgres object | Source | SQLite (DECISIONS P2.2) |
|---|---|---|
| `Message`, `Attachment` hypertables, `by_range('createdAt', INTERVAL '7 days')` | `20260622040000_align_message_attachment_to_shard_schema` | one plain table each. No chunks; the time indexes `Message_workspace_created_idx (workspaceId, createdAt DESC)`, `Message_conversation_history_idx (conversationId, createdAt DESC, id DESC)`, `Attachment_workspaceId_createdAt_idx`, `Attachment_conversationId_idx (conversationId, createdAt DESC)` do the job of chunk exclusion |
| Compression policy after 30 days (`compress_segmentby = workspaceId, conversationId`, `orderby createdAt DESC`) | same | none. Size control: P2.6 retention jobs + `PRAGMA incremental_vacuum` (P2.2 §3.1, risk 4) |
| PK `(id, createdAt)`, unique `(contactInboxId, sourceId, createdAt)` | hypertable rule (partition column in every unique key) | PK `(id)`; dedup unique keeps 3 columns (1.2 item 3) |
| `update_updated_at_column` triggers on both tables | same migration | Rust sets `updatedAt` on every UPDATE (P2.2 §3.4) |
| `liftDecompressionLimit` (`timescale.ts`, `SET timescaledb.max_tuples_decompressed_per_dml_transaction`) | `src/timescale.ts` | no-op (nothing is compressed) |
| Message sharding: `MessageShard`, `ShardTimeRange` (gist EXCLUDE, `btree_gist`), `MessageShardConnectionManager`, `ShardedMessageRepository` fan-out/merge/retry, `init-message-shard.sql`, shard migration runner | `src/sharding/**` | **not created / not ported** (DECISIONS P2.2: "Sharding not used"). The Rust `MessageRepository` runs each public method of `ShardedMessageRepository` as one query on the main connection; "read shards for a time range" and "merge write shard" disappear; `withShardRetry` disappears (one file, no network) |
| `ContactOnBroadcast` HASH(broadcastId)×64 | `20260612235000_partition_contact_on_broadcast` | one table; `broadcastId` is the PK prefix, so "partition = broadcast" lookups use the PK autoindex |
| `ContactOnSequence`, `SequenceDispatch` HASH(workspaceId)×64 | `20260612235500_…` | one table each; workspace lookups use `ContactsOnSequence_workspaceId_idx`, `SequenceDispatch_workspaceId_status_runAtMs_idx` (both Postgres indexes) |

| Per-partition index builds (`CREATE INDEX CONCURRENTLY … "T_pN_…"`, `ON ONLY`, `ATTACH PARTITION`, validity checks) | `20260924105732_…`, `20260920111706_…`, `20261025020711_…` | one `CREATE INDEX` each (SQLite DDL is transactional; the runner applies a version all-or-nothing) |

### 2.2 Hot queries and the index that serves each (no partition pruning in SQLite)

Checked with `EXPLAIN QUERY PLAN` on 0001 + 0002 after `ANALYZE` with a synthetic load (60,000 messages in 3 workspaces, 600 conversations/contact inboxes,
12,000 attachments, 3,000 conversations) and realistic bound values. The plans depend on statistics: the runner already does `PRAGMA optimize=0x10002`
at open and P2.6 runs `PRAGMA optimize` every 6 h (P2.3 2.3); without statistics the planner chose `Message_workspace_created_idx` for several of these.
Python's SQLite build has `ENABLE_STAT4`; check that the bundled rusqlite build also has it (doubt 4).

| Caller (TS source) | SQLite query shape (Rust) | Index used | Postgres equivalent |
|---|---|---|---|

### 2.3 Proposed SQLite-only index (not in 1.7; needs an orchestrator decision, doubt 3)

```sql
CREATE INDEX "Message_workspaceId_sourceId_idx" ON "Message" ("workspaceId", "sourceId") WHERE "sourceId" IS NOT NULL;
```

Effect (checked): `patchBySourceId` / `deleteBySourceId` become `SEARCH … USING COVERING INDEX Message_workspaceId_sourceId_idx (workspaceId=? AND sourceId=?)`;
`findBySourceId` and `findManyBySourceIds` also switch to it. Cost: one more index on the largest table (about 30–40 bytes per message with a Meta `mid` source id).
It is not a parity requirement (Postgres had no such index either) but these are per-webhook-event writes and the skip-scan cost grows with the number of
contact inboxes of a workspace. It does not touch any FK, so `workspace-purge-coverage` is not affected. If adopted, add it as the last index of the `Message` block.

## 4. Doubts

1. **Message dedup key** (1.2 item 3). This spec keeps `UNIQUE (contactInboxId, sourceId, createdAt)` (P2.2 allowed it; the frozen test `sharded-message-repository.test.ts:90`
   needs the 3-column conflict target). P2.2's recommended 2-column key is stricter (one row per source id) but breaks that port and changes dedup semantics.
   Orchestrator: confirm and record the answer to P2.2 §7 point 3 in DECISIONS.
2. **PK `(id)` instead of `(id, createdAt)` / `(id, workspaceId)`** for `Message`, `Attachment`, `ContactOnSequence`, `SequenceDispatch` (DECISIONS P2.2). The frozen
   test `partition-migrations.test.ts:83` text names the composite PK; the replacement asserts `[id]`. Queries that pass both columns still work. The extra UNIQUE
   `ContactOnSequence_id_workspaceId_key` is required by SQLite for the composite FK.
3. **Proposed SQLite-only index `Message_workspaceId_sourceId_idx`** (2.3). Not in the DDL. Without it, the per-event `…BySourceId` updates use a skip-scan whose
   cost grows with the contact inboxes of a workspace; with it, one more index on the largest table. Recommendation: add it (the original's cost was a scan of every
   chunk, so this is no regression either way, but it is a hot write path). Needs an orchestrator yes/no.
4. **Planner statistics.** Several message queries pick the right index only after `ANALYZE` (checked: with no statistics the planner chose
   `Message_workspace_created_idx` for conversation reads). P2.3 runs `PRAGMA optimize=0x10002` at open, which analyzes only tables that need it; on a fresh file with
   few rows this is fine, but a fresh import of many messages before the first `optimize` can give slow plans. Check that the bundled SQLite of rusqlite has
   `SQLITE_ENABLE_STAT4` (Python's has); if not, plans are still correct with STAT1 but range estimates are coarser. Option for P3: `INDEXED BY` on the 3–4 hottest message queries.
5. **`DbError` needs the CHECK constraint name** (1.6 item 3). Frozen tests 8.1 and 9.1 assert it; P2.3's mapping leaves it `None`. Small change in `error.rs`
   (parse `CHECK constraint failed: <name>`). For an unnamed column CHECK (enum, boolean, json) SQLite reports the column name or expression, so `constraint()` would be
   that text; Postgres raises `22P02` (invalid enum input) or a `<table>_<col>_check` name there. No code checks `22P02` (grep), so mapping all CHECK failures to `23514` is safe.
6. **FK constraint names** (9.2): SQLite does not report them (P2.3 doubt 6). The composite FK name is kept in the table SQL only for readability; the replacement
   assertion checks the FK definition and the SQLSTATE.
7. **Shared state in `broadcast-recurrence-constraints`** (8.x): the TS cases run in order inside one rolled-back transaction and later cases rely on rows of earlier ones
   (8.4 on 8.3's run). The Rust port makes every case self-contained; the assertions are unchanged. If the verifier wants strict file order, use one Rust test with 7 steps
   instead (loses per-case names).
8. **PK name of `ContactOnBroadcast`** is `ContactsOnBroadcast_pkey` in Postgres; the P2.3 error mapping would report `ContactOnBroadcast_pkey`. No code or test checks it
   (grep). Optional fix in 1.6 item 4.
9. **Redundant Postgres indexes kept** (`SequenceDispatch_id_idx`, `TriggerStat_triggerId_date_idx`). They cost writes on hot tables (`SequenceDispatch` is a claim queue).
   Dropping them changes no FK coverage and no frozen test; kept for parity of the index set. Phase 5 can drop them with a decision.
10. **Column order** of `ContactOnSmartDelay` changes when P2.5 appends `appointmentId` (same as P2.3 doubt 10). Rust code must name columns.
11. **No FKs on `Message` / `Attachment`** (same as Postgres). Deleting a workspace, conversation or contact inbox does **not** delete messages by cascade; the purge code
    (P3 workspace-purge, `hardDeleteAllByContactInbox`) must keep deleting them explicitly, chunked by rowid (single writer, P2.2 §3.6).
12. **`now()` defaults on `Message.createdAt`**: the DB default stays as a safety net, but `bulkCreate`/`create` must stamp `createdAt` in Rust (frozen
    `sharded-message-repository.test.ts` "stamps a missing createdAt itself"), because the dedup key and the `(id, createdAt)` lookups need the exact value.
