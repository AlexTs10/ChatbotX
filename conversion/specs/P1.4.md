namespaces `appointmentCalendars`, `appointmentExternalCalendars`,
`appointmentReminders`, `appointments`, `botFields`, `botSimulator`,
`broadcasts`, `capabilities`, `carts`, `channelIntegrations`, `channelPosts`

Tests: `conversion/parity/tests/p1-04-appointments-broadcasts/` (files `00-` to

## 1. Common contract (all 55 operations)

### 1.1 Auth (`workspaceTokenAuthAPIForScope(scope)`, `apps/builder/src/orpc.ts:208-222`)

Order of checks, all before input validation:

1. No `Authorization: Bearer` and no `?token=` query parameter -> **401**
   `{defined:true, code:"INVALID_CHATBOT_TOKEN", status:401, message:"Invalid or missing workspace API token"}`.
   Unknown token -> same 401. The deprecated `?token=<cbx_ws_…>` query
   parameter still authenticates (logged as deprecated).
2. Pre-auth rate limit per client IP: 600 / 10 s. Per-workspace limit:
   120 / 10 s (`apps/builder/src/lib/rate-limit/api-rate-limit.ts`). Over -> 429.
3. Read-only token (`permission: "read_only"`) on any POST/PUT/PATCH/DELETE of
   this unit -> **403** `{defined:true, code:"FORBIDDEN", message:"Read-only token cannot perform this operation"}`.
   No P1.4 POST is on `READ_ONLY_TOKEN_ALLOWED_POST_PATHS`
   (`broadcasts.previewAudience` and `broadcasts.previewRecurrence` are blocked too).
   Read-only tokens pass auth on every GET.
4. Scope (`requireTokenScope`): `scopes === null` = all scopes. Otherwise the
   operation's scope must be in the list, else **403**
   `{defined:true, code:"FORBIDDEN", message:"Token is not authorized for the '<scope>' scope"}`.

Scopes: `appointments` (appointmentCalendars, appointmentExternalCalendars,
appointmentReminders, appointments), `automation` (botFields), `channels`
(botSimulator, channelIntegrations), `broadcasts` (broadcasts), `contacts`
(capabilities, channelPosts), `ecommerce` (carts).
`appointments.createBookingLink` with `send: true` additionally needs the
`inbox` scope (checked in the handler, before any lookup).

Covering tests: `00-auth.test.ts` (table of all 55 operations: no token, unknown
token, wrong scope, read-only write, read-only read; scoped-token reads; `?token=`).

### 1.2 Errors

- Input schema failure (body, query or path) -> **422**
  `{code:"invalidRequestData", status:422, defined:true, data:{issues:[{path,message,…}]}}`
  (`apps/builder/src/orpc.ts:110-122`). Tests compare `code`, `status` and the
  issue `path`s, not zod's message text.
- `ChatbotXException` -> its `code` and `httpStatusCode` (default `systemError`/400).
  `validationException` -> `validation`/422. `notFoundException` -> `notFound`/404.
  The `message` is compared where the code defines fixed text.
- Snapshots record `{httpStatus, defined, code, status}` (`errorShape` helper).

### 1.3 Paging (`publicListRequest`)

`page` integer >= 1 (default 1), `perPage` integer 1..50 (default 50); strings are
coerced. Response `{data, pageCount}`, `pageCount = ceil(total/perPage)` (0 when
empty) unless noted.

### 1.4 Normalization used by this unit

P1.1 section 7 rules, plus: dates a test sets itself (2030 slots, recurrence
runs, `publishedAt`) are kept verbatim (`keep`), calendar `publicLinkSlug`
(a snowflake that is not in an id-named key) is replaced by `<slug:n>` in every
string, reminder `jobId` by `<jobId>` after an explicit assertion of its format,
the channel-post cursor `sortAt` is asserted by regex + instant (see 11).

## 14. Not covered black-box (with reason)

No operation is skipped. Parts of operations that are not tested:

- `appointments.book` 409 `appointmentAvailabilityChanged`: needs a calendar
  update between the availability read and the booking transaction of one
  request (race); not reproducible over HTTP.
- `appointmentCalendars.update` 409 `duplicateReminder`: the schema already
  rejects duplicates with 422; the 409 is only reachable through a race.
- `broadcasts` template payloads (`templateId`, `templateParams`, `targets`,
  `integrationWhatsappId/MessengerId`): need connected WhatsApp/Messenger
  channels and approved templates (Meta connect, other units). Only the
  flow-based legacy (`channel`) layout is covered.
- Broadcast plan restrictions (`broadcastPlanLimit`, trial Messenger rate cap):
  cloud/enterprise plan policy; parity runs the community edition (DECISIONS
  P1.1 #4).
- `listContacts` for `message:delivered/seen`, `flow:clicked`: need channel
  delivery receipts (provider webhooks); only `message:sent` and
  `message:failed` are covered.
- Mobile member principals and MCP OAuth tokens on these routes (member scope
  filters): covered by the auth units, not here.
- `listOccurrences`/`listRunGroups` paging cursors over several slots and
  `missed`/`catchUpSuperseded` outcomes: need hours of scheduler time or an
  outage.

## 15. Harness findings (shared files not changed)

- `run-original.sh --update-snapshots` passes `-u` **before** the test filter
  (`vitest run -u <path>`). vitest 5 reads the path as the value of `--update`,
  so the filter is lost and the whole `tests/` tree runs (and other units'
  snapshots on the PC are rewritten). Workaround used by this unit: no
  `--update-snapshots`; pass `-- tests/<unit> --update` instead. Proposed
  shared change (orchestrator): in `run-original.sh` line 39 append the flag,
  `vitest_args=("${vitest_args[@]}" --update)`.
- Parallel units' `chatbotx-dell` calls rsync the Mac tree to the PC with
  `--delete` before they wait for the lock, so snapshots written on the PC can
  disappear before they are copied back (seen three times in this unit: the
  PC files got the older Mac copy during `docker compose down`). This unit's
  runs start a watcher inside the same locked command that copies newer
  snapshot files every second (`cp -ru`) into the git-ignored
  `conversion/parity/.state/p104-snap/`, then fetch that folder. The wrapper
  is a private script outside the repo. Proposed shared change
  (orchestrator): let `run-original.sh` (or `runner-entrypoint.sh`) copy
  `tests/**/__snapshots__` into `.state/snapshots/` right after vitest exits,
  and let `chatbotx-dell` exclude `__snapshots__/` from `--delete`.
