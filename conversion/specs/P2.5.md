### 1.5 Rollup design (replaces the TimescaleDB continuous aggregates)

#### 1.5.1 Tables

| Rollup table (name kept) | Source events | Group columns (= the cagg `GROUP BY`) | Postgres retention |
|---|---|---|---|
| `analytics_contact_events_hourly` | `AnalyticsContactEvent` | `workspaceId`, `bucket`, `eventType`, `channel`, `senderType`, `country`, `source`, `adminId` | 3 years |
| `analytics_bot_message_events_hourly` | `AnalyticsBotMessageEvent` | `workspaceId`, `bucket`, `hasResponse`, `responseType`, `routeType`, `result`, `aiProvider` | 3 years |
| `analytics_conversation_events_hourly` | `AnalyticsConversationEvent` | `workspaceId`, `bucket`, `eventType`, `toAssignee` | 3 years |
| `analytics_message_events_hourly` | `AnalyticsMessageEvent` | `workspaceId`, `bucket`, `eventType`, `channel`, `senderType`, `adminId` | **10 years** |

- `"bucket"` = `("occurredAt" / 3600000) * 3600000` = Timescale `time_bucket('1 hour', "occurredAt")` (UTC hour start, ms). `"count"` = `COUNT(*)`, always > 0
  (a group whose last event goes away is deleted, as a refreshed cagg drops it). Column names `bucket` / `count` and the table names are the cagg names, so
  the ported analytics SQL keeps `FROM analytics_message_events_hourly … SUM(count)` (and the frozen `filtered-stats.repository.test.ts` text checks port).
- Unique key `("workspaceId", "bucket", <group columns with ifnull(col, x'')>)`: SQLite UNIQUE treats NULLs as distinct, so a plain key would never match an
  upsert with a NULL group value. `x''` is a BLOB, which never equals a TEXT or INTEGER, so `NULL`, `''` and `0` stay three groups (same as `GROUP BY`). The stored
  columns keep the real NULLs (no sentinel mapping in Rust; P2.2's sentinel idea is not needed). The key leads with `workspaceId`: it serves the reads
  (`WHERE "workspaceId" = ? AND bucket BETWEEN …`) and covers the rollup FK (`workspace-purge-coverage` stays exact, checked).
- FK `workspaceId` → `Workspace` ON DELETE CASCADE ON UPDATE NO ACTION (same as the event tables), so a workspace delete removes its rollup rows at once.
- No `inboxId` column: the caggs have none, and `shouldUseCagg` already sends every filtered read (channel / inbox) to the raw table.

| Write (Rust port of) | Statement on the event table | Rollup effect (trigger) |
|---|---|---|
| `ContactStatsRepository.insertEvents` (event-bus consumer `events:analytics-dashboard`, P2.6 §stream) | `INSERT … ON CONFLICT DO NOTHING` | `…_rollup_ai`: `INSERT … ON CONFLICT (<key>) DO UPDATE SET count = count + 1` for each row really inserted (a duplicate `eventId` fires no trigger: checked) |

Cost per event insert: one extra index-keyed upsert in the same B-tree page set (rollup rows per workspace ≈ hours × groups, small).

#### 1.5.3 Reads (input for the P3 analytics unit and P1.3)

- Keep the routing as the original: `shouldUseCagg(props)` (`!hasAnalyticsFilter && from >= now − 6 days`), `readsHourlyCagg` for bot messages, month paths.
  The rollup path and the raw path must stay **separate SQL** with the original shapes, because they can give different numbers for the same events:
  - rollup path filters `bucket >= from AND bucket <= to` (hour starts), the raw path `occurredAt >= from AND occurredAt <= to`;
  - rollup day buckets are `(tz_wall_ms(bucket, tz_resolve(?)) / 86400000) * 86400000` over **UTC hour buckets**: for a half-hour zone (`Asia/Kolkata`, +05:30)
    the events of 18:30–18:59 UTC fall on the previous local day, exactly as Postgres `time_bucket('1 day', bucket AT TIME ZONE tz AT TIME ZONE 'UTC')` does;
    the raw path buckets each `occurredAt` (correct local day). Same rule across DST changes (the offset is taken at each hour bucket).
  - `time_bucket('1 hour', bucket)` on the rollup = `bucket`; `SUM(count)::int` = `SUM("count")` (INTEGER).
- Numbers vs Postgres: the raw path is identical (P1.3 parity tests use 2025 data → raw path). On the rollup path the SQLite result equals the **raw data at
  hour granularity at every moment**; Postgres equals it only after the 5-minute refresh, and late inserts into an already materialized bucket, or events older
  than the 7-day refresh window, can stay invisible (P1.3 §6, not asserted black-box). So the port is never lower than the original's steady state and has no lag.
  This is the P1.3 rule "the Rust port must give the raw-table numbers for the same data".

  "sku" TEXT,

  "subcategoryId" INTEGER REFERENCES "ProductCategory" ("id") ON DELETE SET NULL ON UPDATE CASCADE,

  "externalId" TEXT,

## 2. Vector columns

### 2.1 DDL

```sql
-- AIEmbedding (file chunks) and AIConversationEmbedding (per-conversation sources): same column form
"embedding" BLOB CHECK ("embedding" IS NULL OR length("embedding") = 6144)
```

- 1536 little-endian IEEE-754 f32 = 6,144 bytes = libSQL `F32_BLOB(1536)` / `vector32()` bytes. NULL while the chunk is `pending` / `error` (Postgres: same).
- STRICT accepts only BLOB or NULL here: a TEXT value fails with `cannot store TEXT value in BLOB column` (checked); a wrong length fails with
  `CHECK constraint failed: embedding` (checked).
- Rust writes `Vec<f32>` → `bytemuck::cast_slice` / `to_le_bytes` per element (no NaN check in Postgres either; pgvector rejects NaN/Inf on input → Rust must
  reject non-finite values before the write to keep that behavior).
- Indexes that serve the filters (all copied from Postgres): `AIEmbedding_aiFileId_chunkIndex_idx ("aiFileId", "chunkIndex")`, `AIEmbedding_workspaceId_idx`;
  `AIConversationEmbedding_sourceId_status_idx ("sourceId", "status")`, `…_sourceId_chunkIndex_key`, `…_lookup_idx`. No vector index (section 1.2 item 4).

### 2.2 The exact filtered cosine scan

File chunks (port of `repositories/ai-file-embedding/repository.ts:82` `vectorSearch`; `fileIds` empty → return `[]` without a query, as now):

```sql
SELECT "id", "content", "aiFileId", "chunkIndex",
       1 - vector_distance_cos("embedding", vector32(?1)) AS "similarity"
FROM "AIEmbedding" INDEXED BY "AIEmbedding_aiFileId_chunkIndex_idx"
WHERE "workspaceId" = ?2
  AND "aiFileId" IN (SELECT value FROM json_each(?3))
  AND "status" = 'success'
  AND "embedding" IS NOT NULL
ORDER BY vector_distance_cos("embedding", vector32(?1)) ASC NULLS LAST, "id"
LIMIT ?4
```

Conversation sources (port of `repositories/ai-conversation-embedding/repository.ts:74`):

```sql
SELECT "id", "chunkIndex", "content",
       1 - vector_distance_cos("embedding", vector32(?1)) AS "similarity"
FROM "AIConversationEmbedding"
WHERE "sourceId" = ?2 AND "workspaceId" = ?3 AND "status" = 'success' AND "embedding" IS NOT NULL
ORDER BY vector_distance_cos("embedding", vector32(?1)) ASC NULLS LAST, "id"
LIMIT ?4
```

Notes:
- `?1` = the query vector as the same JSON text the original binds (`[0.1,0.2,…]`), converted once per row by `vector32` — or bind the blob directly and drop
  `vector32` (both give identical results; the text form keeps the frozen param assertion portable). `vector_distance_cos` is DETERMINISTIC, so SQLite computes
  the `ORDER BY` expression once per row and reuses it for `"similarity"` only if written as the same expression; to be sure, compute it once in a subquery:
  `SELECT …, 1 - d AS "similarity" FROM (SELECT …, vector_distance_cos(…) AS d FROM … WHERE …) ORDER BY d ASC NULLS LAST, "id" LIMIT ?4`.
- `NULLS LAST`: pgvector gives NaN for a zero vector and sorts it last; `vector_distance_cos` gives NULL (P2.3 3.6), so `NULLS LAST` keeps the order.
- `, "id"`: tie-break for equal distances. Postgres has none (order of ties undefined); adding one makes the result deterministic and cannot contradict a test.
- `INDEXED BY "AIEmbedding_aiFileId_chunkIndex_idx"`: checked with `EXPLAIN QUERY PLAN`: without it, and with planner statistics for one workspace, SQLite chose
  `SCAN AIEmbedding` (whole table) or `AIEmbedding_workspaceId_idx` (every chunk of the workspace); with it, `SEARCH … USING INDEX AIEmbedding_aiFileId_chunkIndex_idx
  (aiFileId=?)` for each file id. The conversation query picks `AIConversationEmbedding_sourceId_status_idx (sourceId=? AND status=?)` by itself (checked).
- SQLite reads the 6 KiB blob (two overflow pages at 4 KiB page size) only for rows that pass the `WHERE`.

### 2.3 Expected row counts and speed

Limits in the code: chunk size default 1,000 chars, step 800 (overlap 200), max 2,000 (`AI_FILE_CHUNKING_LIMITS`); at most `HEAVY_MAX_CHUNKS_PER_FILE` = 5,000
chunks per file; extracted text cap 5,000,000 chars (`HEAVY_MAX_EXTRACTED_TEXT_CHARS`). A conversation source is one attached document / image / URL.

| Case | Rows scanned per query | Blob bytes read | Estimated time (Rust, warm OS cache) |
|---|---|---|---|
| Typical agent: 1–5 files of 20–200 KB text | 25–1,250 | 0.15–7.5 MB | < 1–8 ms |
| Large: 10 files × 1,000 chunks | 10,000 | 60 MB | ≈ 40–80 ms |
| Worst case allowed by config: 10 files × 5,000 chunks | 50,000 | 300 MB | ≈ 0.2–0.5 s (cold disk: seconds) |
| Conversation source (one `sourceId`) | 1–500 | ≤ 3 MB | < 3 ms |

Basis: measured on this Mac with Python's SQLite: reading 2,500 blobs (15 MB) through the `workspaceId` index took 4 ms warm (sequential rowids) and 76 ms
through the `aiFileId` index when the rows of two files were interleaved (random access); Rust cosine over 1,536 f32 ≈ 0.5–1.5 µs per row
(≈ 4,600 flops, auto-vectorized). Per-row SQLite overhead (row + 2 overflow pages) ≈ 2–5 µs. The page cache (4 MiB per reader, P2.3 2.3) does not hold these
blobs; the OS file cache does (not counted in process RSS with mmap off).

Verdict: **fast enough at the expected volume** (self-hosted, small user count; one agent query touches only that agent's files). It is the same algorithm as
production (exact scan; production has no vector index on `AIEmbedding` and the HNSW on `AIConversationEmbedding` was never created). The only risk is an agent with
tens of thousands of chunks (doubt 3). Disk: 6 KiB per chunk (100,000 chunks ≈ 600 MB). Exact row counts of production are unknown to the analyst; a read-only
query gives them: `SELECT count(*), max(n), percentile_disc(0.99) WITHIN GROUP (ORDER BY n) FROM (SELECT "aiFileId", count(*) n FROM "AIEmbedding" GROUP BY 1) s;`.

## 4. Doubts

1. **Vector column type** (1.2 item 1): `BLOB` in STRICT tables (recommended) vs P2.2's `F32_BLOB(1536)` in non-STRICT tables. Same bytes and same SQL; only a future
   libSQL DiskANN index needs the `F32_BLOB` type name (then a 12-step table rebuild of 2 tables). Orchestrator: confirm.
2. **Rollups by trigger, not by Rust code** (1.2 item 2). P2.2 §3.4 preferred Rust ("one code path"). Triggers are the only way to also see FK cascades and the
   backfill UPDATE, and they cannot be forgotten by a new write path. Cost: one indexed upsert per event, 3 triggers per table. Orchestrator: confirm.
3. **Vector scan at the extreme** (2.3): an agent with ≥ 50,000 chunks (10 files at the 5,000-chunk cap) needs ≈ 0.2–0.5 s per query warm. Production does the
   same exact scan. Options if Phase 5 finds it slow: a per-file in-process cache of decoded vectors, or libSQL DiskANN (recall loss with pre-filters, P2.2 §1.9).
   A read-only production query (2.3) would give the real distribution.
4. **HNSW `AIConversationEmbedding_embedding_idx` not created** (snapshot drift). A future schema-manifest test generated from the snapshot (P2.2 §4.1) must
   exclude it, or it fails.
5. **`lower_u` in 4 unique indexes** (1.2 item 5): ops tools without the app functions cannot write `Vendor`, `DiscountCode`, `CouponTopic`, `PlaceCategory`
   (same trade-off as P2.3 doubt 4; P2.3 recommended a `chatbotx-server db-shell` that registers the functions). Alternative: Rust-maintained key columns
   (`nameKey`, `codeKey`) — one more column per table, and every write path must set them.
6. **`webSearchAuthorizedDomains` default** (1.2 item 6) comes from the migration history, not the snapshot (drift). The frozen list supports it. If the orchestrator
   wants strict snapshot parity, the frozen test `:91` (via `APP_SIDE_DEFAULTS`) and this DDL would disagree; keep the default.
7. **Money range** (1.2 item 7): no `abs(x) <= 9e18` CHECK. `numeric(19,4)` allows up to 10^15 major units; INTEGER × 10,000 caps at ≈ 9.22 × 10^14. The
   API must reject larger input (P2.2 1.4). Also the 2 scaled CHECK bounds (`<= 1000000`) assume the percent columns are scaled like every other money column.
8. **Two unique indexes on one column list** (`AdsConversionEvent`: full + `WHERE "channel" = 'whatsapp'`): SQLite reports only `UNIQUE constraint failed:
   AdsConversionEvent.workspaceId, …` (the first index that fails). The P2.3 rule returns the non-partial name. Check that no business code branches on the partial
   index name (grep found `onConflictDoNothing` targets with `targetWhere` by channel, which work; no name check).
9. **Rollup vs cagg numbers** (1.5.3): the port gives raw-exact hourly counts with no refresh lag; the original can lag ≤ 5 min and can miss late or
   back-dated events in materialized buckets. Not asserted by P1.3 parity tests (cagg path not tested black-box); record as an accepted improvement.
10. **Retention of 10 years** for events (and 10 years for the message rollup, 3 years for the others) is kept for parity, through the new scheduler
    `purgeAnalyticsEvents` (`45 3 * * *`). It is the 45th scheduler; P2.6 owns the jobs list. Calendar years: use `chrono` `checked_sub_months(120)` for the cutoff
    (Postgres interval semantics), not 3,650 days.
11. **Composite PK of `LeaderboardScoreEvent` kept** (`createdAt`, `id`): the score insert uses `ON CONFLICT ("createdAt", "id") DO NOTHING`
    (`repositories/leaderboard/participant.ts:149`) and the purge deletes `WHERE ("createdAt", "id") IN (…)` (`leaderboard/history.ts:57`), so SQLite needs exactly
    this key; the dedup lookup by `id` also filters `leaderboardId`, `contactId`, `createdAt` (served by `LeaderboardScoreEvent_leaderboardId_contactId_createdAt_idx`). `PipelineItemActivity` changes to PK `(id)` (no lookup needs `workspaceId` in the key).
12. **Trigger order on a `Workspace` delete**: the cascade deletes events and fires one rollup trigger per event row. For a large workspace this is slow inside one
    write tx; the purge code must delete the rollup rows and then the events in chunks **before** `DELETE FROM "Workspace"` (P2.2 risk 1 rule).
13. **`count` / `bucket` as column names**: valid SQLite identifiers; the DDL quotes them, and unquoted `SUM(count)` in ported SQL also works (checked).
