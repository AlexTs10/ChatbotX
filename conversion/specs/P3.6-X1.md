## Decisions

- `Call` keeps its four fields: the locked fixture builds `Call {..}` and
  `Principal {..}` by struct literal. `call.token_id()` reads the token id of
  the running `dispatch_as` (a tokio task-local, the `AsyncLocalStorage`
  pattern of the original). `dispatch` (no principal) gives `None`.
  Accepted by the orchestrator.
- `ApiState::new(db, app_url)`: every service off (no realtime, kv, jobs;
  audit records dropped; bus without subscribers). `with_jobs` also turns on
  the audit writer. The server wires a `JobStore` on the app database, the
  `Kv`, and the `Realtime` producer when the gateway is on.
- The in-process bus (`events::EventBus`) is a list of subscribers that
  `publish` awaits in order; a subscriber error is logged ("Failed to emit
  event: <type>") and the next subscriber still runs (`emitToAllEmitters`,
  `Promise.allSettled`). Events are typed: `Event::Trigger(TriggerEvent)`
  (the `BaseEventEmitter.emit` shape: type, workspace id, contact id,
  metadata) and `Event::Bus { event_type, payload }` (for the durable buses).
- Trigger / webhook emitters are bus subscribers (`QueueEmitter::trigger` /
  `::webhook`): they queue `evaluate-triggers` / `evaluate-webhooks` jobs.
  The workers that evaluate them (and start flows) are out of scope.
  `isWorkerContext` (skip emits from the worker) is not ported: the API is
  never a worker context.
- The active-condition cache keeps only the RAM layer (5 s TTL) of
  `BaseCache`; the Redis layer (1 h) shared state between processes, and the
  lean build is one process.
- The audit writer enqueues `sendAuditLog` on the `default` queue with job id
  `audit-log-<id>`, as the original. The handler (`send-audit-log.ts`) does
  nothing on the community edition.
- `dispatchAuditRecord` / the global recorder registry is not ported: the
  writer is injected through `ApiState`.
- The server wires `AuditService::direct(db, edition != community)`: the
  `sendAuditLog` job handler runs in the request (no default-queue worker is
  ported yet, so a queued job would wait for ever). The community edition
  writes no rows, as the original handler. `AuditService::new(jobs)` (the
  queued form of the original) is what `ApiState::with_jobs` sets and what
  the ported tests check.
- The server subscribes the trigger and webhook emitters to the bus (on the
  `JobStore` and the SQLite condition caches). Their jobs wait for the
  trigger / webhook worker port.

- The audit actor comes from the token middleware context
  (`AuthContext.audit`: workspace owner, `api-token:<id>`, IP, user agent)
  and is set by the route layer around `dispatch_as` (`with_audit_context`).
  A call through `handlers::dispatch` (tests) has no actor, so no record.
- The by-name tag routes (`addTagsByName`, `removeTagsByName`, `setTags`)
  read the contact's tag ids before and after the write to find the changed
  pairs (the services do not return them).
- `/v1/members`: business module `workspace_member` (list / get), handler
  `handlers/workspace_members.rs`; the output keeps only the eight
  `workspaceMemberPermissionsSchema` keys of the stored permissions.

## Behaviour differences

- Emits are awaited in the request (the original fires several of them
  without `await`). A subscriber error is logged, never returned.
- No `analytics:dashboard` events (`contact:created` / `contact:deleted` /
  `contact:blocked`): no dashboard consumer is ported, and the contact
  services do not return the inbox attribution they need.
- `contacts.upsert` (new contact) emits `newContact` without
  `contactInboxId`; an upsert of an existing contact emits no
  `contactInfoUpdated` events (no before snapshot).
- `contactInfoUpdated` / `customFieldValueChanged` on `contacts.update` carry
  no `contactInboxId` / `decisionFlowOrigin` (the public route sets none).
- `/v1/members` lists in `id` order (the original has no `ORDER BY`).
- The trigger / webhook jobs are queued but no worker consumes them yet.
